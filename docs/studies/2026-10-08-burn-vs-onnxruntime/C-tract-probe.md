* **M8 (the one clean win).** CPU profile: `OptMatMul` 226 nodes 54.0 ms (61 %), `MultiBroadcastTo` 52 nodes 17.1 ms (19 %), rest small; `Entire network performance: 88.4 ms/i`; FMA(F32) 2.82 G per run. Metal bench 127.2 ms/i vs CPU 93.6 ms/i. `--threads 4` was 2.9× **slower** than 1 thread at load ≈ 25 (rayon pool contending with ~40 other runnable threads; not a quiet-machine number).
* **M4.** Loads with `MmapDataResolver` (RSS 2.88 GB for an 880 MB file plus i32 casts of the weights). Optimised op mix: `Reduce<Sum>` 241 nodes 2555.6 ms, `OptMatMul` 340 nodes 119.7 ms, `Cast` 475 nodes 58.3 ms, `DynamicQuantizeLinearU8` 169 nodes 11.4 ms, `RmsNorm` 144, `DepthWiseConv` 26, `Silu` 72; `Entire network performance: 2781.7 ms/i`; FMA(I32) 7.49 G + FMA(F32) 0.67 G per run. Excluding the weight sums the rest of the graph is ≈ 230 ms/i on one core. Under `--metal` the GEMMs/elementwise/norms run on the GPU (`MetalMlxGemm` 146 nodes 11.5 ms accel, `MetalMul`, `MetalRmsNorm`, `MetalSilu`, `MetalSoftmax`, `MetalConv` 27 …; total accelerator ≈ 34 ms) but the 97 weight `Reduce<Sum>` (2392.5 ms) remain on the CPU: `Entire network performance: 2850.8 ms/i`. Numerics: encoded max abs 0.017 on a 0.36-max tensor (4.9 % of range), cache_last_time_next up to 5.2 on a 61-max tensor — tract's `DynamicQuantizeLinear`+`MatMulInteger` path does not reproduce ORT's int8 rounding; whether that is acceptable for ASR needs a WER check, not done here.
* **M9.** All ops are implemented (the unoptimised typed graph reproduces ORT to 3.6e-7); only the declutter pass trips (`Downsample` pulled over `AddAxis`: Invalid axis). Unoptimised it is 1.07 ms/i vs ORT 0.054 ms (generic ops, no codegen — the documented "silently slow" trap), and `-O`/`bench` cannot be used without declutter.
* **M1.** Two spec deviations in the OnnxScript export that ORT tolerates and tract's shape rules reject (STFT rank-2 signal, Range rank-1 limit). Not pursued past one patch; the original file was not modified (patched copy at `models/nemo128.stft-r3.onnx`).
* **M7.** `If_117` (pyannote SincNet) has branches of different rank; tract requires identical typed output facts across branches and does not fold the (shape-derived, actually constant) condition before typing.
* **M2 / M6.** 8-bit `MatMulNBits` (block 32) is what `onnx.quantize`/HF exported; tract 0.23.8 implements only 2- and 4-bit. The 945 MB file parses in < 1 s (mmap) and fails at the first MatMulNBits node.
* **M3 / M5.** `com.microsoft::DynamicQuantizeLSTM` (ORT's dynamically-quantised LSTM) is not implemented; `MatMulInteger`/`DynamicQuantizeLinear`/`TopK`/`ReduceLogSumExp` in the same graphs are.

## 3. Behaviour notes

* **Symbolic dims from ONNX are a trap for the CLI default.** With default options tract keeps every `dim_param` of `value_info`/outputs as a symbol and fails to unify it with a concrete `-i`/bundle shape: M1 `Impossible to unify Val(1) with Sym(batch_size)` (StridedSlice), M8 `Unifying shapes B,512 and 1,512 · Impossible to unify Sym(B) with Val(1)`, M3/M5 `… Sym(encoder_outputs_dynamic_axes_1) with Val(1)`, M7 `Unifying shapes Conv122_dim_0,80,Conv122_dim_2 and 1,80,7975`. Workaround used: `--onnx-ignore-value-info --onnx-ignore-output-shapes` (API: `OnnxOptions`); alternative not tried: keep the symbols in the input fact and bind them at run time (`--set`).
* **Bench semantics.** `bench` prints `Bench ran N times, X ms/i` = mean; `--max-time` is in ms and defaults to 5000 (we set 600000 so `--max-loops 20` governed); `--profile` per-node times carry dispatch overhead and are not an A/B tool (doc). The Metal `bench` includes GPU kernel compilation only in the warmup; the first-run cost showed up as 14 s wall for M8's Metal bench vs 3 s on CPU.
* **Noise.** 1-minute load average was 23–35 during the small-model runs and **54–70 during M4's `--threads 4` and Metal benches** (other sessions' cargo builds). Single-thread numbers are the least affected; the `--threads 4` regressions are consistent with CPU oversubscription and should be re-measured on a quiet machine before being believed.
* **RSS.** tract mmaps the ONNX file (`MmapDataResolver`): M2 reached 3.5 GB RSS in the 1 s before failing, M4 2.88 GB steady; M8 ≈ 190–240 MB. Nothing approached the 24 GB stop line; the memwatch log (`logs/memwatch.log`) peaked at 1.6 GB resident during M4 benches (RSS as `ps` reports; `/usr/bin/time` max RSS includes the mapped file pages).

## 5. Streaming: pulsification vs. M4's cache-state ONNX

* tract's streaming story is **pulsification at translate time**: a full-sequence model (NNEF/tract-OPL, with a symbolic time axis) is rewritten by `tract-pulse` into a network that consumes a fixed pulse per step and carries its own delay/state ops (runtime needs only `tract-pulse-opl`). The nemotron example does exactly this: `pp.transform(Pulse::new("1600").symbol("INPUT_SIGNAL__TIME"))` on the preprocessor (100 ms pulses) and `Pulse::new("112")` on the encoder (14 output tokens × 8 subsampling), then reads `pulse.delay` / `pulse.output_axes` properties; the CLI equivalent is `tract … --pulse 'T=112' run --input-from-bundle io.npz --assert-output-bundle io.npz` (the CLI accounts for `pulse.delay` when comparing against the batch reference). Both NeMo examples start from the **NeMo checkpoint**, not ONNX: `pip install "nemo-toolkit[asr]" "torch_to_nnef[nemo_tract]"` then `t2n_export_nemo -s nvidia/nemotron-speech-streaming-en-0.6b -e assets/model -tt skip --split-joint-decoder` (Parakeet: `-s nvidia/parakeet-tdt-0.6b-v3`), producing `preprocessor/encoder/decoder/joint.nnef.tgz` + `model_config.json`; the Rust side uses `tract::nnef()?.with_tract_transformers()?`, `SetSymbols BATCH=1`, `transformers_detect_all`, a `patch` transform to derive `length` from `shape_of(audio_signal)`, and `runtime_for_name("gpu-or-cpu")`. That path needs **Python + NeMo + torch at export time** (once), yields f32 NNEF (not the int8/MatMulNBits ORT artifacts theuth ships), and ships no ONNX loader at runtime.
* M4 is the other design: NeMo's **cache-aware streaming export to ONNX** with the state made explicit as tensors (`cache_last_channel [24,1,70,1024]`, `cache_last_time [24,1,1024,8]`, `cache_last_channel_len`) and a fixed 65-frame chunk (9 pre-encode-cache + 56 mel frames, as parakeet-rs feeds it). tract runs it as a **stateless graph** — no pulsification is involved or needed; the application threads the cache tensors between calls exactly as it does with ORT. What tract adds here is nothing (and today it costs 32× on the MatMulInteger path, §2).
* The pyannote/wespeaker graphs are offline (whole-window) models; pulsifying them would require their NNEF form and a symbolic time axis; not attempted.

## 6. Metal runtime maturity (as documented and as measured)

* Documented: "GPU is first-class. `cuda` + `metal` `Runtime` impls … automatic per-node CPU fallback when GPU rejects a shape; virtual `gpu` / `gpu-or-cpu` names" (CHANGELOG 0.23); Metal kernels are a mix of ported MLX kernels (gemm, `gemv_wide`, implicit-GEMM conv for NHWC single-group 2-D, Sdpa/flash attention via Metal Flash Attention metallib), GGML and MFA backends selectable with `--force-metal-backend`; recent entries add pooling, Resize, multi-axis Reduce, native STFT/FFT on GPU, constant Pad, `Not`, f16 GGML matmul, fused RMSNorm. Primary production target stated in `doc/pipeline.md`: "Single-threaded ARM CPU loads are the primary production target; x86_64, Apple Silicon (CPU and Metal), CUDA, and WASM are all supported."
* Measured here: both runnable graphs were **slower on Metal than on one CPU core** (M8 127 vs 94 ms; M4 2768 vs 2640 ms) because unsupported nodes force `DeviceSyncToHost` round-trips (M8: 55 syncs = 73 ms of a 112 ms run, pooling/downsample on CPU) or because the dominant op is a CPU-only artefact of the quantised lowering (M4). GPU kernel time itself was small (M8 ≈ 19 ms, M4 ≈ 34 ms). Metal numerics matched CPU/ORT on M8 (4.5e-5).
