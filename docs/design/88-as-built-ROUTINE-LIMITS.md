# 88 — as built: ROUTINE-LIMITS

Routines get a real model picker and a settable per-run time limit: a new
front-matter key `run_timeout:` per routine, and the global
`schedule.run_timeout_secs` default made live and editable from Settings.
Branch `feat/88-routine-limits`, base `fca080be`. Line numbers are after the
change. Brief: `omp-ROUTINE-LIMITS.md` (2026-10-03).

## §1 Semantics

- `run_timeout:` — humantime as written (`45m`, `2h`, `90s`); the time limit
  of ONE run of this routine. Absent → the global `schedule.run_timeout_secs`.
  Allowed with every kind (`cron` / `every` / `at`, with or without `when:`);
  independent of `until` / `max_runs`. Below 30 s → `run_timeout: below 30s`.
  No upper bound. The existing `timeout:` (the watcher sensor wall clock,
  40 §5) is untouched.
- `schedule.run_timeout_secs` is now owned live by the schedule actor:
  `SetRunTimeout { seconds }` (≥ 30, else `run_timeout: below 30s`) changes it
  for runs fired from then on (in-flight runs keep their deadline) and
  persists it to `<data_dir>/config.yaml` under `schedule:`; `GetRunTimeout`
  reads it. `info().schedule_run_timeout_secs` carries it to the UI; `0` from
  an older harness.
- A run past its deadline is cancelled exactly as before (`cancel_tree`, the
  history row says `timeout`); only the deadline's source changed.

## §4 Deviations

- **`Run.deadline` test** (brief: "fires a routine with `run_timeout: 30s` and
  asserts the `Run.deadline`"). `Run` is only built on the session path of
  `fire`, which needs a registered `agent::Agents` actor; the unit tests in
  this crate have none (`plain_schedule_path_is_untouched` pins "agent is not
  running"), and spawning a real supervisor (model catalog, auth client, …) in
  a schedule unit test is not warranted. Instead the deadline computation was
  pulled into `Schedule::deadline_for(run_timeout)` — the one expression
  `fire` uses at `:1132` — and the test asserts, for files loaded from disk,
  that a `run_timeout: 30s` routine's deadline is 29–30 s out while a plain
  one gets the actor's 60 s default. (The range tolerates two `Instant::now()`
  reads landing in the same clock tick, which happened on the first run.)
- **`SetRunTimeout` test value**: the test actor's default is 60 s, so
  "set to 60" would not show a change; the test sets 90 and asserts
  `GetRunTimeout` = 90 and `run_timeout_secs: 90` in config.yaml. The 29 →
  `run_timeout: below 30s` arm is as specified. `schedule` has no
  `serde_yaml` dev-dependency, so the file is compared as text
  (`write_config_value` creates exactly `schedule:\n  run_timeout_secs: 90\n`).
- **UI smoke**: not run against a live engine (the brief's gates are
  `bun run check` and `bun run test`, both green; the worktree rules forbid
  touching `~/.theuth`). The new surfaces are type-checked and follow the
  existing `RuntimeAccessFields` / `Loop.tsx` patterns verbatim.
- README: one comment line edited in the config block rather than left alone,
  since that line is the only place `run_timeout_secs` is documented.
