## The product in one paragraph
A **cell** is a block of code the user runs with one press, inside theuth: in a chat reply (the agent presents it when told to prepare-but-not-run), in a note, or in a notebook's note. Bash, zsh, sh, pwsh, Python (a local interpreter, or theuth's built-in Monty when that is enough) and later JavaScript. The engine owns a persistent kernel per scope, so `cd`, exports and variables carry between cells and between lines. Output streams live into the cell for the user (a real terminal while it runs, so prompts like pulumi's arrow-key "Do you want to perform this update?" can be answered); when the run ends the agent gets a cleaned, capped, secret-scrubbed copy in its context. The agent can present, edit and read cells; it can never run one. This is not a tool and changes nothing in tools/MCP/policy/approvals.

## Calls

D1 ONE GRAMMAR. A cell is a fenced code block in a runnable language whose body starts with `#|` option lines (Quarto's convention; `//|` for JavaScript). Identical text in a chat reply, in `doc_insert` markdown, in a note's code block, in an exported .md. A fence without the header stays a snippet (copy only). Options live in the body because BlockNote's code block stores only `language` and the fence info string does not survive notes, Slack or copy (streamdown 2.6 does pass `meta` to renderers — irrelevant once notes are in scope). Rejected: a `present_cells` tool call (no streaming, cannot live in notes, a second grammar); Runme-style JSON in the info string (lost in BlockNote/yrs/channels; ids written back into human text); an OpenUI `Cell` in `app` (apps are live tool screens, not durable runbooks); making every bash/python fence runnable (snippets and examples would get Run buttons).

D2 OPTIONS (v1, closed set; unknown keys are a validation warning): `cwd` (absolute or ~; the agent always writes it in chat), `name` (stable id; same name later = new version), `label` (the Run button's text, naming the consequence: "Apply to ir-prod1"), `danger` (true: red outline, never in Run all, no keyboard run), `after` (name of a cell that must have succeeded — exit 0 and every expect met — before this one arms; the armed button shows that run's summary), `expect` (repeatable; text, or /regex/, that must appear in the output), `env` (repeatable KEY=value; values may hold vault placeholders), `python` (monty | auto | .venv | uv | absolute path; python cells only), `review` (true: the agent wakes when this run, or the Run-all pass containing it, ends), `private` (true: the agent gets exit/expect only, never output), `timeout` (duration). Reserved for wave 3: `on` (a sandbox VM / mesh engine). Note-level defaults (`cwd`, `shell`, `python`) in the note's front matter block (a `cells:` map).

D3 HUMAN PRESS ONLY, WHAT YOU SAW RUNS. A run starts only from an RPC sent by an authenticated owner client (desktop, web, phone) on a press or keyboard shortcut. No tool, runtime function, MCP tool, routine, subagent, ACP child, the owner's double, a doc guest or a channel can start one. The press is the approval: one press, the label states the consequence, never a second confirmation dialog. Cells are outside tools.policy and the approval/double machinery entirely; they are audited instead (D17). Guarded execute (nteract's `ExecuteCellGuarded{cell_id, observed_heads}`): the press names the cell and the digest of the text the user saw; the engine reads the source from its own record (the message snapshot or the doc block), never from the button payload, and refuses with "this cell changed — look again" when the digest no longer matches (superseded, edited by a member, re-written by the agent). A user edit in the editor is sent as the edit and recorded as `edited` with attribution (operator vs author, nteract's identity model). Rejected: routing runs through tools.policy (the double could answer; approval fatigue; agent and user actions mixed); nteract's model where agents run cells via MCP (breaks the guarantee).

D4 KERNELS. Engine-owned, one per (scope, spec). Scope = the chat session for chat cells; the document for note cells. Specs: shell `bash` / `zsh` / `sh` / `pwsh` (a PTY on the existing jobs/PTY layer, marked as a cell kernel so the agent's `send`/`cancel_job` refuse it and `jobs()` does not list it); `python` (a local interpreter running a stdlib-only theuth kernel shim over a framed pipe: persistent namespace, last-expression display, streams, input(), rich MIME via _repr_*_ and matplotlib capture, SIGINT interrupt); `monty` (an isolated in-process Monty instance per scope with NO tool bindings, type-checked before each run, time/memory limits); `node`/`deno`/`bun` in wave 3 (same shim protocol). An optional Jupyter-protocol backend (runtimed's jupyter-zmq-client / jupyter-protocol, BSD-3) for interpreters that have ipykernel or `deno jupyter` is wave 3. Lifecycle: start on first run, idle shutdown after `cells.kernel_idle_hours` (12), Restart and Close from the kernel strip, closed with the session/doc. Rejected: Jupyter protocol for everything (ipykernel in every venv, no bash kernel by default); a fresh process per run (kills line-by-line, cd/export).

D5 ENVIRONMENT. Kernels start with the user's login-shell environment (captured once per engine start by running the login shell, refreshable from the kernel strip) so PATH, AWS_PROFILE defaults and ssh-agent match Terminal.app; the engine's launchd environment is never used. The cell's language decides the program: a `bash` cell runs bash even though Sky's login shell is zsh — the whole class of zsh paste traps (PIPESTATUS, trailing # comments) disappears. zsh kernels load the user's real zsh config plus `setopt interactive_comments`. Shell integration (theuth-owned rc snippets) emits OSC 133 command marks (start/end + exit code) and OSC 7 cwd, which the engine's terminal parser reads: completion and exit codes are exact, no prompt-pattern waits.

D6 HOW CODE ENTERS A SHELL KERNEL. A cell whose cwd does not exist at press time does not start — never a fallback to home or the kernel's current folder; the cwd chip warns at presentation and the cell arms when the folder appears (an earlier cell may create it). Every run (whole cell, one line, a selection) writes the exact code to a run file and `source`s it (dot-source in pwsh): state persists, nothing is typed ahead onto a program's prompt, an incomplete construct fails at once instead of hanging in a continuation prompt. CWD RULE: a whole-cell run always `cd`s to the cell's cwd and exports its env first; a line/selection run does so only when the kernel's previous run came from another cell (or the kernel is fresh) — so `cd sub` on line 1 holds for line 2.

D7 INTERPRETERS. `#| python:` names it. `auto` resolves deterministically from the cell's cwd: nearest `.venv`/`venv` upwards → the uv project's interpreter → pyenv/conda active → `python3` on the login PATH → none (cell invalid with a one-press fix). Monty is chosen when sufficient (the user's words): pure computation over Monty's stdlib subset — no third-party imports, no subprocess, no network, no files outside the cwd; the engine runs Monty's type check when the cell is presented, and a failing check shows "Monty can't run this: … — use Python 3.12 (.venv)" with a one-press switch. The interpreter chip shows what will run (nteract's env-source vocabulary: `.venv`, `uv:…`, `conda:…`, `pyenv:…`, `system`, `Monty`) and is a menu of the discovered interpreters (`interpreters(cwd)`, also a read-only runtime function for the agent). Windows: pwsh native; bash via Git Bash or WSL if found.

D8 OUTPUT MODEL = Jupyter's. nbformat v4 output types (stream, display_data, execute_result, error) with MIME bundles, plus theuth's `exit` (code/signal/seconds) and `expect` (met/missed). Shell runs stream terminal bytes: live in an xterm (reusing TerminalViewer's attach, keys and 167's mappings; the user can type into it), frozen on completion to text with SGR colours for the static view. For the record and the agent, the engine renders the run's byte range through a terminal emulator into final text (carriage returns resolved, spinners collapsed, escapes gone) — the end of the agent's regex stripping; nteract does exactly this server-side with alacritty_terminal (10,000-line scrollback; `stream_terminal.rs`) — reuse whatever emulator the engine's PTY layer already has (167). Ordering contract (nteract): the terminal status is written after the last output; consumers read the record, broadcasts are hints. Lifecycle never starves behind output: Stop/interrupt travel on their own channel and stay responsive during an output flood. Huge output: the UI collapses to the last N lines with "show all"; the run store keeps everything.

D9 UI — LEAST CODE, HIGHEST QUALITY (Sky 2026-11-03 17:2x: "why do we care if there's no license. the focus is the least code and highest quality product. we don't care about the license issues."). Licences are not a gate anywhere in this design. Use nteract's components as they are, restyled only through theuth's tokens: install from the `@nteract` shadcn registry where the item is current, and take the production version from nteract/nteract `src/components` where the registry lags or lacks a piece (the registry has no `code-cell`; `codemirror-editor` needs `lib/dark-mode.ts` that only `markdown-output` ships; `CompactExecutionButton` is not in the registry) — 171-recon-theirs.md §1.7/§6.1. Pieces: `ansi-output` (+ anser, escape-carriage; swap its hard-coded stream colours for tokens), `output-area` + `media-router` + `error-boundary` + `highlight-text` (nbformat-shaped list, collapse, maxHeight, MIME priority, custom renderers — wrap, don't fork), cell chrome `cell-container` (re-colour the fixed sky/emerald/amber ribbons), `cell-header`, `cell-controls`, `execution-status`, `runtime-health-indicator`, `CompactExecutionButton`. Skip widgets/anywidget/ipycanvas/isolated-renderer in v1. nteract is chrome, not a runner: it has no run-line, run-selection, gutter run or bash language — those few pieces are ours. Editor: @uiw/react-codemirror (already a dependency: knowledge/Editor.tsx, agents/CharterEditor.tsx) + @uiw/codemirror-extensions-langs (bash, python, javascript), `basicSetup:false` plus a small theuth extension set, one `EditorView.theme` reading theuth's CSS variables, keymaps Shift+Enter (run cell, advance), Mod+Enter (run line or selection), a hover ▶ in the gutter per line, a "Run selection" pill on a selection. Live shell output: @xterm/xterm (already a dependency, TerminalViewer). HTML/SVG/markdown outputs render inside theuth's own sandboxed inline-page frame (120) — a quality call (agent-authored HTML must not reach the network), not a licence one. One `Cell` component serves chat, notes and notebooks. Options render as chips (language, interpreter, cwd, host when it is not this device, name), not as raw `#|` lines; a raw toggle shows the text.

D10 CHAT PLACEMENT. Cells render inline in the reply as the agent writes them. A reply with ≥ 2 cells gets a runbook bar: Run all (label names its boundary: "Run all · stops before Apply to ir-prod1"), progress (2/3), kernel state. Run all runs in order and stops before a danger cell, at a non-zero exit, at a missed expect, or on Stop. A small kernel strip (shell · state · live cwd · Restart · Close) shows whenever the session has a live kernel — state is never invisible. Finished cells fold to a one-line summary (✓ exit 0 · 41 s · expect ✓), the latest one stays open. Same `name` re-presented → the older cell is superseded: its Run is disabled with "replaced by a newer version ↓"; its outputs stay. Chat cells are editable before a run ("edited" badge; the agent sees the code that actually ran).

D11 WHAT THE AGENT SEES. When a run ends, the session receives one `<cell_result …>` input (the `<job_result>` pattern): attributes name, run id, exit, seconds, cwd, interpreter, expect met/missed, edited, pressed from which device; body = the emulator-cleaned output, head+tail capped (`cells.agent_bytes`, 8 KiB), vault values scrubbed and credential patterns (AKIA/ASIA keys, aws_secret_access_key, session tokens, JWTs eyJ…, ghp_/xox* tokens, PEM private keys) masked; `cell_output(run)` reads the rest (redacted), `cell_runs(scope)` lists runs. Private cells send exit/expect only. Validation problems in a just-finished reply come back once as `<cell_error>` (the `<surface_error>` pattern) so the agent fixes them by re-presenting. Cells the agent wrote into a note report their runs to the session that wrote them (origin session) as `<cell_result>` too; notebook chats get a `<notebook_changes>` notice (ids only — 157's rule).

D12 WAKE RULE (fork F1). A `<cell_result>` joins a running turn at once. Otherwise it is delivered quietly (in context at the next turn) unless the cell or its Run-all pass carries `review: true`, which starts one turn after the pass ends; the output's "Ask theuth" button starts a turn on demand. Sky's 2026-10-16 mode ("allow me to review the output, and then tell you what to do next") is the default; `review` is how the agent keeps a plan → review → apply promise.

D13 SAFETY WITHOUT CONFIRMATIONS. (a) consequence labels + danger styling + Run-all boundaries (D2/D10); (b) `after` gates: Apply arms only after its preview succeeded and shows that preview's summary on the button — the lesson of the 2026 terraform-destroy incident (approval existed; the consequence was not on screen); (c) a deterministic lint that puts chips on a cell: invisible/bidi characters, a download piped into a shell, base64-decoded execution, a call into a script the agent edited in this session (with the diff one click away); (d) secrets: vault placeholders are substituted only at run time by the engine, never shown in the editor or the agent's copy, and vault values are scrubbed from every view; (e) never re-run anything automatically (engine restart = the run ends "lost — engine restarted" with the last screen and log path, the kernel is gone, nothing is replayed, and the button reads "Run again", never a silent retry); graceful quit / update waits for running cells (F6 a).

D14 NOTES. A note's code block whose body starts with `#|` IS a cell — no BlockNote schema change, no new ProseMirror node, no Yjs change: CodeBlock.tsx's render (already ours, already rendering json-render/mermaid diagrams) mounts the Cell for it. "Make it a cell" / "Make it plain code" toggle the header. Outputs and run state live outside the Y.Doc in an engine-side run store keyed by (doc, block id), with the latest run per cell replicated to members as capped, scrubbed text (fork F2) — the nteract pattern (content doc vs runtime state) and the Jupyter AI v3.1 data-loss race argue against writing outputs into the shared CRDT. doc_read renders a cell as its fence plus an `output` fence (capped) and a `ran 14:38 · exit 0 · 33 s · expect ✓` line; doc_insert of a `#|` fence creates a cell. A run whose code no longer matches the block's text shows "ran an earlier version" (stale, never re-run). One kernel per note per spec; the note header gets the kernel strip and Run all. Export: .md carries cells and last outputs; .ipynb import/export is wave 3 (nbformat crate).

D15 SHARING. Members with edit rights can edit cells (collaboration does not regress); ONLY the owner can run, on the owner's engine. A cell whose text was last changed by a member shows "Changed by <name> since your last run · Review diff" and its button reads "Run <name>'s edit" — doc-member text is untrusted input (59). Guests see the replicated latest outputs (F2) and never a Run button.

D16 SURFACES. Desktop (macOS/Windows/Linux), web and phone run cells (the press executes on the engine that owns the session/doc; the host chip shows which machine when it is not this device). TUI renders cells as code with "run in the app" (a run key is wave 3). Slack/Telegram/Signal render the fence as code plus a "Run in theuth" deep link; no runs from channels in v1. A run longer than `cells.notify_after_secs` (30) that ends while the window is unfocused posts a system notification.

D17 AUDIT. Every run is a durable record: who pressed (device/client), the exact code run (after edits) and its digest, the presented code's digest, cwd, interpreter, env NAMES (never values), timestamps, exit, expect, output digest, log path. A cell's history menu lists its runs; the session/doc lists all.

D18 PROMPTING. A short `## Cells` section in the system prompt (≤ ~18 lines) plus a `cells` skill. Triggers: the user says prepare-but-don't-run in any words ("prep it, don't apply", "give me the commands", "I'll run it", "present the commands", "step by step, I'll review each output", "make me a run sheet"); a step changes production or shared state the user has not told the agent to change; it needs the user's login/SSO/MFA; it is interactive; the user wants to watch. Not triggers: work the user asked the agent to do (tools as today), read-only investigation the agent may run itself under policy, snippets to read. The mode is sticky for that work until the user lifts it: read-only checks stay the agent's (unless "hands off entirely"), every changing step becomes a cell. Writing rules: cwd on every cell; one action per cell; checks before changes; explicit --profile/--context/-s; `label` + `danger` on every changing step; `after` from apply to its preview; `expect` from the run sheet's "You should see"; `review` when it promised to read the output; never run the same command itself, never type into a cell kernel, never tick a run sheet's boxes, never add --yes/-auto-approve to a danger cell unless asked. Placement: ≤ ~5 one-off steps in chat; longer or repeatable procedures in a note (doc_insert the same fences) with a one-line link in chat. After a result: check expect, report the counts that matter in one or two lines, propose the next cell or a superseding version. Amend the existing prompt lines "commands to run stay a plain code block" (Show-first table and rules) to "commands the user runs in their own terminal stay a plain code block; commands the user asked to run here are cells".

D19 WHERE IT LANDS (writer verifies against the tree): a new `crates/cells` (fence parser, options, kernels, run store, redaction, emulator cleaning), RPC methods + events in crates/rpc (owner-only), `<cell_result>`/`<cell_error>` delivery in crates/agent, read-only runtime functions `cell_runs` / `cell_output` / `interpreters`, the prompt section where the other sections live, `skills/cells.md`, UI in `components/cells/` + the streamdown renderer for runnable languages (falls back to the stock code block without a header) + CodeBlock.tsx's cell branch.

D20 WAVES. W1 CHAT-SHELL: contract (types, RPC, events, bindings) + engine shell kernels/PTY/OSC 133/run store/delivery/redaction + UI Cell/runbook bar/kernel strip in chat + prompt section + skill. W2 PYTHON-NOTES: python shim + Monty kernel + interpreter discovery + notes cells (CodeBlock branch, doc_read/doc_insert, run store keyed by block, replication of latest outputs, sharing rules, notebook notices, origin-session delivery, note front-matter defaults). W3 REACH: JavaScript kernels, Jupyter-protocol backend, .ipynb import/export, TUI run key, `on:` sandbox/mesh targets, rich outputs for guests (and the detached PTY host only if Sky picks F6 b).

## Forks for Sky (the design applies the recommended default; §0 and §18 list them)
F1 Wake rule — when a run ends, does the agent start talking? (a) only when the cell says `review: true` or you press Ask theuth — RECOMMENDED; (b) after every Run-all pass; (c) also on any failure.
F2 Outputs in shared notes — (a) the latest run's text output (capped, scrubbed) replicates to members — RECOMMENDED; (b) owner-only outputs; (c) full outputs incl. images.
F3 Phone — (a) the phone can run cells, danger cells included, with the same consequence label — RECOMMENDED; (b) the phone runs non-danger cells only; (c) desktop only.
F4 Editing agent cells in chat before running — (a) allowed, "edited" badge, the agent sees what actually ran — RECOMMENDED; (b) read-only in chat; edit only in a note.
F5 JavaScript — (a) wave 3 with node/deno/bun through the same shim — RECOMMENDED; (b) wave 2; (c) not at all.
F7 What `auto` means for Python (added in review, 18:10) — (a) the local interpreter first, Monty only when none exists; the agent writes `python: monty` on purpose for pure computation — RECOMMENDED; (b) Monty first whenever every `auto` cell in the scope is sufficient.
F6 Surviving an engine restart — Sky ruled in 109 R1 that jobs are not durable, and in Revision 1 rejected job adoption / no-kill shutdown as "process-surviving jobs by another name" ("I thought we decided jobs aren't durable"; knowledge decisions/theuth-durability-design-109-rulings-2026-10-06; docs/design/109-durability.md:28,42,46). ## Anchors from the recon (verified 2026-11-03 against theuth-171 @ 6eba65b1 and the nteract clone; the writer re-opens each)
