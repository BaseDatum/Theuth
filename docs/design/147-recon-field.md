# R3 — Survey: generated code maps / architecture docs, what users value (2026-10-08)

Scope: how tools GENERATE architecture maps of a codebase (method, grounding, refresh, navigation, limits, cost, licence, praise/complaints), 2024–2026, plus research anchors. Rendering rules are NOT redone here — see `facts/codemap-visualisation-survey-2026-09-28` (≤ 20 nodes, lists first, butterfly, no hairballs); this report builds on it.
Evidence marks: **[V]** verified — I read the page/API today; **[I]** inferred from verified facts; **[M]** memory, not re-checked. Web search was degraded (brave/google/qwant blocked); most evidence is GitHub REST + MCP issue reads + direct page reads + HN Algolia.

## 0. Headline findings

1. The field has converged on ONE generation shape: **static index → cluster/decompose → LLM names + describes each cluster → recurse into clusters → render as Mermaid/graph + prose, with every node linked back to files/lines.** CodeBoarding, CodeWiki (ACL 2026), DeepWiki (cluster-based planning), Understand-Anything and oh-my-mermaid all do this; the pure-LLM ones (GitDiagram, Swark) are the ones with the worst complaint records. [V]
2. **Grounding beats prose.** Every survivor shows the source snippet/line next to each claim (DeepWiki "we display the code snippets so you can double check" — HN 43796308; Code Wiki "hyper-linked to files and definitions"; Codemaps "send you to the exact part of the codebase you clicked on"; CodeViz click-to-code). The one product that drew pictures without a reliable code anchor at scale (CodeSee) is dead. [V]
3. **Users' top three complaints, in order: (a) invalid Mermaid syntax from the LLM, (b) tokens/time on first run, (c) unusable/wrong at scale (hairball, prompt overflow, missing components).** Measured below with issue ids. [V]
4. **Accuracy is the open wound.** ICSA 2026 (340 repos, 4,137 views): best agent still 22.6 % clarity failures, completeness fails on 73–88 % of views, and the general-purpose Claude Code agent scored WORST (71.8 % clarity failures). DeepWiki's public backlash (LibreOffice "uses Buck", LLVM missing TableGen) is the same failure in production. [V]
5. **Shneiderman + C4 are what people actually ask for**: a top-level map with ≤ ~8 components, drill-down per node, text form of everything, and "where does X happen?" search. Nobody asked for a force graph; two projects had to remove theirs (Understand-Anything #14, #27; CodeViz HN "top level graph with 5 items… not useful, quite small in the left panel"). [V]

## 2. What users notice / value / complain about — ranked by evidence weight

Value (praise, in order of frequency across sources):
1. **Click-through to the exact code** — Codemaps' core pitch, Code Wiki's "hyper-linked", CodeViz click-to-code, DeepWiki snippets; CodeSee's buyers wanted "a picture someone else had already made sense of" with tours. [V]
2. **Richer downstream answers** once a map exists — UA #76: chat/explain "much richer… than plain Claude Code"; Codemaps `@codemap`; Code Wiki Reddit comment about Gemini CLI querying the wiki; DeepWiki MCP is the "preferred way" (aitidbits). The map is valued as **agent context** as much as a human artefact. [V]
3. **Plain-text, diffable, in-repo output** (`.omm/`, `.codeboarding/`, `.ua/`) — hysenlabs on both omm and CodeBoarding: "a diagram in a text file can be argued about in a PR". [V]
4. **Scoped question → focused map** (Codemaps, CodeViz NL search, Cursor's guide). [V]
5. **Edge labels that say why** (omm rule "every edge must have a meaningful label"; CodeBoarding edges like "reads call graph edges and nodes"). [V]

Complaints (ranked by issue count × comment count):
1. **Invalid Mermaid from the LLM** — GitDiagram ≥ 13 issues incl. #29 with 70 comments; Swark #7 cycles (12 c); UA #39 schema-invalid graph JSON. Pure-LLM emission without a parse/validate/repair loop is the single most-reported failure. [V]
2. **Tokens and wall time on first run** — UA #76 (19 c), #46, #212, #472; omm #20; CodeBoarding #298 (205 k-token prompt); README warnings to "run on a subscription". [V]
3. **Breaks or lies at scale** — UA #14 (2.7 k nodes freezes browser), #27 layout; CodeBoarding #298 overflow, #280 one-language crash; DeepWiki LibreOffice/LLVM errors, "fixation on large files while missing distributed components". [V]
4. **Too high-level to be useful / too small to read** — BigGo on DeepWiki "too high-level for engineering work"; CodeViz HN "5 items… not useful… quite small". The top level must be a *door*, not the destination. [V]
5. **Non-determinism / no verification** — hysenlabs on CodeBoarding; omm never renders what it writes; GitDiagram #7 "diagram can be false in case of misleading file names". [V]
6. **Platform/setup friction** — omm #24 (Windows detection), UA #385/#16/#25 (OpenCode/commands missing), Swark #35, CodeBoarding Windows #389. [V]
7. **Unsolicited/unofficial docs** — DeepWiki backlash about SEO and takedown (not applicable to a local tool, but relevant if theuth ever publishes maps). [V]

## 3. Research anchors (brief)

- **C4** (c4model.com [V]): four hierarchical abstractions and diagrams; the "zoom" is semantic (system → container → component → code), notation-independent. Every LLM tool's prompt uses this ladder; the ICSA study used C4-ish views as ground truth. [I]
- **Shneiderman 1996**, "The Eyes Have It" (cs.umd.edu/~ben/papers/Shneiderman1996eyes.pdf [V URL, M content]): overview first, zoom and filter, details on demand, relate, history, extract. Codemaps' outline→drawn→"See more"→jump is this mantra in product form.
- **Semantic zoom** (Perlin & Fox, Pad, 1993 [M]): representation changes with scale rather than scaling pixels — the justification for level-specific diagrams instead of one zoomable canvas (which is also the prior survey's anti-pattern).
- **Program comprehension**: Brooks 1983 beacons/hypothesis-driven top-down [M]; von Mayrhauser & Vans 1995 integrated model — experts switch between top-down (domain model), bottom-up (program/situation model) opportunistically; "program understanding behavior during corrective maintenance of large-scale software" found maintainers work mostly bottom-up from a beacon, not from the top (cs.kent.edu PDF, scanned, not re-read [M]). Implication: entry points (a symbol, a file, a failing test) matter as much as the overview.
- **Yoghourdjian et al. 2020** (prior survey): node-link path tasks fail above ~50 dense / ~100 sparse nodes. UA #14 (2,747 nodes) is the field re-discovering it. [V]
- **ICSA 2026 — "LLM-based Automated Architecture View Generation: Where Are We Now?"** (Miryala, Dhar, Vaidhyanathan; arXiv 2603.21178; sa4s-serc.github.io/ViewGeneration [V]): 340 repos, 13 configurations, 4,137 views, 110 human-evaluated. Clarity failures: zero-shot 40 %, few-shot 30.8 %, custom ArchView agent 22.6 %, **Claude Code general agent 71.8 %**. Completeness fails 73.6–88.3 % everywhere. Human level-of-detail success at best 50 %. Findings: "Summarization is the bottleneck — when repository summarization misses architectural intent the view drifts regardless of model"; richer notations beat plain boxes; control-flow and data-flow views generate most reliably; "general documentation" weakest.
- **CodeWiki, ACL 2026** (arXiv 2510.24428 [V]): hierarchical decomposition + recursive agents + diagrams; 68.79 % on CodeWikiBench vs DeepWiki lower; "LLMs… fail at the repository level, where capturing architectural patterns and cross-module interactions is essential."
- Code-hallucination surveys (arXiv 2511.00776, ACM 3728894) [V titles only]: taxonomy work, no architecture-specific numbers beyond the two above.

## 4. Lessons for theuth (8–12, each tied to evidence)

L1. **Generate from the index, not from file names.** theuth already has symbols, refs, imports, PageRank; use them to propose clusters and edges deterministically, and let the LLM only *name and describe* clusters (CodeBoarding's split; CodeWiki's dependency-graph-first; GitDiagram #7 shows what tree-only produces; ICSA: summarisation is the bottleneck, so feed structured facts not prose). Edge labels can come from actual ref kinds (calls/imports/implements) before any LLM touches them.

L2. **Validate every diagram before it is shown; repair or fall back to the list form.** Parse Mermaid (theuth has `procedures/mermaid-parse-check-local`), reject cycles where the grammar forbids them, re-prompt once with the parser error, else render the list. GitDiagram's 70-comment #29 and Swark #7 are the cost of skipping this. Also validate the structured output against a schema (UA #39).

L3. **Perspectives are the right top-level unit, chosen by evidence, not forced.** omm's 12-perspective catalogue with "don't force perspectives that don't exist" matches how users already ask Cursor ("data flow for our payment system"); ICSA finds control-flow/data-flow views generate best and "general documentation" worst. Derive candidates from index facts: HTTP route definitions → request-lifecycle; CLI subcommands → command-surface; DB clients → storage; ≥ 2 crates/packages → dependency-map.

L4. **Top level ≤ 8 nodes and it must be a door, not a poster.** CodeBoarding's self-map has 8; CodeViz's 5-node pane was "not useful" because it was terminal; BigGo: DeepWiki "too high-level for engineering work". Every node must open a child diagram or a file list; recursion stops only at "single file / trivial wrapper / external system" (omm rule). Stay under the prior survey's 20/12 caps.

L5. **Semantic zoom = one diagram per level, filesystem/tree as the model.** omm's "the filesystem is the nesting" and C4's level ladder both avoid a zoomable canvas; UA #14's proposed fix (file nodes first, expand on demand, cluster by dir/layer, layout off-thread) is exactly this. Store the map as a tree of elements (id = stable moniker), each with its own small diagram.

L6. **Anchor every node and edge to `path#Lx-Ly`, and show the evidence inline.** Codemaps' value claim is "densely linked to the exact lines"; Code Wiki links sections to definitions; DeepWiki's defence against hallucination is the snippet. theuth boards already have the anchor grammar — reuse it; a node whose anchor no longer resolves is marked stale, never silently kept.

L7. **Incremental by construction: source→element manifest + reconcile on index change.** omm #20 asks for exactly this; CodeBoarding ships it; UA defaults to it. theuth's index already reconciles per call — keep `element ↔ {symbol_ids, files}`; on change, re-describe only touched elements, and badge "stale since <commit>" (Code Wiki's "regenerates after each change" is the bar users now expect).

L8. **Budget the LLM pass and say the cost up front.** Tokens/time is complaint #2 (UA #76/#46/#212/#472, CodeBoarding #298). Cap input per element (signatures/outline, not bodies — omm #20's `.d.ts` idea; theuth `code_outline` is that), cap elements per run, run element descriptions in parallel with a small model and reserve the frontier model for perspective selection and top-level naming; show a progress card with element count and spend; make the first run optional per perspective (overall-architecture only, others on demand).

L9. **Offer the task-scoped map too.** Windsurf Codemaps' JIT map from a question is the most-praised shape in 2025–26 and is cheap because it is scoped; theuth's `code_symbol`/`code_refs` can seed a "map for this question" and the result can be saved as a perspective.

L10. **Every map is also agent context.** UA #76, Codemaps `@codemap`, DeepWiki MCP, Code Wiki + Gemini CLI: users value the map most when their agent reads it. Expose the element tree to `code_map()`/briefs (a perspective's description + anchors as the brief for a subagent) and let a board cite it.

L11. **List form first, picture second, text always.** Codemaps toggles outline↔drawn with the same clicks; the prior survey found mass products use trees. Render each element as list + diagram; on phone, list only.

L12. **Record provenance and expect disagreement.** CodeBoarding is non-deterministic; ICSA shows ~1 in 4 views unclear even with the best agent. Store `generated_by` (model, index commit, time), let the user edit/pin an element's description (Swimm-style coupling, omm's `note`/`concern` fields), and never overwrite a human edit on refresh.

## 5. Open questions

1. **How many perspectives on first index?** omm always writes overall-architecture plus whatever the model picks; cost evidence says start with one and offer the rest as buttons. Needs a decision on default vs on-demand.
2. **Where does LLM judgement add value over PageRank clustering?** Nobody has measured cluster naming vs purely structural grouping; a small A/B on theuth's own repo (does a reviewer recognise the clusters?) would settle the model budget.
3. **Verification depth**: parse-check only, or also assert every edge against the refs table (an edge with no supporting ref is dropped or dashed)? The latter is cheap for theuth and no competitor does it — potential differentiator against the DeepWiki-class accuracy complaints.
4. **Staleness policy**: regenerate on every index reconcile (Code Wiki) vs mark-stale-and-regenerate-on-open (cheaper). Users have not yet complained about either; cost argues for the second.
5. **Dynamic views** (sequence/request-lifecycle) need call-path evidence the static index gives only partially (no runtime); ICSA says these are the *most* reliable LLM views — decide whether to allow LLM-inferred sequence steps marked "inferred".
6. **Human edits**: which of omm's seven fields (description, context, constraint, concern, todo, note) survive regeneration, and who owns them (owner vs agent) in the knowledge base.
7. **Publication**: if maps are ever shared outside the harness, DeepWiki's backlash (unofficial docs outranking official) says they must carry generation provenance and an opt-out.
