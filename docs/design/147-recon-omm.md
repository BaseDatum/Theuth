**In one paragraph.** omm is a two-week-old TypeScript CLI + one-file viewer in which an AI coding agent, following a 181-line prompt, writes Mermaid
flowcharts and short prose into a `.omm/<perspective>/<element>/…` directory tree; the viewer re-parses those `.mmd` files with regexes, lays each
diagram out with dagre, draws every child diagram scaled down inside its parent node, and lets the reader semantic-zoom through one big SVG with a
sidebar of prose. The shape of the idea (perspectives → recursively drillable groups → leaves, name+path labels, why-labelled edges, typed prose
fields) is the valuable part; the mechanisms (LLM-only generation, slug ids, regex parsing, whole-map SVG, no grounding, no URL state) are not. Their
own self-scan is 62 elements / 6 diagrams / 68 nodes / 74 labelled edges, and 4 of 29 audited claims in it are wrong or stale.

**Interaction model in six lines (details A11).** Click a group *or* a leaf → it is selected, the right panel opens with its prose, the viewport
animates to fit it beside the panel (no page change, no breadcrumb). Zoom = ⌘/Ctrl+wheel or pinch; plain wheel/drag = pan; `fit` / ⌘0 = whole map;
⌘1/⌘2 = 100 %/200 %; Escape = close panel. Collapsed/expanded is not a state you toggle — a group's interior fades in when it is wider than ~50 % of
the viewport and fades out below ~27 %. The left tree mirrors the directory tree with fold toggles. No search, no URL state, no Back, no keyboard
traversal. Live reload = SSE on `.omm/` → full refetch and re-render, re-selecting the open element.

## A2. Vocabulary and unit

Terminology is fixed in `CLAUDE.md#L26-L31` VERIFIED: **element** = any architectural unit in `.omm/`; **perspective** = a top-level element;
**group** = element with children (rendered as an expandable box); **leaf** = element without children; "class" is the internal code name
(`listClasses`, `ClassData`) and must not appear in user-facing strings.

- **Identity = filesystem path.** An element IS a directory `.omm/<perspective>/<child>/<grandchild>`; the id of a node in a parent's `diagram.mmd`
  must equal the child directory name, kebab-case, English (`skills/omm-scan/SKILL.md#L14`, `#L32`, `#L150`) VERIFIED. The CLI addresses elements with
  `/`-joined paths (`src/cli.ts#L61`) and splits them into `{perspective, nodePath[]}` (`src/commands/read-write.ts#L18-L21`) VERIFIED.
- **Two id spaces in the viewer.** The viewer keys loaded data both by the scoped path (`data-flow/store`) and by the bare short name (`store`) — the
  comment says the short name is "ONLY for renderGroup ref lookup" (`src/server/viewer.html#L1444-L1447`) VERIFIED. Short names collide across
  perspectives (this `.omm/` has `store`, `validator`, `diff-engine`, `class-field` twice each): the last-loaded element wins the short-name slot. DOM
  selection uses the scoped id (`data-cls="…/…"`, `#L672`, `#L1065`).
- **Stable ids?** Only as stable as the directory name the LLM picks on each scan. No numeric id, no hash, no rename tracking; `meta.yaml` carries
  `title`, `kind: perspective|nested-class`, `children[]`, `parentPath[]` (`src/types.ts#L14-L28`) VERIFIED, and `children` is maintained by the store
  on every nested write (`src/lib/store.ts#L163-L178`) VERIFIED.
- **Legacy `@class-name` convention (v0.1).** PLAN designed flat classes linked by `@target` node ids (`PLAN.md#L201-L228`); the parser still
  recognises `@` ids and `@` label prefixes (`src/server/viewer.html#L368-L381`, `src/lib/refs.ts#L4`), and `omm refs` / the sidebar "References"
  section are built on it (`src/lib/refs.ts#L24-L59`, `src/server/viewer.html#L1100-L1107`) VERIFIED. Their own v2 `.omm/` contains zero `@` refs, so
  `refs` is dead data in practice (`omm refs overall-architecture` → "No element references …", run by me).
- **Mapping to theuth vocabulary.** perspective ≈ a *lens* over a *root*; element ≈ a *node* whose identity should be a *moniker* (file/symbol), not a
  free-text slug; group/leaf ≈ expandable row with children vs terminal row.

## A3. Generation pipeline

**Who produces the content: an LLM coding agent following a prompt file; the CLI only stores.** PLAN's core design decision: "the CLI manages `.omm/`
deterministically; the Claude Code skill does the AI analysis and then calls the CLI" `PLAN.md#L6` VERIFIED. There is no deterministic indexer, no
AST, no language awareness anywhere in `src/` (grep for parser/ast/tree-sitter: none; the only parsers are regex Mermaid parsers in `src/lib/diff.ts`
and `viewer.html`).

The generator is `skills/omm-scan/SKILL.md` (181 lines) VERIFIED, installed into the user's AI tool by `omm setup` (`src/lib/platforms/*`). Ordered
steps:

0. `omm config language` — prose fields are written in the configured language; ids stay English kebab-case (`skills/omm-scan/SKILL.md#L26-L32`).
1. **Explore**: Glob/Read manifests, top-level dirs, entry points, routes/services/DB/integrations (`skills/omm-scan/SKILL.md#L34-L41`).
2. **Select perspectives** from a 12-row catalog, "Don't force perspectives that don't exist in the code" (`skills/omm-scan/SKILL.md#L43-L64`; catalog
   reproduced in A4).
3. **Per perspective, recursive drill-down** (`skills/omm-scan/SKILL.md#L66-L116`):
   3a. write the perspective `diagram` via `omm write <p> diagram - <<'MERMAID' … MERMAID` (one Bash call per field, `skills/omm-scan/SKILL.md#L179`);
   3b. write the other six fields;
3c. **for every node in the diagram**: analyse the code it represents, *write `description` for every node — no exceptions* (this creates the element
directory), then decide leaf vs group: "distinct internal components found → write a diagram and recurse deeper; no meaningful sub-components (single
file, trivial wrapper, external system) → leaf" (`skills/omm-scan/SKILL.md#L103-L105`). If group, write its diagram and repeat 3c for its nodes.
4. **Summarise** and suggest `omm view` (`skills/omm-scan/SKILL.md#L144-L146`).

- **Termination rule**: purely judgemental — recursion stops when the agent decides a node has no internal structure; the only numeric hint is "More
  elements in one diagram means you should recurse deeper" (`skills/omm-scan/SKILL.md#L159`) and the validator's soft 5–15 node band
  (`src/lib/validate.ts#L153-L168`). No depth cap in the skill; the viewer renders to `maxDepth = 6` (`src/server/viewer.html#L781`).
- **Rules the prompt imposes**: ids = child dir names; two-line labels `Name\npath`; every edge labelled; `graph LR` default, `graph TD` for
  hierarchies; four approved `classDef`s with fixed hex colours; no circular references, a child never references its parent; do not rewrite unchanged
  elements (`skills/omm-scan/SKILL.md#L148-L181`) VERIFIED.
- **Tool calls used**: only the host agent's Glob/Read/Bash; the CLI side is `omm write` (stdin heredoc) → `writeField`/`writeNodeField`
  (`src/commands/read-write.ts#L44-L79`, `src/lib/store.ts#L126-L183`). Write side-effects: `prev_diagram` saved to `meta.yaml` on diagram overwrite,
  `meta.updated/update_count/last_field` bumped, parent's `children[]` updated, git commit/branch recorded (`src/lib/meta.ts#L9-L45`) VERIFIED.
- **Update mode**: skill says "Do not rewrite elements that haven't changed" but gives no mechanism; PLAN v0.1 imagined `git diff`-driven selective
  refresh (`PLAN.md#L147`) and a focused mode `/omm-scan <topic>` (`PLAN.md#L159-L170`) — **neither is in the v0.2 skill** (planned, not built).
  Incremental analysis is a ROADMAP item.
- **What their own scan actually did** (evidence of the recursion in practice): 62 elements, only 6 with a diagram; every one of the 56 leaves has
  only `description` (see T3 stats). The recursion went 3 deep once (`overall-architecture/{commands,platforms,server}/*`), and `command-surface`'s 19
  children and `data-flow`'s 11 children are all leaves.

## A5. Hierarchy and drill-down

- **Nesting rule**: filesystem containment. A node `x` in `P/diagram.mmd` is a group iff `.omm/P/x/` exists and contains a `diagram.mmd`; the viewer
  resolves `refCls = currentChildren.includes(n.id) && classesData[n.id]?.diagram ? n.id : null` (`src/server/viewer.html#L482-L487`) VERIFIED. An
  element directory with only `description.md` is a leaf that still gets a sidebar.
- **Depth**: unbounded in the store; viewer stops at `maxDepth = 6` (`src/server/viewer.html#L781`); their own data reaches depth 3 (`omm tree
  overall-architecture`, run by me).
- **Leaf vs group decision**: LLM judgement (A3). Practical outcome in their scan: 6 groups / 56 leaves.
- **Node caps**: soft only — validator warns `<3` or `>15` nodes (`src/lib/validate.ts#L156-L167`); skill says 5–15 implicitly. Their
  `command-surface` has 20 nodes and passed (because the validator's node counter is wrong — T3).
- **How nested things are shown (the central mechanism).** Everything is ONE SVG. `buildCanvas` lays the perspectives out in a `ceil(sqrt(N))`-column
  grid (`src/server/viewer.html#L1187-L1209`); `renderGroup` is recursive: for a node that is a group, it renders the child's diagram first (dagre),
  then **scales the child's whole SVG down to fit a 320×220 box** (`fitScale = min((MAX_W-2PAD)/W, (MAX_H-2PAD)/H, 1)`) and uses that box as the
  node's size in the parent's dagre layout (`src/server/viewer.html#L487-L497`, `#L644-L657`) VERIFIED. So a group is literally its child diagram
  drawn small inside the parent — no icon, no "+N" badge.
- **Progressive reveal by on-screen size** (`applyTransform`, `src/server/viewer.html#L822-L840`): a group whose border is narrower than 27.5 % of the
  viewport gets `grp-collapsed` (inner content at 15 % opacity, one centred title, `#L120-L122`); a group wider than 50 % + 15 %·depth of the viewport
  gets `grp-expanded` (title moves to top-left, centre title hidden, `#L145-L149`). Below 42 % zoom the whole canvas enters `zoom-overview` (leaf
  nodes 20 % opacity, edges 40 %, edge labels hidden, sub-group centre labels drawn from an overlay layer, `#L128-L134`, `#L820`). A focused group and
  its ancestors are `focus-exempt` from all of that (`#L151-L161`, `#L886-L899`).
- **Hidden things**: nothing is hidden by data — collapsed groups fade, they do not disappear; there is no "show N more". A child class is expanded
  only once per render (`_expandedGlobal`, `src/server/viewer.html#L458-L459`, `#L487-L488`) so a child that appears under two parents is drawn as a
  plain node the second time.
- **Fan-out compaction**: a node with more than 3 leaf-only targets gets them laid out as a 3-column grid under a virtual node
  (`src/server/viewer.html#L510-L533`, `#L573-L587`); edges to grid children are drawn straight from the parent (`#L604-L609`) — in their
  `command-surface` this gives 19 near-parallel lines from `omm` (visible in `omm-shots/01-overview.png`).
- **Aspect-ratio re-layout**: if the dagre result is wider than 2.0× (1.6× above 7 nodes, 1.4× above 12) its height and the direction is not TB, the
  diagram is re-laid as TB (`src/server/viewer.html#L566-L571`) — the author's own `graph LR` can be overridden silently.

## A6. Diagram language

**Written subset (what the skill asks for and what their `.omm/` contains)** — all VERIFIED by reading the six `.omm/**/diagram.mmd`:
- `graph LR` (5 of 6) and `graph TD` (1: `command-surface`); no `flowchart` keyword, no `subgraph`, no `direction`, no `%%` comments, no `click`, no
  `style`/`linkStyle`.
- Node declaration `id["Name\npath"]` — two-line quoted label with a literal `\n` (`skills/omm-scan/SKILL.md#L151-L156`); every node in their data
  uses it. The second line is a file path or a one-line hint (`omm view [--port N]`, `Claude Code / Codex / Cursor`).
- Edge `A -->|"label"| B`; 74/74 edges in their data carry a label (my count). Inline declaration of the target on the edge line (`… -->
  store["Store"]`) occurs in `overall-architecture/server/diagram.mmd` and `…/commands/diagram.mmd`.
- `classDef external|concern|entry|store fill:… stroke:… color:…` with four fixed Catppuccin-ish hexes and `class a,b,c name` assignments
  (`skills/omm-scan/SKILL.md#L161-L175`, `src/lib/validate.ts#L7-L14`). Their data uses external/entry/store; `concern` never.
- Shapes: only `[ ]` rectangles in their data; the viewer also parses `(( ))` stadium, `( )` round, `{ }` diamond
  (`src/server/viewer.html#L376-L381`).

**Parsers (there are two, both regex, neither Mermaid).**
1. `src/lib/diff.ts#L12-L58` `parseMermaid` — line-based; skips directive lines; a strict edge regex then a "broad" fallback
   `^([^\s[\]({]+).*?(-->|…).*?([^\s[\]({]+)` (`#L38`); used by `omm diff` and by the validator's node count. It mis-tokenises quoted labels
   containing spaces/`|` — see T3 (counts 23 nodes where there are 11).
2. `src/server/viewer.html#L362-L420` `parseFlowchart` — tokeniser `tok()` for the four shapes with optional `@` prefix; `-- "label" -->` form first
   (`#L386`, `#L394-L404`), then split on arrow regex `-->(?:\|[^|]*\|)?|--o|--x|---|-.->|==>|~~>` (`#L387`, `#L405-L413`); `class a,b c` assignments
   are kept (`#L392-L393`), `classDef`/`style`/`subgraph`/`click` lines are dropped (`#L391`) — so **the approved classDef colours are never
   rendered**; `nodeStyle` only knows `external` and `lib` and gives them the same grey as everything else in dark mode (`#L423-L434`). Edge label
   `<br>` → space, label `\n` → newline (`#L367`, `#L401`).

**Validator** `src/lib/validate.ts#L58-L174` VERIFIED — rules: `graph-declaration` (error; first content line must match
`^(graph|flowchart)\s+(LR|RL|TD|TB|BT)$`), `balanced-brackets` (error, quote-aware per line), `edge-label` (warning for `-->`/`==>`/`-.->` lines
without `|…|`), `classdef-name`/`classdef-color` (warnings against the palette), `ref-self`/`ref-exists` (errors, `@` refs only), `node-count`
(warning outside 3–15). It validates only top-level perspectives (`src/commands/validate.ts#L32-L49` iterates `listClasses()`), so the three nested
diagrams are never validated.

**Not written, not parsed**: `subgraph` (both parsers skip it; nesting is done by directories instead), sequence/class/ER/state diagrams, `click`
callbacks, `linkStyle`, markdown strings, icons. The diagram vocabulary is therefore "boxes with two-line labels, labelled arrows, four colour
classes".


### A6 addendum — why the sibling spike's `.omm` showed an empty frame (parent's question)

Tested on a copy of `…/codemap-omm/spike/.omm` served with `node dist/cli.js view --port 3931` and inspected with `browser_eval`:
- **The parser does not fail on any construct in `spike/.omm/overall-architecture/diagram.mmd`.** After `init()` the DOM held every node and edge: 5
  `.grp-node`, 30 `.reg-node`, 49 `.edge-path` (= 11+5+9+3+5 nodes minus the 3 nodes that are groups; 16+6+16+3+8 edges), the root `<svg>` was
  1233.6×1113.9, `overall-architecture`'s border 667.6×993.9, every node had a position. `classDef` lines are dropped (`src/server/viewer.html#L391`),
  `class a,b c` lines are kept (`#L392-L393`), `→`, `::`, `(…)`, `{…}` and `\n` inside a quoted label are all swallowed by `tok()`'s `\["([^"]+)"\]`
  (`#L376`) and by the edge split `-->(?:\|[^|]*\|)?` (`#L387`, `#L405-L413`); kebab ids match `[\w-]+`. There is only one `-->` per line in that
  file.
- **What actually failed is the theuth headless browser's SVG rasteriser, not omm.** The spike has a group nested at depth 3
  (`overall-architecture/content-stores/codeindex/diagram.mmd`), i.e. `<g clip-path><g class="grp-inner" transform="translate() scale()"><g
  clip-path><g transform="translate() scale()">…`. With that one file moved aside (copy only), the same page rendered completely (`omm-shots`-style
  screenshot taken, all 11 top-level nodes + 2 sub-groups visible); with it present, the raster stops after the first few elements and the frame is
  drawn ~140×130 px although the DOM says 667×993. Removing `clip-path` attributes did not help; replacing `→` with `->` did not help; reducing the
  depth-3 diagram to node declarations only did not help — so it is the nesting depth, not the text. The same renderer also returns
  `getBoundingClientRect() = 0` for SVG `<g>`/`<rect>`, lacks `:scope` and `getBBox()`, and ignores CSS `display:none` on SVG text — all of which I
  had to work around for the screenshots in A11. In Chrome/Safari omm's own README screenshot shows depth-3 nesting rendering fine.
- **Silent failure in omm exists but did not trigger here**: `dagre.layout` is wrapped in `try { … } catch { return null; }`
  (`src/server/viewer.html#L561`); a null group is dropped (`#L1182-L1185`) and if every root drops, `buildCanvas` returns null and `init()` leaves
  the canvas as it was (`#L1513-L1517`) — no message, no console line. `renderFlatSVG` has the same pattern (`#L706`, `#L722`). A diagram whose first
  content line is not `graph|flowchart` still parses (the viewer never checks it; `rankdir` just stays LR, `#L389-L390`).

## A7. Per-element prose

- **Fields**: exactly seven — `description`, `diagram`, `constraint`, `concern`, `context`, `todo`, `note` → files `description.md`, `diagram.mmd`,
  `constraint.md`, … (`src/types.ts#L1-L12`) VERIFIED. PLAN's rationale: splitting `note.md` into constraint (rules) / concern (risks) / context (why)
  / todo / note improves the AI's analysis quality (`PLAN.md#L11-L12`).
- **Semantics as the skill defines them**: description = what the element does and which files/dirs it covers (`skills/omm-scan/SKILL.md#L98-L100`);
  the rest "if relevant". `description` is mandatory for every node (`#L95`).
- **Length in practice** (their `.omm/`, measured by me): 62 descriptions, 14,650 bytes total → mean ≈ 236 bytes (≈ 2–3 sentences), min 63
  (`command-surface/logout`), max 554 (`overall-architecture`); one `constraint.md` (5 bullets) and one `context.md` (1 paragraph), both on the root
  perspective; zero concern/todo/note anywhere. So the "7 fields" promise collapses to "one paragraph per node" after the first level.
- **Language**: `omm config language <code>` sets a free-form value stored in `.omm/config.yaml`; default "English" (`src/commands/config.ts#L41-L52`)
  VERIFIED. Prose is translated by the LLM at write time; ids stay English.
- **Display**: the right sidebar renders, in this fixed order, Meta (updated · N updates · branch · commit), Description, Constraints, Concerns (with
  a left rule), Context, Todo, Notes, References; markdown via marked.js; empty fields are omitted (`src/server/viewer.html#L1083-L1110`) VERIFIED.
  The sidebar's `sb-diagram` slot and `renderFlatSVG` (`src/server/viewer.html#L704-L765`) exist but are never filled (`sbDiagram.innerHTML = ''` at
  `#L1086` and nothing writes to it) — dead code from v0.1.
- **CLI display**: `omm show <path>` prints `--- field: name ---` blocks plus `meta` YAML (`src/commands/show.ts#L12-L20`); `omm read <path> <field>`
  prints raw content for piping (`src/commands/read-write.ts#L23-L42`).

## A8. Grounding

- **Links to code**: none that software can follow. The only grounding is the second label line (`Name\nsrc/lib/store.ts`) and free-text file mentions
  inside descriptions. The viewer renders the path line at 9 px / 45 % opacity under the name (`src/server/viewer.html#L688-L689`) and does nothing
  with it — no click, no copy, no existence check. No line anchors, no symbol names, no `click` handlers.
- **Verification of diagram claims against code**: none. `omm validate` checks Mermaid shape and conventions only (A6). Nothing compares the node's
  path to the filesystem, nothing checks that an edge corresponds to an import/call. Consequence measured in T3: 4 of 27 audited claims are wrong or
  stale after two weeks of commits, and nothing in the tool could tell.
- **Cross-references between elements**: the `@class-name` convention (A2) plus `omm refs [--reverse] <class>` (`src/lib/refs.ts#L24-L59`,
  `src/commands/refs.ts#L4-L35`) and the sidebar "References" list (`src/server/viewer.html#L1100-L1107`). Only top-level perspectives are scanned for
  refs (`listClasses()` in `getIncomingRefs`), and their v2 data uses none. The skill forbids a child referencing its parent
  (`skills/omm-scan/SKILL.md#L181`); nothing enforces it except `ref-self` for the `@` form.
- **Same thing in two perspectives** is two unrelated elements (A4) — no identity join.
- **Git grounding**: `meta.yaml` stores `git_commit`/`git_branch` at the time of each write (`src/lib/meta.ts#L9-L19`, `#L41-L43`) — a "scanned at
  commit X" stamp per element, shown in the sidebar Meta line. That is the only freshness signal (A10).

- **Staleness detection**: none automatic. The only signals are `meta.updated` and `meta.git_commit` per element (`src/lib/meta.ts#L41-L43`), surfaced

- **Incremental regeneration**: not built; ROADMAP item "Incremental analysis — detect changed files since last scan and update only affected
  perspectives" (`docs/ROADMAP.md#L8-L9`). The skill's only lever is the sentence "Do not rewrite elements that haven't changed"

- **Diff between versions**: `omm diff <class>` = set difference of node ids and `src arrow dst` strings between `meta.prev_diagram` and the current
  diagram (`src/lib/diff.ts#L60-L76`, `src/commands/diff.ts#L4-L27`) VERIFIED; output "Added/Removed nodes/edges". Top-level only

- **Watch / live reload**: `fs.watch(.omm, {recursive:true})` → 300 ms debounce → SSE `event: change` with `{file, time}` to every `/events` client

    `data: connected` and the page kept the old text. A bare `fs.watch(…, {recursive:true})` probe in the same directory failed with `EMFILE: too many
    open files, watch`, also with `ulimit -n 65536` — this shared Mac (load ≈ 40, many running sessions) has exhausted its file-watch descriptors. So:
    SSE wiring VERIFIED from code and the `connected` frame; the change round-trip is UNVERIFIED live; and omm's silent error handling means a user in
    this state sees nothing at all.

## A11. Viewer

**Stack**: one file, `src/server/viewer.html` (1,562 lines), vanilla JS module; `dagre@0.8.5` and `marked` from jsDelivr CDN, Google Fonts
(`src/server/viewer.html#L7-L9`) VERIFIED — so the viewer needs internet even though the server is local. Served by a dependency-free `node:http`
server that injects `window.__projectName` (`src/server/index.ts#L47-L54`) and auto-increments the port on `EADDRINUSE` (`#L60-L68`).

**Layout engine**: dagre per diagram, `nodesep 32 / ranksep 44` (20/28 when >10 nodes), rankdir from the `.mmd`, TB fallback for over-wide results
(`src/server/viewer.html#L536-L571`); node boxes sized by canvas-measured text width, 80–220 px wide (160 max when >10 nodes), 38 px high (+14 for a
path line) (`#L499-L507`); groups scaled into 320×220 (A5). **Renderer**: hand-built SVG strings (`<rect>`, `<polygon>`, `<text>`, quadratic-bezier
`<path>` through dagre waypoints, `src/server/viewer.html#L436-L455`, `#L597-L627`), inserted with `innerHTML`; the whole map is one `<svg>` inside a
CSS-transformed `<div>` (`src/server/viewer.html#L788-L789`).

**Navigation model (precise)** — all VERIFIED by reading and by driving it:
- *Click on a group or a leaf does the same thing*: `window.__openSb(scopedId)` → mark `.selected`, highlight the nav row, open the right sidebar with
  that element's fields, then `focusGroup()` animates the viewport (380 ms ease-out) so the element fills ~85 % of the space left of the sidebar
  (`src/server/viewer.html#L1054-L1081`, `#L886-L929`). There is no separate "drill-in page": drilling is semantic zoom into the one big SVG; a
  group's children are already drawn inside it. Clicking a leaf zooms to the leaf box itself.
- *Nav tree* (left, 200 px): perspectives as roots with ▾/▸ fold toggles; children and grandchildren indented with box-drawing connectors; built from
  `meta.children` (`src/server/viewer.html#L1299-L1376`). Clicking a row = `__openSb`. Mirrors the filesystem, not the diagram.
- *Zoom*: wheel with ⌘/Ctrl (pinch → `0.993^deltaY`, mouse wheel → ×1.22 steps) around the cursor; plain wheel/two-finger = pan; `−`/`+` buttons
  ×1.25; `fit` = `centerView` (scale ≤ 0.9 to fit the whole map); limits 2 %–3000 % (`src/server/viewer.html#L786`, `#L844-L866`, `#L934-L955`). Pan:
  drag on empty canvas, middle button, or Space+drag (`#L987-L1011`). Touch: one-finger pan, two-finger pinch (`#L1013-L1046`).
- *Keyboard*: ⌘/Ctrl+0 fit, ⌘1 100 %, ⌘2 200 %, ⌘± zoom, Space pan, Escape closes the sidebar (`src/server/viewer.html#L967-L985`). No arrow-key
  traversal, no focus ring, no `/` search.
- *Breadcrumbs / back / URL state*: **none**. `location.hash` is never read or written; the sidebar title is the only path indicator (`fmtLabel(cls)`
  → "Overall Architecture/server", `src/server/viewer.html#L1085`). Browser Back leaves the app. Reload resets to the fit view.
- *Hover*: edge highlight on node hover is coded (`src/server/viewer.html#L1255-L1272`) but **broken for every v2 node**: it compares the node's
  scoped id (`data-cls="data-flow/store"`) with the edge's bare ids (`data-from="store"`), so nothing matches (I dispatched `mouseover` on
  `data-flow/store`: 0 `.edge-hl`). Node/group hover gets a white glow via CSS (`src/server/viewer.html#L109`, `#L113`).
- *Detail panel*: right sidebar 400 px, slides in; Meta, Description, Constraints, Concerns, Context, Todo, Notes, References (A7). Click on empty
  canvas or × or Escape closes it and clears selection/focus (`src/server/viewer.html#L1049-L1051`, `#L1112-L1118`).
- *Search*: none (ROADMAP "AI-powered search in viewer").
- *Empty state*: "No perspectives found. Run /omm-scan in Claude Code." centred (`src/server/viewer.html#L1481-L1484`). *Error state*: none — fetch
  errors become `{}` (`#L783`), layout errors drop the group silently (A6 addendum).
- *Theme*: dark default, light toggle persisted in `localStorage` (`src/server/viewer.html#L314-L337`); rebuild on toggle.
- *Live reload*: SSE → full `init()` → re-select (A10).
- *Mobile* (≤ 768 px): nav becomes an off-canvas drawer behind a ☰ button, the detail panel becomes a bottom sheet (50–70 vh) with a drag handle and
  swipe-down-to-close; float controls hidden (`src/server/viewer.html#L237-L282`, `#L1120-L1150`).

## A13. Scale and performance

- **Repo sizes handled**: unknown — no benchmarks, no large example. Their own repo is ~2,900 lines of TS + one 1,562-line HTML; the resulting map is
  62 elements / 6 diagrams / 68 nodes / 74 edges.
- **Nodes per view**: whole map in one SVG; their largest single diagram is 20 nodes. Validator's comfort band 5–15. Nothing is virtualised;
  `rebuildCanvas` re-renders everything (`src/server/viewer.html#L1284-L1296`) and live reload refetches every element (`#L1478-L1504`: 3 requests per
  perspective + 1 per nested element, all in parallel).
- **Layout/render time**: dagre on ≤ 20-node graphs is milliseconds; no measurement in the code. The map rendered within ~1 s in my headless run
  (first screenshot blank until `requestAnimationFrame(centerView)` ran).
- **Generation time**: their self-scan's `meta.yaml` timestamps run 12:24:32 → 12:31:00 on 2026-03-25 (≈ 6.5 min wall for 62 elements, including two
  scan passes `update_count` 2–4) — read from `.omm/*/meta.yaml` created/updated fields. Each element is at least one Bash tool call
  (`skills/omm-scan/SKILL.md#L179`), so 62 elements ≈ 70+ tool calls.
- **Scaling hazards in the design**: one SVG for everything (DOM grows with total elements, not visible ones); the fan-out grid handles > 3 leaves but
  edges to grid children are straight lines from the parent (`src/server/viewer.html#L604-L609`), already ugly at 19; the short-name `classesData` map
  (A2) collides as soon as two perspectives name a child the same.

## A14. Cost

- **Who pays**: the user's AI-tool subscription/API key — omm itself makes no model calls; everything runs inside the host agent

- **Budget controls**: none (no depth cap, no element cap, no token budget, no timer).
- **Wall time**: ≈ 6.5 min for their own small repo (A13), single-threaded.
