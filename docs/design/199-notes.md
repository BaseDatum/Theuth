### Deviations from the design (and the brief)
1. **Type names follow the design, not the brief's list.** The brief named `FileState, FileDirection, IntakeState`; the design (rounds 3–5) has `InState`, `OutState`, `FileDirection`, `NoticeState`, and `FileState` = "`InState` or `OutState`, tagged by `direction`". `IntakeState` went with the held intake (round 3). The brief's `contact_files` RPC is the design's `contact_file`.
2. **`ContactFile.direction` and `.state` are one flattened field** `state: FileState` (`#[serde(flatten)]`, adjacently tagged): the wire still carries `"direction": "in", "state": "saved"`, and an `out` state under `in` cannot be expressed. `FileState::direction()` reads the tag.
3. **Sizes in error texts are exact bytes**: `files: <path> is 5000000001 bytes (over the 5 GB limit per file)`, `read_file: <path> is 300000000 bytes; too large to read whole (limit 256 MB). …` (the design leaves `<size>` unformatted).
4. **Gate refusals**: a socket does not open (`ENXIO` on Linux, `EOPNOTSUPP` on macOS); a failed open on an existing non-regular file reports `not a regular file`. `Refusal::Changed` (`files: <path> changed since it was offered`) is the reopen's mismatch; the route turns it into `410 changed`.
5. **`FileMeta` ignores unknown keys** (a later v1 field does not refuse a message); the receipt body is strict (anything else is a 400, as the design says).
6. **`ContactFileChanged` is an `AgentEvent` variant** as the design says, so the exhaustive matches in `crates/slack/src/channel.rs` and `crates/tui/src/model/agents.rs` gained an arm (slack ignores it; the TUI arm is `199-UIT`).
7. **The quarantine timestamp is 8 hex digits** (`{:08x}`), as Safari and curl write it.
8. **`notice_id`** is `Uuid::new_v5(NAMESPACE_OID, "theuth/contact-file/<holder>/<id>")`.
9. **`Store::notice_committed`** is frozen here (round 5's shared predicate), with a test; nothing calls it yet.
10. **ProtoJSON makes `size` a double.** Part metadata is a `google.protobuf.Struct`, so a `FileMeta.size` of `2516582` comes back from `a2a_pb::protojson_conv` as `2516582.0` (found by the round-trip test). `FileMeta.size` therefore deserialises a `u64` or a non-negative whole double up to 2^53 (exact; `FILE_MAX` is far below); a fraction or a negative is refused. Senders still write an integer.
11. **The receipt parser is a flat struct** with `deny_unknown_fields`, not the tagged enum: serde's internally tagged enums let unknown keys through on unit variants (`{"state":"received","x":1}` parsed). `Receipt` itself only serialises.

## 199-UIT as built

Branch `feat/199-uit` from the contract fold `c5d0895af`. TUI only (`crates/tui`); no wire, type or RPC change.

### What landed
- **`components/files.rs` (new, UIT-owned):** `Line` parses one engine-written `<message_file …/>` element (`state` `receiving|received|failed`; `holder` and `file` must be hex) or takes a typed `ContactFile`. Every line is a keyed plain card, `entry_key = file:<holder>:<id>`, CardKind key `notice_id(holder, id)`: `▤ name · size · type · state` (`✕` and red when failed), and on Ctrl+O the sender, saved path, machine, holder and id. Values lose control characters (line breaks included) and bidi controls (U+061C, U+200E/F, U+202A–E, U+2066–9). Sizes are decimal, as the mock writes them (`12 KB`, `24.1 MB`, `1.2 GB`). States: in `queued`, `receiving N%`, `saving`, `saved`, `failed · <reason>`; out `offered`, `sending N% · <bytes>`, `sent`, `failed · <reason>`. An ended share appends ` · not given to the agent`; an element that does not parse is the error line `File notice (unreadable)`.
- **Rows** (single routing points, so every caller gets them):
  - `model/transcript.rs` `injected`: a `<message>` wrapper's placeholder tail (the elements and the receiving hint) belongs to it. The live `TurnStarted` echo of a message row with files therefore stays hidden, and `contact_row`'s inbox path and the peer wrapper read the words only.
  - `model/history.rs` `from_history`: a stored user row's placeholders follow its card as lines (`files::placeholders`). `user_entries`: a notice row (element plus the `File notice from theuth` hint) is its line, never a `you` row; a human typing the tag without the hint keeps a `you` row. The `HistoryEntry::Error` arm renders an ended-share row.
  - `model/agents.rs`: the live `AgentEvent::Error` arm renders it the same way; the **`ContactFileChanged` arm** (`files::changed`) sets every line of that file to the new state and glyph (receiving progress, terminal state). An outgoing file's first event inserts its line under the `send_message` tool entry whose receipt line names `id=<exchange>`, after that call's earlier lines: the four send states on the sender's tool entry.
  - `components/peers.rs` `PeerDelivered`: `event.files` follow the live peer card as lines.
  - `ui.rs` `queued_text`: a queued notice shows as its line.
- **Actions** (`Files` component): `/files` opens a picker of this chat's file lines (newest line per file); `⏎` open (`platform::open::open_path`), `r` reveal (opens the folder), `y` copy path (`arboard`), `s` save to `~/Downloads/<name>` (`contact_file_export`, no-clobber on the holder), `f` fetch here (`contact_file_fetch`, then open). `o` on an empty composer opens the newest file line of the exchange. Each action reads the file from its holder (`contact_file(holder, id)`); open, reveal and save refuse with `<name> is stored on <machine> · f fetches it here` when `mesh_status().self_id` is not the holder. No phone-style limits.
- **D15 attach** on the `/peers` answer prompt: opening the prompt reads where the chat lives (`list_sessions` `here`/`owner`, the machine named from `mesh_status` peers, else its short id). A submitted `+<absolute path>` attaches a file only when the chat is owned here; elsewhere it answers `attach on <machine>`, a relative path `files: <path> is not an absolute path`, and the hint shows `+<path> attaches (N attached)` or `attach on <machine>`.

### Deviations
1. **Placement beyond `contact_row`.** `contact_row` only sees rows with typed peer provenance; placeholders also reach the live `TurnStarted` echo and history fallbacks, and notice rows are automatic input with no peer origin. The parse sits once in `injected`/`from_history`/`user_entries` (one line each) and in the new module; `contact_row` itself is unchanged except its comment.
2. **File lines are their own keyed cards**, not text inside the peer card body: a `WrapperView::Card` carries no entry key, and keyed cards give live updates and actions for free.
3. **D15 send against the decided signature** (see the next heading): the answer carries the attachments as the 4th positional parameter of `answer_peer_request`.
4. **Outgoing lines after a reload**: history keeps no `structured.files`, so a reloaded sender shows the tool's own text until the next `ContactFileChanged` for that file adds its line.
5. **The non-TTY line printer** (`lib.rs`) still prints rows as text (as it does for every wrapper).
6. **fmt**: house compact style, matching the sibling components; no whole-file `cargo fmt` (none of the TUI component files is rustfmt-clean on main).

### Contract changes after C (199-UIT)
- **`answer_peer_request(session, reply_to, text, files)`**, decided by the orchestrator on 2026-11-17: `files` is an optional 4th positional parameter (Rust `Option<Vec<PathBuf>>`, serde default, wire `string[]`), sent only when non-empty. E1b implements it and regenerates the bindings; the RPC trait is unchanged here. Until then, the TUI builds that one call in its own request plumbing (`components/peers.rs`, `Request::AnswerPeerRequest`): with no attachments it calls the typed client exactly as today; with attachments it calls `ClientT::request("answer_peer_request", rpc_params![session, reply_to, text, files])`. Not run against an engine: one without E1b should refuse the extra parameter with its own params error, not drop the files silently. Once E1b lands, the second arm can become the typed call.
