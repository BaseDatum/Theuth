## The bug (Sky, 2026-10-06 18:37, iPad)

"Whenever I open a task, I literally have no way to get back to the task board, so I have to use the tabs at the top to open Agents and then open Tasks again. But then all of the filters that I selected are gone. So overall, this task screen just needs a lot better state management and awareness of what the user is trying to do. Like if I open a task card, I should be able to go immediately back to the task board in the state that I left it in."

Cause, three mechanisms. (1) No way back: `TaskDetail.tsx:48/58/65` wrap the page in `Frame` (`backTo="/tasks"`), and `Frame` renders the back chevron `md:hidden` in both shells (`DocumentPage.tsx:48` popout header, `:60` `SectionRow back`) because Notes/Knowledge have their list pane beside the document from `md` up; `/tasks/$id` has no list pane, so on an iPad (820 px ≥ 768) and on desktop the button was simply not rendered — `AgentDetail` and `RoutineDetail` show theirs at every width. (2) Filters lost: the board keeps its filters only in the URL (`Board.tsx:121` `set()` → `navigate({ search, replace: true })`) and falls back to the first known project without `?project=` (`Board.tsx:114`); every route back into it was a bare `/tasks` — the band's Tasks tab (`SectionBand.tsx:35` `navigate({ to })` with `lib/nav.ts:13`), the Frame back link (`DocumentPage.tsx:49` `<Link to={backTo}>`) and the navigate after cancelling a task (`TaskDetail.tsx:462`). (3) Position lost: the board is a horizontal scroller (`Board.tsx:207`) that mounts fresh at `scrollLeft 0`, so three columns fit on an iPad and coming back always lands on Backlog.

## What changed

1. **A – the task page has its back at every width, in both shells.** `Frame` gets `backAlways?: boolean` (default false: Notes/Knowledge unchanged); when set, the `md:hidden` is dropped from the popout header button and from `SectionRow.back.className` (`backClass = backAlways ? undefined : 'md:hidden'`). `TaskDetail` passes it on all three `Frame`s (pending, error, loaded); label stays `Back to tasks`; the chevron is the same focusable `Link`.
2. **B – the device remembers the filters; every bare entry restores them.** New pure module `tasks/boardMemory.ts`: `BoardSearch` and `parseBoardSearch()` (the one set of rules — moved out of the route, which now has `validateSearch: parseBoardSearch`), `BOARD_KEY = 'theuth_tasks_board'`, `rememberBoard(search, storage = localStorage)` (JSON, try/catch, `{}` written too), `recallBoard()` (re-validated through `parseBoardSearch`, `{}` for anything missing/invalid; guarded for node), and `boardEntryRedirect(cause, search, remembered)` → `remembered` only for `cause === 'enter'` with an empty search and something remembered, else `null`. `routes/tasks.index.tsx` gains `beforeLoad: ({ cause, search }) => … throw redirect({ to: '/tasks', search: to, replace: true })`. `Board` does `useEffect(() => rememberBoard(search), [search])` on the RAW url search, so a never-picked project stays "first project" and clearing everything is remembered as `{}`. router-core 1.170 (`router.js:664-720`) sets `cause` from the committed match at the same index: `/tasks/$id → /tasks/` is `enter`, a filter change on the board is `stay` (clearing the last filter never snaps back), hover preloads are `preload`; the redirect's own navigation is `enter` with a non-empty search, so it cannot loop. Explicit entries (`AgentDetail` `agent`, Hud `state: 'doing'`) carry their own search and are untouched; `project: ''` = All projects and the Radix `any`/`all` sentinels are as they were.
3. **C – coming back, the board shows where the user was.** Module memory in `boardMemory.ts` (per window, never persisted): `rememberBoardScroll/recallBoardScroll` and `rememberOpenedTask/takeOpenedTask` (returns and clears). `TaskDetail` runs `useEffect(() => rememberOpenedTask(id), [id])`; the board's scroller has `onScroll={(e) => rememberBoardScroll(e.currentTarget.scrollLeft)}` (no state); a `useLayoutEffect` on the first render with `tasks.data` (once per mount, `placed` ref) takes the opened task and, if its card `li[data-task-id]` is on the board, `scrollIntoView({ block: 'nearest', inline: 'nearest' })` + `returned` state, else `scroller.scrollLeft = recallBoardScroll()`. `TaskCard` gets `data-task-id` on the `<li>` and `returned?: boolean`: the inner `Link` always carries `transition-shadow duration-700` and adds `ring-2 ring-primary/60` while returned, so dropping the prop fades the ring out; the 1.5 s timer lives in an effect keyed on `returned` (a timer set inside the layout effect was cleared by StrictMode's dev-only effect replay and the ring stuck — seen in the first headless run). `AgentDetail.tsx::TasksTab` renders `TaskCard` without the prop, unchanged.
4. **Tests** `boardMemory.test.ts` (node, pure): `parseBoardSearch` keeps/drops, `rememberBoard`/`recallBoard` over a Map-backed store incl. `{}`, invalid JSON, arrays/`null`, a throwing store and a `null` store, the `boardEntryRedirect` matrix (enter+empty+remembered → remembered; enter+empty+`{}` → null; enter+explicit → null; stay → null; preload → null), `takeOpenedTask` returns then clears.

## Rejected

- `history.back()` for the chevron: the previous entry is often not the board (Attention, a chat, the Queue, a deep link); B + C make a forward `/tasks` land where the user was.
- Carrying the filters on the detail URL (`retainSearchParams` / `?from=`): survives the back link only — the Agents → Tasks tab path Sky actually used would still arrive bare, and every link to a task would have to know the board's state.
- A `tasks.tsx` layout route owning the search: changes every task URL and still loses the tab path.
- Persisting scroll / last card to storage: ephemeral by nature — a reload or a new window starts at the left like any fresh visit; per-window module memory is enough.
- Keeping the ring until the next interaction: a return should be noticed, not nagged; 1.5 s plus a 700 ms fade.
