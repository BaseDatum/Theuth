### 0.1 The ten facts the design most depends on
1. **A chat fence reaches renderers as `{code, isIncomplete}` (+`language`) only — no meta.** The engine, in contrast, keeps the *whole* info string as `lang` and compares it by equality. Options therefore cannot ride on the info string in chat without a streamdown override; they can in notes (the BlockNote `language` prop holds the whole string). (§1.2, §3.1)
2. **`FenceContext` already gives a renderer `session` + assistant message id (`entry`)**; with a fence ordinal that is a usable chat cell id and a ready-made hook for a Run button that talks to `useApi()`. Inline `openui` fences are inert precedent. (§1.3)
3. **A cell press is neither of theuth's two press paths.** `@Run` → `app_call_tool` → registry with a `UserActivation`; `@ToAssistant` → a `[app …]` user message. A cell press reaches no registry, no `tools.policy`, no `Approval`, and the owner's double (a bus subscriber keyed on a closed `CardKind` enum) never sees it. (§2, §8)
4. **Everything for a bash cell's execution and live streaming already exists as `Jobs`/PTY plumbing**: event stream (`JobStarted/Output/Screen/Idle/Finished`), per-job log, vault-value redaction on the byte path, `vt100` screen + `subscribe_pty` byte stream, `pty_input`/`pty_resize`, an xterm viewer. What is missing is a non-tool *entry point* and an inline mount. (§5)
5. **The `shell` tool is an embedded `brush` shell with persistent per-session state; pipe jobs have stdin `/dev/null`; PTY jobs run `$SHELL -lc` (zsh on Sky's Mac).** A user bash cell must not reuse the agent's session shell and must choose bash explicitly. (§5.1, §12.1)
6. **Jobs are not durable** (Sky's ruling): an engine restart kills a running cell; the log and last screen survive; `<job_result exit="lost">` is the model's notice. (§5.5)
7. **Monty is a subprocess pool (`monty-pool =1.4.0`, worker = `t subprocess`) with type-check-before-run, read-only `/cwd`, 512 MiB heap, 60 s protocol turns, stdout buffered per cell** — and a second, tool-less, differently-profiled Monty user (sensors) already ships. (§6)
8. **Notes are Yjs docs edited by BlockNote; the `codeBlock` node has one prop (`language`); markdown↔Y.Doc conversion is done by a bun helper, not Rust; no per-block side data exists; a replaced block gets a new id; ≤48 KiB/update, ≤8 MiB/doc; guests are gated to 11 `doc_*`/notebook read methods, so a cell RPC is owner-only by default.** (§3, §4)
9. **Secrets: `tools::secrets::{expand, redact, redact_spans}` are process-global and already used outside the registry** — a cell path can reuse them; redaction is **value-based only** (no AKIA/JWT pattern masking, which Sky's agent did by hand). (§7)
10. **Prompt plumbing is ready for a new block + skill**: `RegisterPrompt` blocks gated per audience (attended-only like `app`), bound-only precedent (`notebooks`), binary-owned skills rewritten at every start; the sentence to amend ("commands to run stay a plain code block") sits in `surface/visualize.md` and `surface/src/prompt.rs`, and "cell" already means a Monty `python` invocation in the runtime block. (§10, §6.4)

### 0.3 Short answers to the six design questions (from this recon only)
- **Q1 grammar:** nothing carries options through chat meta today; decide body-directive vs streamdown override (§1.2, G1–G3).

## 1. Chat rendering of fences


**Verdict for 171:** a ` ```bash cwd=… ` fence cannot be told apart from plain code by streamdown today (no meta reaches a renderer); the engine already treats the *whole* info string as the "language"; and the engine's validate/correct loop is closed to a fixed language list. A cell fence needs (a) dispatch by the first language word on the UI side with its options carried somewhere that survives, and (b) an engine-side opt-in if cells are to be validated.

### 1.1 Dispatch by language
- One `<Streamdown>` per assistant message, `mode='static'` once closed, `isAnimating` while open: `crates/desktop/ui/src/components/chat/MessageAssistant.tsx:322`.
- Custom fences are streamdown `plugins.renderers`, matched **by language before the built-in code block**. Three exist; everything else falls to `@streamdown/code` (shiki, github-light/dark): `crates/desktop/ui/src/components/chat/MessageAssistant.tsx:34`, entries `crates/desktop/ui/src/components/chat/MessageAssistant.tsx:37`, `crates/desktop/ui/src/components/chat/MessageAssistant.tsx:38`, `crates/desktop/ui/src/components/chat/MessageAssistant.tsx:39`. The rule is stated in the comment at `crates/desktop/ui/src/components/chat/MessageAssistant.tsx:31`.
- `markdownComponents` (`td`, `img`, `a`), `shikiTheme` and `rehypePlugins` are module-level so the highlighter is not re-initialised: `crates/desktop/ui/src/components/chat/MessageAssistant.tsx:60`, `crates/desktop/ui/src/components/chat/MessageAssistant.tsx:61`.
- `bash` / `python` / `sh` / `js` fences are therefore ordinary highlighted code blocks with streamdown's own header; the app passes no `controls` prop to `<Streamdown>` (props at `crates/desktop/ui/src/components/chat/MessageAssistant.tsx:325`), so defaults apply. Helpers `fenced()` and `lastCode()` exist for copy paths: `crates/desktop/ui/src/components/chat/MessageAssistant.tsx:73`, `crates/desktop/ui/src/components/chat/MessageAssistant.tsx:80`.

### 1.2 Does the info-string "meta" reach a renderer? — **No** (documented contract; the package is not installed in this checkout)
- Every renderer is declared `({ code, isIncomplete }: CustomRendererProps)`: `crates/desktop/ui/src/components/chat/surface/JsonRenderFence.tsx:72`, `crates/desktop/ui/src/components/chat/surface/OpenUIFence.tsx:67`; Mermaid adds only `fill` (`crates/desktop/ui/src/components/chat/Mermaid.tsx:139`).
- Streamdown's documented contract is `interface CustomRendererProps { code: string; language: string; isIncomplete: boolean }` — three props, no `meta`, no hast node (https://streamdown.ai/docs/custom-renderers, read 2026-11-03 through search_web, table "Every custom renderer receives these props"). Could not read the installed package: `crates/desktop/ui/node_modules` is absent here; the dependency is `streamdown ^2.6.0` (crates/desktop/ui/package.json, grep line 66). In mdast the text after the first word of an info string is `meta` and the hast class is `language-<first word>` only, so `renderers: [{language:'bash'}]` would still match ` ```bash cwd=/x ` but the options would be invisible to the component. **Design must therefore pick:** options in the fence *body* (first-line directive), or a `components.code` / rehype override reading `node.data.meta`, or a side table keyed by (message id, ordinal).
- The engine behaves the opposite way: `Fence.lang` is documented "Trimmed info string" (`crates/surface/src/fences.rs:13`) and `opening()` returns everything after the backtick run, trimmed (`crates/surface/src/fences.rs:94`). Selection is then **exact string equality**: `crates/surface/src/lib.rs:265` (`fences_of`, ordinals 1-based per language) and `crates/surface/src/fences.rs:72`. So ` ```json-render title=x ` is not a json-render fence to the engine, and ` ```bash cwd=/x ` has `lang == "bash cwd=/x"` there.
- The TUI hook also receives the whole info string: `FenceHook = Fn(&str lang, &str body, usize width)` (`crates/markdown/src/lib.rs:58`) filled from pulldown's `CodeBlockKind::Fenced(lang)` (`crates/markdown/src/lib.rs:613`); the TUI wires `surface::fence` into it (`crates/tui/src/model.rs:11124`).

### 1.6 Message identity, regeneration, and read-only transcripts
- `FenceContext.session` is **`undefined` for read-only renderings** (archive / search "Earlier messages" pages / viewers) — `session: readOnly ? undefined : session, entry: id`: `crates/desktop/ui/src/components/chat/MessageAssistant.tsx:299`. OpenUI's "Open as app" already hides itself when `session === undefined` (`crates/desktop/ui/src/components/chat/surface/OpenUIFence.tsx:93`). A cell widget gets the same switch for free: no session ⇒ show source, no Run.
- `hasLaterAssistant` is computed from the store ("whether a later assistant reply follows this message before the next human one"): `crates/desktop/ui/src/components/chat/MessageAssistant.tsx:289`. In the surface-error flow that flag means "a later reply in this turn carries the fix, so the broken fence renders nothing" (§1.3). For cells the equivalent question is whether an *earlier* presented cell is superseded by a corrected one in the same turn — the flag exists but its meaning for runnable cells is a design decision (disable, dim, or keep runnable).
- Regenerate / fork rebuild or branch the transcript from a turn: `crates/desktop/ui/src/components/chat/MessageAssistant.tsx:342`, `crates/desktop/ui/src/components/chat/MessageAssistant.tsx:200` (in `useFork`). A regenerated reply gets a new assistant message id (`entry`), so a chat cell key `(session, entry, ordinal)` is not stable across regenerate; stored run records must survive as "ran from a previous version of this reply" or be keyed by the source's content hash as well.
- Context removal ("RemoveButton") can drop a message from what the model sees without deleting it from the UI: `crates/desktop/ui/src/components/chat/MessageAssistant.tsx:346`. A cell run result delivered to the agent as a harness input is a context row like any other and is subject to the same removal and compaction rules (compaction folds old rows; a `<cell_result>` older than the epoch disappears unless kept in the notebook-style manifest).

## 2. Button presses from a message to the engine


**Verdict for 171:** theuth has exactly two ways a human click leaves a chat message: (A) an `app` button `@Run` → RPC `app_call_tool` → the **tool registry** with a `UserActivation` (it is a tool call, answered `Allow` by the press), and (B) `@ToAssistant` / draft buttons → ordinary `send_input`/`steer` of a text message that starts with `[app <name> v<n> · <record> · action <id>]`. A cell press is neither: it is a new RPC that never touches the registry, `tools.policy`, `Approval`, or the double — and its result needs a third, new wrapper (§5.7, §13).

### 2.1 Path A — `@Run` Mutation → engine
- UI: `AppHost` builds a provider per `(record, instance, generation)`: `crates/desktop/ui/src/components/apps/AppHost.tsx:276` over `crates/desktop/ui/src/components/apps/lifecycle.ts:253`. It records every press outcome as an `AppCallChanged` locally (comment "Every press outcome the view itself learns is recorded like its `AppCallChanged` would be (46 §6.4)").
- RPC: `app_call_tool(args: CallArgs)` — `crates/desktop/ui/src/rpc/api.ts:347` and the trait method `crates/rpc/src/api.rs:2615`, impl `crates/rpc/src/api.rs:8434`. Design 46 §6.3 lists the four `app_*` methods and says "No client-chosen arbitrary tool name": the server derives the tool from the pinned statement binding (`docs/design/46-apps.md:550`).
- Engine: the app actor turns a press into `UserActivation { record_call_id, action_id, request_id }` and asks the registry with `AppInvoke`: `crates/app/src/actor.rs:677`. The type: `crates/tools/src/registry.rs:183` — "Evidence that a human activated one action … It answers `Ask` for exactly the call whose id equals `request_id`: it is not inherited by later refreshes, other `@Run` targets or the model."
- Admission order in the registry (`admit_app`): visibility → availability → pinned identity → schema → activation matches this call → policy; on `Ask` with an activation it logs "app call approved by the user's activation" and proceeds, on `Deny` it is final, on `Ask` without activation it returns `NeedsApproval` (no prompt): `crates/tools/src/registry.rs:1049`, `crates/tools/src/registry.rs:1098`. Docs: `docs/design/46-apps.md:488` ("No mutable approval bypass on the session … no `press_mutating` option").
- So Path A **reuses** policy (`Deny` still wins, risk is still computed) and the human press *replaces the approval card*. A cell press differs: no tool, no risk class, no `tools.policy` row, no `Approval` actor, no `ApprovalRequested` event (§8).

### 2.3 Approval cards and the owner's double
- A tool needing approval publishes `ApprovalRequested` (`crates/tools/src/approval.rs:43`) and waits for `Resolve` (`crates/tools/src/approval.rs:73`); UIs answer through RPC `resolve_approval` / `answer_ask` (`crates/rpc/src/api.rs:666`, `crates/rpc/src/api.rs:670`).
- The double (design 126) is a **bus client**, not a hook: "it subscribes to `ApprovalRequested` / `AskRequested` the way the RPC bridge does … at L2/L3 answers through the same actor messages a UI sends (`tools::ResolveBy`, `agent::answer_ask_by`). Nothing inside the agent loop knows it exists": `crates/double/src/lib.rs:4`. Its decision classes are a closed enum: `crates/double/src/class.rs:18` = Approval, Ask, Attention, Packet, Draft — no cell kind, and a draft's button press is only *predicted* (L0/L1 chip), never auto-pressed: `docs/design/126-double.md:119`.
- The double's chip appears beside the approval title and preselects Allow/Deny at L1: `crates/desktop/ui/src/components/chat/ApprovalCard.tsx:38`, `crates/desktop/ui/src/components/chat/ApprovalCard.tsx:40`.
- **Why a cell press is invisible to the double by construction:** it emits no `ApprovalRequested`/`AskRequested`, so nothing subscribes and nothing can answer. The remaining risk is a different one: a double-driven *UI* automation (none exists) or the agent faking a press — the RPC must be the only entry and must refuse agent-origin callers (§9, §13 G3).

## 3. Notes: BlockNote schema, document crate, sharing


**Verdict for 171:** a note is a ProseMirror/Yjs document edited by BlockNote in the UI and by a headless **bun helper** (`packages/documents`, BlockNote server editor) for the engine; the Rust `document` crate only stores Yjs bytes, never parses markdown. The `codeBlock` node has **one prop, `language`**, and a markdown import keeps the whole info string in it. There is no per-block side data keyed by block id today other than text/props inside the Y.Doc itself and one derived map of member labels. Cell options (cwd, interpreter) and cell outputs have no home yet.

### 3.1 BlockNote schema and the code block
- One shared schema for helper and UI: `packages/documents/src/schema.ts:71`; blocks are BlockNote defaults minus media plus `frontmatter` (comment at `packages/documents/src/schema.ts:59`). The document body lives in one `Y.XmlFragment`: `packages/documents/src/schema.ts:25`.
- The substitutable `codeBlock` spec is typed `BlockSpec<"codeBlock", { language: { default: string } }, "plain">` — **the only prop is `language`** and the content is plain text: `packages/documents/src/schema.ts:73`. A new cell block *type* would "fork the shared schema (§4.5 split) and every collaborator's editor" (design 59 §9.2: `docs/design/59-documents.md:951`).
- The UI builds it from BlockNote's own spec: `crates/desktop/ui/src/components/editor/CodeBlock.tsx:18`; only `render` is ours, so "the ProseMirror node — and the Yjs fragment — are the default's" (`crates/desktop/ui/src/components/editor/CodeBlock.tsx:16`). Exported spec: `crates/desktop/ui/src/components/editor/CodeBlock.tsx:161`; its `toExternalHTML` (copy / external HTML) emits plain `<pre><code class=\"language-…\">`: `crates/desktop/ui/src/components/editor/CodeBlock.tsx:169`.

### 3.3 Limits, sharing, untrusted members
- Limits: one update ≤ 48 KiB (`crates/document/src/actor.rs:947`), Y state ≤ 8 MiB with `DocTooLarge` (`crates/document/src/actor.rs:357`); documented in `docs/design/59-documents.md:499`. Long outputs must therefore stay out of the Y.Doc (or be capped hard).
- Roles: `owner` (implicit: the harness's devices), `editor`, `viewer` — `docs/design/59-documents.md:809`. A member's text is labelled `by <name> · doc-member:<id>` when `doc_read` returns it and treated as untrusted data: `crates/document/src/tools.rs:34`; "Prompt injection in a member's text steers the owner's agent" is threat row 1 of 59 §11 (`docs/design/59-documents.md:1016`).
- **Guests cannot call anything but doc methods**: mode-2 connections are gated to an 11-method list, `doc_join … cite_resolve`, membership-checked per call: `crates/link/src/conn.rs:538`, `crates/link/src/conn.rs:566`. A new `cell_run` RPC is therefore **owner-only by default**; a member who edits a shared note could change cell source (a Y.Doc write) but can never press Run on the owner's engine. The risk to design for is the other direction: the owner pressing Run on source a member wrote — show the `doc-member` authorship on the cell and require a fresh look (the block's last author is available, §3.2).
- Undo / attribution: "Undo last agent edit" is an inverse `doc_replace` computed from touched ids (`docs/design/59-documents.md:601`); `DocEvent::Authored { blocks, by }` is published when the agent wrote (`crates/document/src/actor.rs:343`).

### 3.4 Where an agent-authored cell lands in a note
Agents write notes by `doc_create(markdown=…)` / `doc_insert(markdown=…)` with fenced blocks; whatever follows the language word becomes the `language` prop (above). Sky's run sheets today are exactly this shape (checkbox heading + ```bash block + "You should see:"), so the minimal 171 note path is: keep a plain ```bash fence as the source of truth, add a Run affordance in `CodeBlock.tsx` for languages in a cell set, and keep options in the fence body or a leading directive line so they round-trip through markdown unchanged.

### 3.5 Search and export of notes (what a cell inherits)
- Every block of every note, board, meeting note and source is indexed at block level (FTS5 `nb_blocks` + `nb_vec`), kind ∈ note|board|meeting_note|source|insight|notebook: `docs/design/144-notebooks.md:504`. A code block's text is therefore searchable by the agent's `nb_search` and the user's search; **outputs would be searchable only if they were written into the document**, which §3.3 argues against (size, noise, secrets).
- Export: notes export through the derived `note.md` and design 72 (PDF/HTML; "diagrams as text" in PDF, client-rendered SVG in HTML — per the `doc_export` description in the tool list: "`pdf` (default; A4, diagrams as text, excerpts as n…)"). A cell exported to PDF/markdown is just its fenced source; the run record would be absent unless 171 decides otherwise.
- The agent's view of a note (outline) shows the cell as `[code:bash cwd=/x] first line … (N lines)` (§3.2) — there is no way for `doc_read` to say "this cell was run, exit 0, at 17:12" unless that state is written into the document or surfaced through a different read (a notebook-style `<notebook_changes>` line or a `cell_runs` read tool).

## 4. Notebooks (144, 157)


**Verdict for 171:** a notebook is *not* a new cell container — it is a `DocKind::Notebook` description document plus replicated `notebook_items` rows that point at ordinary note documents. A "notebook cell" is therefore a code block in one of its notes (§3). What the notebook adds is (a) a chat column bound to a session, (b) a per-turn `<notebook>`/`<notebook_changes>` context channel, and (c) a hub/replica model with guests. "Run all" has to be defined over *one note*, not the notebook.

### 4.1 Page structure
- Three columns `320px | 1fr | 320px` — sources | chat | notes (and one column with tabs under 768 px): `docs/design/144-notebooks.md:677`. UI files: `crates/desktop/ui/src/components/notebooks/NotebookPage.tsx:142` (left), `ChatColumn` (centre), and the right pane switching between the list and one note: `crates/desktop/ui/src/components/notebooks/NotebookPage.tsx:156`.
- `NotePane` is the *same* editor as `/notes/$id`: `crates/desktop/ui/src/components/notebooks/NotePane.tsx:22` with the title input, a pop-out ("Open in new window", `openPopout({ kind: 'note', … })`), and "Ask theuth…" from a block, which pre-fills the notebook chat composer (`about block <id>: `): `crates/desktop/ui/src/components/notebooks/NotePane.tsx:33`. So a cell's run affordance placed in `CodeBlock.tsx` appears in notes, notebook note panes, popped-out windows and the share-link guest view at once.
- Chat column: `ChatColumn` lists the notebook's sessions, "every message leads with the notebook's `[attached notebook …]` marker; the first message's session is bound with `session_set_notebook`": `crates/desktop/ui/src/components/notebooks/ChatColumn.tsx:48`. Binding is server-side: "`sessions` gains `notebook TEXT NULL` … One notebook per session": `docs/design/144-notebooks.md:585`.
- The notebook chat column is **owner-only**: "Members and guests never get a composer"; `notebook_chats` is not on the guest allow-list (`docs/design/144-notebooks.md:603`, `crates/link/src/conn.rs:546`).

### 4.2 How the notebook chat agent edits notes
- The agent crate does not depend on `document`; every read/write is a tool call as `Principal::Agent { session }`: `crates/agent/src/notebooks.rs:6`. Tools: `notebook_create/list/get/add/remove`, `source_add/list/get/refresh` (`crates/document/src/nb_tools.rs:122`, `crates/document/src/nb_tools.rs:352`) plus `doc_read` / `doc_insert` / `doc_replace` / `doc_create`.
- "Save answer as note" and "Promote into this note" are UI actions that call `doc_create` / `doc_insert(at="end")` with the message markdown under `## From chat · <date>` (`docs/design/144-notebooks.md:596`) — a ```bash fence in the answer lands in the note as a plain code block, language prop = whatever followed the language word (§3.1). - The static contract block for a bound session: `crates/agent/src/notebooks.rs:25`, appended only when bound: `crates/agent/src/notebooks.rs:44` and called with `bound` from `crates/agent/src/loop_.rs:4250`. This is the existing example of a **conditional prompt block** (a `## Cells` block could follow it).

### 4.3 `<notebook>` and `<notebook_changes>`
- Once per epoch the first user turn of a bound chat gets a `<notebook id title>` block (full / summary / mention per item), and "a short `<notebook_changes>` message lists each change with the item's id and how to read it, never the content": injection point `crates/agent/src/loop_.rs:5588`; message builder `crates/agent/src/notebook_context.rs:851` ("One line of a `<notebook_changes>` note (157 D2/D7): never the content", `crates/agent/src/notebook_context.rs:700`).
- **Consequence for cell outputs:** a notebook edit made by a *run* (output written into a note, if the design stores outputs there) would show up as a change line, not as content — the agent would have to `doc_read` it. If outputs are instead delivered as a `<cell_result>` message (§5.7) the notebook machinery is not involved at all.

### 4.4 Sharing and replication (what a cell inherits)
- A notebook is shared like a note (`doc_link_create` / `doc_member_set` on the Notebook document); a member's grant extends to its note and source items; sessions never: `docs/design/144-notebooks.md:650`. Guests dial the hub and get three columns, no composer, notes editable per role, sources read-only (`docs/design/144-notebooks.md:661`).
- Replication: documents mirror like every document; the hub lease decides who serves editors: `docs/design/144-notebooks.md:658`. A cell run is by definition **on the engine that owns the session** (jobs carry an `engine` column since 139: `crates/tools/src/journal.rs:375`); when the notebook is edited on a phone against a hub engine the run still has to be routed to the right engine — see §9.4.

## 5. Jobs and PTYs


**Verdict for 171:** everything a bash cell needs already exists as *engine plumbing* — a `Jobs` actor that runs processes under a session, streams their output as bus events, keeps a log, redacts vault values, and (for PTY jobs) keeps a `vt100` screen that any client can attach to over `subscribe_pty`. What is missing is only an *entry point that is not a tool call* and a *delivery wrapper that is not `<job_result>`*. Jobs are **not durable** across an engine restart (Sky's ruling, 109 R1). The user can already open and type into any live PTY job from the UI.

### 5.1 `shell` — embedded bash, one persistent shell per session
- Implementation: `ShellTool` over an in-process `brush_core::Shell`, **not** `/bin/bash` or the login shell: `crates/tools/src/shell.rs:1`; "State (cwd, variables, functions) persists across calls within a session" and shell state is last-finished-wins: `crates/tools/src/shell.rs:45`. A call with `cwd` or `env` runs on a throw-away clone: `crates/tools/src/shell.rs:49`. Args (`command`, `cwd`, `timeout_secs`, `env`): `crates/tools/src/shell.rs:26`.
- PATH: with `tools.login_path` (default true, `crates/tools/src/lib.rs:513`) the session shell's `PATH` is seeded from `$SHELL -l -i -c 'printf %s "$PATH"'` once per process: `crates/platform/src/env.rs:12`. Only `PATH` is probed (module comment at crates/platform/src/env.rs:2). brush is bash-compatible but a *different implementation*; builtins `bind history fc complete compgen compopt` are skipped (`crates/tools/src/shell.rs:22`). A user-run "bash" cell on macOS therefore has three candidate meanings: brush (engine), `/bin/bash` 3.2, or the user's `$SHELL` (zsh) — see §12.
- Job plumbing: every `shell` call is a job; stdin is `/dev/null` (`params.set_fd(0, null)`), stdout/stderr are two pipes, its own process group: `crates/tools/src/jobs.rs:1747`, `crates/tools/src/jobs.rs:1750`. **No stdin for pipe jobs** — an interactive prompt in a bash cell would hang until the job timeout unless the cell runs on a PTY.

### 5.2 `Jobs` actor: events, caps, log, redaction
- Module doc: "every process the model starts is a background job … streams output to `<resources.root>/jobs/<session>/<id>.log`, publishes `JobEvent`s on the bus": `crates/tools/src/jobs.rs:1`.
- Events (wire tags `JobStarted | JobOutput | JobScreen | JobIdle | JobFinished`): `crates/tools/src/jobs.rs:183`. `JobStarted` carries `call_id` ("UIs attach live output to its card"), `log`, `pty`; `JobOutput` carries a lossy-UTF-8 chunk **coalesced to at most one per 500 ms** and "lossy under a flood; the log file is the truth": `crates/tools/src/jobs.rs:50`.
- Caps: output reaching the model is cut to 64 KiB (`crates/tools/src/jobs.rs:42`); the per-job tail is 8 KiB (`crates/tools/src/jobs.rs:44`); the stub quotes 2 KiB; 32 finished rows kept per session (`crates/tools/src/jobs.rs:48`); retained-terminal budget 512 MiB ≈ 80 PTYs engine-wide (`crates/tools/src/jobs.rs:62`). Defaults: `job_grace_secs` 3, `job_timeout_secs` 1800, `pty_idle_secs` 60 (`crates/tools/src/lib.rs:533`, `crates/tools/src/lib.rs:534`, `crates/tools/src/lib.rs:536`).
- **Redaction already sits on the byte path**: `Log::push` runs `secrets::redact` on every chunk before the log file, the tail and the event ("best effort, a value split across two chunks escapes; `run`'s pass over the whole render is the exact one"): `crates/tools/src/jobs.rs:593`, call `crates/tools/src/jobs.rs:598`; the command line shown in events is scrubbed too (`crates/tools/src/jobs.rs:1053`). It redacts only *vault values and their base64* (§7) — it does not pattern-match AKIA…/eyJ… credentials the way the agent did by hand on 10-16.
- Start request: `Start { session, command, call_id, quiet, shell, put_back, root, activity, timeout }` — `quiet` means "No JobEvent, no log file, no jobs row"; `activity` documents that an "untracked or absent parent (pre-registration invocation, RPC, tests) admits under the supervisor installed on the actor": `crates/tools/src/jobs.rs:322`, `crates/tools/src/jobs.rs:344`. So an RPC-originated job start is an anticipated shape.

### 5.3 PTY jobs: `start` / `send` / `screen` / `wait` / `cancel_job`
- Implementation crate/file: `crates/tools/src/pty.rs` ("PTY jobs (design doc 22) … a rendered 120×40 screen instead of the raw bytes"): `crates/tools/src/pty.rs:1`. PTY layer: `portable-pty` 0.9 (wezterm's), screen: **`vt100` 0.18** (`Cargo.toml:269-270`): `Cargo.toml:269`, `Cargo.toml:270`. Not alacritty_terminal, not wezterm-term.
- Spawn: command line run by `$SHELL -lc` (Unix) or `pwsh.exe`/`powershell.exe -NoLogo -Command` (Windows), override `tools.pty_shell`: `crates/platform/src/shell.rs:49`. `StartArgs { command, name, cwd, env, ready, idle_secs }`: `crates/tools/src/pty.rs:266`. Fixed grid 120×40, resizable 2–200 × 10–400: `crates/tools/src/pty.rs:40`, `crates/tools/src/pty.rs:42`, `crates/tools/src/pty.rs:44`.
- The emulator state per job: `parser: Mutex<vt100::Parser::new(ROWS, COLS, HISTORY)>` with `HISTORY = 512` scrollback rows (normal screen only): `crates/tools/src/pty.rs:1436`, `crates/tools/src/pty.rs:71`; a broadcast ring of 256 chunks feeds subscribers (`crates/tools/src/pty.rs:48`).
- **Terminal queries (167, "the engine is the one responder")**: the *engine* answers DA/DSR/cursor-position style queries on the PTY master and never logs the reply: `crates/tools/src/pty.rs:2460` (`fn respond`, carry ≤ 16 bytes across chunks, `crates/tools/src/pty.rs:67`); the client's xterm swallows those same queries so the program is not answered twice: `crates/desktop/ui/src/components/chat/TerminalViewer.tsx:170`, design `docs/design/167-pty-keys.md:1`.
- `screen()` rows: `PtyPage` pages of rows of styled cells (`wide`/`continuation`), history pages ≤ 80 rows, ≤ 256 KiB, ≤ 4 concurrent snapshot renders: `crates/tools/src/pty.rs:85`, `crates/tools/src/pty.rs:91`. The model-facing `screen`/`<job_idle>` body is the non-blank prefix of the 40 rows plus a `cursor:` line (`JobEvent::Screen`/`Idle` doc comments in jobs.rs).
- Input and pacing: `send` replies once no bytes arrived for 300 ms or after 2 s; `wait` default 30 s / max 120 s; replies carry a `user attached` trailer for 30 s after a human typed: `crates/tools/src/pty.rs:50`, `crates/tools/src/pty.rs:57`, `crates/tools/src/pty.rs:54` (design 55 §2.3, `docs/design/55-interactive-terminals.md:114`).
- Idle / busy-quiet (61, 155): `<job_idle>` after `pty_idle_secs` of unchanged screen, with `tree_cpu_pct` and `pty_reaction_secs` refinements: `crates/tools/src/lib.rs:523`, `crates/tools/src/lib.rs:520`. `JobEvent::Idle` carries `user_typed_secs` (`crates/tools/src/pty.rs:2186`).

### 5.4 Delivery to the agent: `<job_result>` and `<job_idle>`
- A finished non-inline job's result becomes a harness input; "the *only* model-delivery path; the public `JobEvent::Finished` stays for UIs": `crates/agent/src/supervisor.rs:2821`, wrapper `crates/agent/src/supervisor.rs:3093` (`<job_result id command exit secs [pty="true"] at>…</job_result>`, command cut to 120 chars, exit = code | `timeout` | `killed` | `lost`). Text is capped with the spill rule (`spill::cap(…, max_tool_output_chars, …)`, `crates/agent/src/supervisor.rs:2134`).
- Quiet PTY: `crates/agent/src/supervisor.rs:3126` — same wrap-cap-inject path under the op's network scope.
- **Does it start a turn?** `inject` admits an `InputOrigin::Automatic` ticket; "an idle session starts a new turn, a running one queues it, and a session with no live actor is resumed by `route`" (doc comment on `settle`: `crates/agent/src/supervisor.rs:2824`); `Automatic` "never opens a new reminder budget (47 §4.5)" (`crates/agent/src/supervisor.rs:1496`). For a session owned by another engine the body is queued in `harness_outbox` and shipped to the owner (139 R2): `crates/agent/src/supervisor.rs:1514`. A talk session parks it until its window opens (`crates/agent/src/supervisor.rs:1551`).
- UI card for these wrappers: `Injected` kinds `job` / `job_idle` in `crates/desktop/ui/src/lib/injected.ts:26` (a precedent for a `cell_result` card; `CARD` table at `crates/desktop/ui/src/lib/injected.ts:53`).
- **Design question this exposes:** for cells the *user* pressed and is watching, injecting `<job_result>` as an Automatic input would wake the agent mid-run-sheet each time. The brief's requirement ("the agent can see it in context once it completes") can be met without a turn: append to the session's history as a harness row that rides the *next* user/agent turn (the `<notebook_changes>` / `<time>` pattern is the nearest), and let the user choose "tell theuth" explicitly.

### 5.5 Durability (109): jobs die with the engine
- Ruling R1: "**Jobs are not durable**: a shell or PTY job dies with the engine. Its `jobs` row exists so that on resume the model gets `<job_result exit="lost">` with the log path, `screen()` serves the last s[creen]": `docs/design/109-durability.md:42`; D3 "NO adoption; graceful shutdown keeps killing job groups" (`docs/design/109-durability.md:46`); detached job-keeper "offered and not chosen for now" (`docs/design/109-durability.md:28`). 139 added `jobs.engine` and attached `pty_screens` to replication: `docs/design/139-as-built-C.md:8`.
- For cells: an `engine restart` / `t update` mid-`terraform apply` kills the process group exactly as it kills an agent's `shell` job. The viewer must say "lost — engine restarted", show the last retained screen and log path, and never offer "Run" as if it were a retry of an idempotent action.

### 5.6 Can the user already watch / drive a PTY job from the UI? **Yes**
- RPC (`crates/rpc/src/api.rs`): `list_terminals`, `pty_screen`, `pty_input` ("A human types into a running PTY job"), `pty_resize`, subscription `subscribe_pty`/`unsubscribe_pty` with items `PtyChunk::{Reset{data b64,rows,cols}, Data{data b64}, Exit{exit}}`, a lagging client gets a fresh `Reset`: `crates/rpc/src/api.rs:271`, `crates/rpc/src/api.rs:292`, `crates/rpc/src/api.rs:314`, enum `crates/tools/src/pty.rs:1124`. All are `authorize(ext, session)`-gated ("Durable sessions admit any authenticated peer; a private one only its owner"): `crates/rpc/src/api.rs:2847`.
- UI: `TerminalViewer.tsx` — xterm.js 6 over `client.stream('subscribe_pty', [session, job, rows, cols], …)`: `crates/desktop/ui/src/components/chat/TerminalViewer.tsx:185`; keystrokes go through one in-flight `pty_input` lane (`crates/desktop/ui/src/components/chat/TerminalViewer.tsx:157`), macOS editing keys via `macKeyBytes` (167 D1), resize via `pty_resize`; the viewer sizes the PTY itself and restores 120×40 on leave (comment at `crates/desktop/ui/src/components/chat/TerminalViewer.tsx:32`). Mounted from the chat header (`TerminalButton`, `TerminalViewer` imported at `crates/desktop/ui/src/components/chat/Header.tsx:39`) and as a pop-out route (`/pty/$session/$job`, `crates/desktop/ui/src/routes/pty.$session.$job.tsx:2`). Sandbox VMs expose the same: `sandbox_terminal(name)` returns `{session, job}` for `msb exec --tty … bash -l` (`crates/desktop/ui/src/rpc/api.ts:722`).
- TUI: has `pty_screen` / `pty_input` commands: `crates/tui/src/model.rs:863`.
- Net: a "Run" that starts a PTY job in the session and shows the existing `Terminal` inline needs **no new streaming protocol** for bash — it needs a way to start the job from the UI, an inline mount of `Terminal` (today only the header panel/pop-out mounts it), and a pairing of (cell id ↔ job id).

### 5.7 Who consumes `JobEvent` (grep, not the code index)
- `grep -rln JobEvent crates --include=*.rs` → producers `crates/tools/src/{jobs,pty,activity,lib}.rs`; consumers `crates/rpc/src/bridge.rs` (fan-out to every connection's `subscribe_events`), `crates/agent/src/supervisor.rs` (the `<job_result>`/`<job_idle>` path, §5.4), `crates/tui/src/{lib,model}.rs`; `crates/rpc/src/{export,client}.rs` carry the wire type. (`code_refs(symbol="JobEvent")` shows the definition `crates/tools/src/jobs.rs:183` and "0 incoming references" — the index does not resolve enum use sites across these crates.) So a cell job that goes through `Jobs` is delivered live to desktop/web/phone/TUI for free, **and** is also eligible for the supervisor's `<job_result>` injection unless it is started `quiet` or marked inline — the cells actor must decide which (§5.4, §13 G9).
- The inline-vs-injected switch is a field of the event: "`inline`: The tool call already returned this result (exited within the grace window), or the model killed it; UIs still count it, the agent must not inject it" (`crates/tools/src/jobs.rs:280`). A cell actor that waits for the job itself and then reports through its own channel can set the equivalent to keep the agent un-woken.

## 6. Monty runtime


**Verdict for 171:** "Monty" is the sandboxed Python-subset interpreter from the `monty-*` crates (pinned `=1.4.0`), run in **worker subprocesses of the `t` binary** under a `monty-pool` `Pool`. The agent's `python` tool is *one* user of it (persistent heap per session, every registered tool bound as an async function, routed through the registry). The **sensor runner is a second, already-shipping user** with its own pool, profile, limits, read-only `/cwd` mount and a fixed tool table that bypasses the registry — i.e. an isolated, non-agent Monty with no tool bindings is an existing pattern, not a new capability. Neither streams stdout live today (print is buffered per cell) but the hook that receives each print is synchronous per call and could be forwarded.

### 6.1 What it is, version, process model
- Pins: `Cargo.toml:260` (+ `monty-types`, `monty-fs`, `monty-proto` with `worker`, `monty-alloc`): "Python runtime (design doc 08): pool of `monty` worker subprocesses". Worker is the app binary itself: "In production that is this binary (`t subprocess`, 08 §9), so nothing has to be installed": `crates/agent/src/repl.rs:166`; pool bounds `REPL_POOL_MAX = 48` (`crates/agent/src/repl.rs:160`), `request_timeout = 60 s` (`crates/agent/src/repl.rs:53`), a checkout is recycled after 100 uses (`max_checkouts_per_worker`). Wire protocol 5→6 and dump format 13→14 at 1.4.0 (knowledge `facts/theuth-monty-1-4-0-bump-facts-2026-11-02`).
- Language: "a sandboxed Python 3.14 subset (Monty): no third-party packages, no generators, no class inheritance; stdlib: json re math datetime time random copy collections itertools functools dataclasses pathlib base64 hashlib decimal bisect csv tomllib os.path asyncio(gather, sleep)": `crates/agent/src/repl.rs:81` — this text is what the model is told. theuth has **no module allowlist**; unknown imports end in `ModuleNotFoundError` via the `OsCall → NotHandled` path (same knowledge item).

### 6.2 State, type check, limits
- State: one `Repl` per live turn owns a `Checkout`; "The heap is dumped after every cell to `<data_dir>/runtime/<session>.monty` and restored on the next open": `crates/agent/src/repl.rs:3`. Names starting with `_` do not carry across cells, imports are re-prefixed per cell, one assignment per line (knowledge `warnings/monty-no-hasattr-and-imports-not-seen-across-cells`).
- **Type check before run, nothing executes on failure**: `ReplConfig { type_check: true, type_check_stubs: Some(stubs(&specs)), limits: Some(ResourceLimits{ max_memory, max_suspensions, max_total_sleep }), os_policy: OsPolicy{ timezone, sleep: SleepMode::System(300s) } }`: `crates/agent/src/repl.rs:1020`; `type_check: true` at `crates/agent/src/repl.rs:1027`. Limits: heap `crates/agent/src/repl.rs:42`, 100 000 suspensions, 600 s cumulative sleep (`crates/agent/src/repl.rs:63`). A pure type-check-without-running exists as a pool call (`feed(code, …, skip_type_check, …)` at `crates/agent/src/repl.rs:1621`); a "lint this cell" affordance would use it. (Counting rule: two suspensions per awaited tool call — knowledge `facts/monty-suspension-counter-is-two-per-tool-call`.)
- Failure shape: `PoolError::Typing(diag)` before any execution, `Runtime(exc)`, `MemoryError` kills the worker and the dump is lost (131: `docs/design/131-runtime-reset.md:9`); restore cap `DUMP_HARD_BYTES = 64 MiB` (`crates/agent/src/repl.rs:48`).

### 6.3 Filesystem, I/O, stdout
- **No host filesystem write, no network, no subprocess.** Reads: `cwd` mounted **read-only** at `/cwd` and the spill dir at `/spill`: `crates/agent/src/repl.rs:1104` ("`/cwd` is the working directory (read-only); write files with `write_file()`", `crates/agent/src/repl.rs:79`). Writing, HTTP and shell exist only because the agent's `python` binds the *registered tools* as async functions.
- stdout capture: per-cell `String` filled by a synchronous callback and rendered with the result: `crates/agent/src/repl.rs:1274`; the result body is capped at `RUN_OUTPUT_CHARS = 8000` (head 6000 / tail 2000): `crates/agent/src/repl.rs:40`. The callback fires per `print` — forwarding to a channel would give line-granular live output; today nothing does.
- Tool binding: names resolve through `TurnEvent::NameLookup` → `find_tool(&cx.registry, session, &name)` and `TurnEvent::FunctionCall` → registry `Invoke` ("exactly like a direct call", policy and approvals apply): `crates/agent/src/repl.rs:1632`, `crates/agent/src/repl.rs:1647`. The `python` tool itself is declared `Risk::ReadOnly` with inner calls gated individually: `crates/agent/src/repl.rs:127`.

### 6.4 A second isolated interpreter (no tool bindings)
- **Precedent — the sensor runner.** One checkout per evaluation under a *sensor profile*, `/cwd` read-only, "a fixed five-entry tool table" that "calls the tool structs directly — never the registry's `Invoke`", results scrubbed by the same redactor: `crates/agent/src/sensor/bridge.rs:1`, profile limits and `SleepMode::Zero` at `crates/agent/src/sensor/bridge.rs:144`, its own `Pool` owned by the schedule plugin ("The sensor-profile pool (40 §4.2)"): `crates/agent/src/sensor/mod.rs:184`. The same runner also falls back to **CPython** for `# needs: cpython` sensors, "No tool bridge and no secrets": `crates/agent/src/sensor/cpython.rs:1`.
- So a cell kernel for `monty` would be: a `Checkout` from a pool (the shared 48-slot repl pool or a third pool), `ReplConfig` with `type_check_stubs: None` (or stdlib only) and an empty tool table, `/cwd` mounted per the cell's cwd, `OsPolicy` as the agent's. State persistence across cells = keep the `Checkout` alive per kernel (`Repl` does this per turn, then dumps/restores); per-kernel lifecycle (idle timeout, restart) would be new code beside `Repl::open`/`dump` (`crates/agent/src/repl.rs:1515`).
- Naming collision to avoid in prompts and UI: the agent already calls each `python` invocation a **"cell"** (`CellPermit`, `CellRunning` in `crates/agent/src/repl.rs:35` and the `RUNTIME_BLOCK` text "a cell is type-checked before it runs"). The design should pick a different word in the agent-facing prompt ("run sheet"? "block"?) or define the two explicitly.
- What the user must be told when choosing Monty over CPython: no `pip` packages, no `subprocess`/`os.system`/network, no file writes, 512 MiB heap, 60 s per protocol turn, subset syntax (no generators/class inheritance). For the "is Monty sufficient?" decision, those are the deciding checks; the pre-run type check gives a cheap automatic answer ("will this even parse/type under Monty?").

## 7. Secrets


**Verdict for 171:** both halves are **process-global, tool-agnostic functions** in `tools::secrets`, already called from non-tool code (sensor bridge, app actor, python bridge, dreaming, double). A cell run path can call `expand` on its source (as a JSON string value) and `redact` / `redact_spans` on every output byte without touching the registry. What is *not* there: pattern-based credential redaction (only vault values and their base64), and any "this cell uses secret X" label for the presser.

### 7.1 Where placeholders become values
- Hook definition (37 §3.4): "where the double-brace `secret:NAME` / `secret:NAME:-N` placeholders in tool arguments become values, and where values in tool output become placeholders again … A process global rather than a message because the readers — the registry, jobs, `mcp::expand` and the python bridge — are four actors across two crates": `crates/tools/src/secrets.rs:1`. Trait: `crates/tools/src/secrets.rs:22`; installed once by the `secrets` plugin (`crates/tools/src/secrets.rs:46`); every function is the identity when no vault is installed.
- Expansion for tool calls: in the registry's dispatch, after approval and before the tool body — "an unknown name fails the whole call": `crates/tools/src/registry.rs:1693`. It operates on a `serde_json::Value` (every string leaf): `crates/tools/src/secrets.rs:64`. "A tool that stores its arguments as an artifact keeps them literal" (comment at `crates/tools/src/registry.rs:1690`): **placeholders written into a note's code block stay literal in the document**; expansion belongs at the run boundary only.
- The gate raises `Ask` when args mention a secret (`mentions`), "at least `Ask` when the args carry a secret placeholder (37 §0.4)": `crates/tools/src/registry.rs:970`; and `Allow` is never granted silently for secret use except by an activation ("including secret use, mutating and destructive risk", 46 §6.1). For cells this is moot (no gate) — so the **press itself is the consent for secret use** and the UI should say which secret names a cell mentions before Run (the scan is the cheap `mentions` function: `crates/tools/src/secrets.rs:54`).
- Other non-tool callers to copy: sensor bridge (`http_request` headers only, "through the same `tools::secrets` hook the registry uses": `crates/agent/src/sensor/bridge.rs:393`), python bridge (`crates/agent/src/repl.rs:1473`), app actor (`crates/app/src/actor.rs:720`).

### 7.2 Where values are scrubbed from output
- Tool results: `redact_output` at the end of dispatch: `crates/tools/src/registry.rs:1766`; implementation redacts `content` and every string in `structured`: `crates/tools/src/secrets.rs:96`.
- Job bytes and command lines (§5.2): `crates/tools/src/jobs.rs:598`, final render `crates/tools/src/jobs.rs:1288`, PTY screens through span masking across the row grid: `crates/tools/src/pty.rs:589` with `max_literal_len()` so a value split over cells is still masked.
- The vault side: `impl Secrets for Vault` — `crates/secrets/src/lib.rs:709`. Redaction replaces "every kept version of every value (and its base64) → its placeholder" (`crates/tools/src/secrets.rs:27`).
- **Gap (matters for IaC cells):** this is value-based. A `pulumi up` / `aws sts` / `kubectl get secret` output that contains an AWS key, JWT or session token which is *not* in the vault passes through unredacted. On 10-16 the agent scanned PTY output by hand for `AKIA…`, `eyJ…`, `aws_session_token` before showing it (axes file). The "agent sees it in context" channel for cells needs its own pattern pass *in addition to* vault redaction, and the user-visible stream should keep the raw bytes only if the user chooses.
- Other scrub points that already exist for model-bound text: dreaming (`crates/dreaming/src/scrub.rs:32`), double store (`crates/double/src/store.rs:7`).

## 8. Policy and approvals


**Verdict for 171:** policy is a pure function of *tool risk class*; approvals are an actor that the registry — and only the registry — calls. Cells are not tool calls, so they neither consult nor bypass any of it. The one thing a cell *must* keep from this machinery is a human-origin guarantee (§9.3).

### 8.1 Where `tools.policy` is enforced
- `Policy { read_only: Allow, mutating: Ask, destructive: Ask }` is the default: `crates/tools/src/lib.rs:549`, defaults at `crates/tools/src/lib.rs:562`; `Risk` has three classes ("Irreversible or unbounded (arbitrary shell, delete, network writes)" is `Destructive`): `crates/tools/src/lib.rs:120`. Config key `tools.policy` (`crates/tools/src/lib.rs:529`).
- The one permission decision: `crates/tools/src/registry.rs:973` — `Deny` for a tool above the session's cap, else the risk's policy, raised to `Ask` for secret placeholders, then `Ask`→`Allow` by approval switches (global `approvals: false`, or a session / ancestor opted out); "`Deny` is never rewritten": doc comment at `crates/tools/src/registry.rs:968`. Denial text: `"denied by policy"` (`crates/tools/src/registry.rs:1000`); subagent caps: `"denied: subagent is capped at …"`.
- Approval flow: `Approval` actor publishes `ApprovalRequested`, any UI answers `Resolve` (`crates/tools/src/approval.rs:43`, `crates/tools/src/approval.rs:73`), RPC `resolve_approval` (`crates/rpc/src/api.rs:666`); card `crates/desktop/ui/src/components/chat/ApprovalCard.tsx:38`.
- The double's ladder: L0–L3, 30 s grace at L2, answers as `ResolveBy` — all keyed on `CardKind` (§2.3): `crates/double/src/class.rs:18`; skill text for the agent: `skills/double.md` (binary-owned, `crates/theuth/src/main.rs:1334`).

### 8.2 Why cells bypass nothing
- A cell run does not call `ToolRegistry::Invoke`, so `effective` is never evaluated, no `Approval` is created, no `ApprovalRequested` is published, no `CardKind` applies, and the owner's double has nothing to answer. The `shell` / `start` *tools* keep their policy exactly as today; an agent that wants to run something itself still goes through `Destructive → Ask`.
- The reverse must also hold: the cell RPC must not be callable by anything that can answer approvals on the owner's behalf. Today `app_call_tool` shows how to bind a press to *one* request id (`UserActivation.request_id == call.id`, `crates/tools/src/registry.rs:1079`); a cell press needs the equivalent: an engine-minted `run_id` per press so a replayed or duplicated RPC cannot run twice (46 §6.4's "request id was already used with different input", `crates/app/src/actor.rs:672`).

### 8.3 Two switches that exist for tools and must be decided for cells
- **Global / per-session approval bypass.** `approvals: false` (config) or a session / ancestor opting out rewrites `Ask`→`Allow` (`crates/tools/src/registry.rs:988`); `SetApprovals` is the runtime message. A "run without asking" mode is meaningless for cells (a press *is* the ask) — the design should say so, so nobody wires a "trust this session" shortcut to Run-all.
- **Subagent cap.** `SetCap` ceilings a subagent's tools by risk (`crates/tools/src/registry.rs:980`). A subagent cannot present cells (the block is attended-only, §10.1) but its *text* can contain a bash fence that renders as a cell in the parent's UI if it is relayed into a chat; relayed child text should not become runnable (it is `Principal`-less data from another agent: "the body is the other agent's text, no more trusted than a web page", guidance text at `crates/agent/src/frame.rs:63`).
- **Untrusted text → runnable code.** The chat renders *any* assistant text, including text that quotes web pages, tool output or `doc-member` blocks. If every ```bash fence became runnable, prompt-injected content would become a one-click command. 59 §11 row 1 and the `doc-member` label are the existing mitigations for *agent* behaviour; nothing today protects a *human click on rendered injected code*. This argues for an explicit opt-in marker from the model (G2) *and* a visible origin line on every cell (who wrote it, in which message/block).

## 9. Engine ↔ client (RPC, events, mesh, durability)


**Verdict for 171:** adding a user-facing run capability is mechanical on the wire — one trait method in `rpc::Api`, mirrored by hand in the UI's `Api` interface and `METHODS` list, plus ts-rs types — and the live path to every client (desktop, web, phone, TUI) already exists as `subscribe_events` (coalesced `Job*` events) and `subscribe_pty` (byte stream). Which engine runs it is decided by the **front door** (`forward::route`): a user session is *taken* by the engine the client is talking to; an agent desk's calls are forwarded to the owner.

### 9.1 The method registry (what a new RPC touches)
1. The jsonrpsee trait with doc comment per method, `#[method(name = "…", with_extensions)]` or `#[subscription(…)]`: `crates/rpc/src/api.rs:266`] (example: `cancel_job`), the PTY set at `crates/rpc/src/api.rs:291`], impls further down in the same file (`crates/rpc/src/api.rs:292`, 2nd match).
2. TS bindings: `just ts` runs `cargo test -p rpc --features ts export_bindings` and writes `bindings/*.ts` for every wire type plus `bindings/methods.json`, "the sorted list of every registered method name": `crates/rpc/src/export.rs:1`. New wire types must be added to the `export!(…)` list (`crates/rpc/src/export.rs:16`).
3. The UI `Api` interface (hand-written) and `METHODS` array, "Every request method name, sorted; `api.test.ts` checks it against `bindings/methods.json`": `crates/desktop/ui/src/rpc/api.ts:1240`, test `crates/desktop/ui/src/rpc/api.test.ts:7`. Evidence of the exact footprint of one new method: in the theuth-170 worktree `git diff origin/main -- crates/desktop/ui/src/rpc/api.ts` shows only two hunks — the `slack_manifest(): Promise<string>` line with its doc comment in the interface and the `'slack_manifest'` entry in `METHODS` (design 170 D1 added that RPC; main at this tree's base 6eba65b1 does not have it, `grep slack_manifest crates/desktop/ui/src/rpc/api.ts` is empty). A UI worker on stub bindings must also add the name to repo-root `bindings/methods.json` (knowledge `warnings/theuth-ui-api-test-reads-repo-root-bindings-methods-json`).
4. Guests/members: not on the guest list by default (`crates/link/src/conn.rs:538` — add nothing).
5. Other clients: the TUI keeps its own command enum per RPC (e.g. `pty_input` at `crates/tui/src/model.rs:863`); Windows/mac companions are Tauri shells over the same UI (design 134/149, not re-read here).

### 9.2 The live event path
- Engine side: the RPC `Bridge` actor subscribes to bus events (`AgentEvent`, approvals, …) and fans them out per connection: `crates/rpc/src/bridge.rs:181`, `crates/rpc/src/bridge.rs:187`. Client side: `subscribe_events(session, descendants)` — `crates/rpc/src/api.rs:2695`] — via `RpcClient.subscribe`, which "Survives reconnects" and is re-issued on every reconnect ("the server starts the stream over, so `onItem` sees its first item again"): `crates/desktop/ui/src/rpc/client.ts:111`, `crates/desktop/ui/src/rpc/client.ts:124`.
- Job events reduce into the session slice: `JobStarted` (attaches `{id, command, lines}` to the tool card with the same `call_id`), `JobOutput` (`pushChunk` into `lines`, handling `\r`), `JobScreen`, `JobIdle`, `JobFinished` (inline → drop): `crates/desktop/ui/src/store/reduce.ts:761`, `crates/desktop/ui/src/store/reduce.ts:771`, `crates/desktop/ui/src/store/reduce.ts:786`. Reducer test shows `'10%\r55%\ndone'` handled: `crates/desktop/ui/src/store/reduce.test.ts:515`. So a cell started as a **shell job with `call_id = <cell id>`** would already get its live tail rendered by the existing `ToolRunCard`-style attach logic *if* the card is a tool entry; for a cell fence the UI must read `slice.jobs`/the job's `lines` by cell id instead.
- PTY bytes ride a separate subscription (`subscribe_pty`, §5.6) with back-pressure: a lagging client gets a fresh `Reset` (ring of 256 chunks); events carry only the 500 ms coalesced screen rows.
- Two clients pressing Run: nothing in the job layer prevents it — `Start` mints a new `j{n}` per call (`crates/tools/src/jobs.rs:64`). The cell RPC needs an idempotency key (cell id + run counter) or a per-cell mutex in the engine (§13 G4).

### 9.3 The front door and "which machine runs it"
- Every session-mutating RPC first asks `forward::route`: "The owner is here → the call proceeds. Not here and a **user session** → the session is taken here (`TakeSession{reason: Write}`), then the call proceeds. Not here and an **agent desk** → the call is forwarded verbatim to the owner as JSON-RPC over `theuth/rpc/1`… 30 s": `crates/rpc/src/forward.rs:1`. `send_input` is the template: `crates/rpc/src/api.rs:3589`. Answers to approvals/asks are forwarded **never taken** (`crates/rpc/src/api.rs:2989`).
- A phone is only an RPC client: the `link` plugin "serve[s] them the RPC API over Noise" through a stateless relay (mode-0 conn), so a phone press runs on the *harness the phone is paired to* (or the session's owner after `route`): `crates/link/src/lib.rs:1`. Processes always live on the engine that owns the session; `jobs.engine` records it (`crates/tools/src/journal.rs:375`), and a result for a session that moved is queued in `harness_outbox` and shipped to the owner (§5.4).
- Other engines in the mesh and VMs: sandbox VMs are engines too (`sandbox_terminal(name)` gives a PTY job inside the VM, §5.6). So "run this cell on the sandbox, not on my Mac" is expressible today only by starting the job in a session that lives on the VM's engine — the design must decide whether a cell has a `host` option (it is the cognitive-load item "which machine" from the axes).
- Windows: PTY spawn uses `pwsh.exe`/`powershell.exe -NoLogo -Command` (`crates/platform/src/shell.rs:60`) and a Job Object instead of a process group (58 §0.4, comment in `setup()`), so a "bash" cell on a Windows engine means brush or WSL, not a login shell.

### 9.4 Durability summary (109 / 139)
- Cell runs are jobs; jobs are not durable (§5.5); the retained screen and log survive in the journal (`pty_screens` replicates since 139). Engine restart mid-run → `JobFinished{exit: lost}` → UI must flip the cell to "lost" (reducer test: `crates/desktop/ui/src/store/reduce.test.ts:1163`).
- Event delivery is at-most-once and lossy under flood (`JobOutput` doc: "the log file is the truth"): a reconnecting client should fetch the log tail (the job `log` path is in `JobStarted`; the UI has no log-read RPC for a job today — only `pty_screen` for PTYs and `artifact_read`/`read_file` for the agent). **Gap:** a `job_log(session, id, range)` read for pipe jobs (§13 G6).

### 9.5 Sizes and rates a live cell stream must respect
- `JobOutput` ≤ 1 event per 500 ms per job; `JobScreen` coalesced the same way; PTY byte stream through a 256-chunk broadcast ring; reader buffer 64 KiB (`crates/tools/src/pty.rs:69`); client falls behind → `Reset`.
- Reducer stores a job's lines in the session slice (`pushChunk`) — unbounded growth is a UI concern for a chatty cell; the existing tool-card tail is the model to copy (8 KiB engine tail per job, `crates/tools/src/jobs.rs:44`).
- `pty_screen` renders are limited to 4 concurrent snapshots engine-wide and answer `terminal busy` when exhausted (`crates/rpc/src/api.rs:278`) — many inline viewers polling `pty_screen` instead of subscribing would hit it; use `subscribe_pty` only.

## 12. Interpreter discovery today


**Verdict for 171:** the engine has *no* Python interpreter discovery for users (no `.venv`/uv/pyenv/conda logic), exactly one `PATH` lookup for CPython (sensors), a login-shell `PATH` probe, and a static project profiler that names `uv`/`poetry`/`pytest` without finding interpreters. The environment facts a cell chip needs (login shell, which `python3`, which `node`, which `bash`) must be computed fresh.

### 12.1 What exists
- **CPython on PATH** — `find_cpython()`: `python3`, then `python`, then Windows `py -3`; each verified with `--version` once per process and cached: `crates/agent/src/sensor/mod.rs:701`. Used only to run `# needs: cpython` sensors via a shim: `crates/agent/src/sensor/cpython.rs:20`. It reads the *engine's inherited* `PATH`, not the login-shell `PATH` — on macOS a GUI-launched engine often sees a short `PATH`, so this is a weaker answer than the one `shell` uses.
- **Login-shell PATH** — `platform::env::login_path` runs `$SHELL -l -i -c 'printf %s "$PATH"'` once (stdin null, own session, timeout), `tools.login_path` (default on) seeds each `shell` session's `PATH` from it: `crates/platform/src/env.rs:12`, `crates/tools/src/shell.rs:196`, state/cache `crates/tools/src/shell.rs:169`. Login shell choice: `$SHELL`, fallback `/bin/zsh` on macOS (`crates/tools/src/shell.rs:205` and the doc comment "fallback `/bin/zsh` on macOS"). **The engine therefore already knows the user's login shell and its PATH**; it does not expose them over RPC.
- **PTY shell** — `$SHELL -lc <command>` on Unix, `tools.pty_shell` override (`crates/platform/src/shell.rs:49`, config `crates/tools/src/lib.rs:516`). With Sky's login shell = zsh (axes file), a cell that is "bash" and runs through this path is run by **zsh -lc** unless the command itself is `bash -c …` — the exact PIPESTATUS / trailing-comment hazard from 10-15.
- **project_profile** (codeindex): reads manifests, lockfiles and task runners and never runs anything: `kind` (cargo|node|python|go|mixed), `package_manager` (`uv`, `poetry`, `pipenv`, `pip`, `bun`, `pnpm`…), `commands` (`uv run pytest`), `test_runner`: `crates/codeindex/src/profile.rs:1`, python detection `crates/codeindex/src/profile.rs:227` and the `run` prefix `crates/codeindex/src/profile.rs:249`. It does **not** look for `.venv/bin/python`, `pyenv`, `conda`, `mise`/`asdf` shims (the repo has `mise.toml`) or Node versions. A cheap addition for "which python for this cwd": check `<cwd>/.venv/bin/python`, `uv run`, `mise which python`.
- **Monty is always available** when the worker pool started (`open_pool` returns `None` with one warn otherwise: `crates/agent/src/repl.rs:178`).
- Autoresearch and sandbox: autoresearch shells out to `python3` for case runners (`crates/autoresearch/src/{cases,suite,hooks,world,custody}.rs` contain `python3`) but none discovers interpreters; sandbox VMs get their own distro Python (`crates/sandbox/examples/vm_spike.rs`). Not found: any Node/Deno/Bun *executable* discovery in `crates/` (a grep for `"deno"`, `"node"`, `"bun"`, `which node` hits mesh `nodes`, the `node` project kind and package-manager names in `codeindex/src/profile.rs`, and MCP launch config — none resolves an interpreter).

### 12.2 What the design must add (facts it can rely on)
- A single engine function `interpreters(cwd) -> [{kind, path, version, why}]` combining: login-shell `PATH` (already probed), `<cwd>/.venv`, `uv`, `pyenv`/`mise`, system `python3`, `bash` (macOS /bin/bash 3.2 vs brew bash), `zsh`, `node`; plus the always-present "monty (built-in)". It belongs beside `find_cpython` or in `platform::env` (§13 G5).
- Login shell zsh: the cell runner must not use `$SHELL -lc` for a ```bash cell; it should exec the chosen bash explicitly (and for macOS warn when the only bash is 3.2).

### 13.1 Risks noticed while mapping (not decisions)
- **Brush vs bash vs zsh.** Three different "bash"es are in play (§5.1, §12.1). A cell labelled `bash` must name which.
- **Two clients, one PTY.** The viewer resizes the PTY (`pty_resize`); two viewers fight (comment in `TerminalViewer.tsx`). Inline per-message viewers multiply this.
- **PTY budget.** 512 MiB ≈ 80 retained terminals engine-wide (`crates/tools/src/jobs.rs:62`); a long run-sheet with one PTY per cell exhausts it; one PTY per sheet is the natural unit (matches Sky's "create one new one, we will drive it collaboratively").
- **`doc_replace` by the agent** drops block ids → any per-block run state.
- **Streaming fence + Run.** A cell must not be runnable while `isIncomplete` or while the turn that wrote it still runs and may regenerate it (openui's button already disables on `isIncomplete`).
- **Context cost.** `<job_result>` text is capped by `max_tool_output_chars` with spill; PTY screens are 120×40 — a long `pulumi preview` needs the log, not the screen.
