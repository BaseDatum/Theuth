## 1. Surfaces macOS offers for an out-of-window companion

Context fact first: Apple's public macOS page now advertises **macOS 27 "Golden Gate"** ("enhanced Liquid Glass", a Siri app, Visual Intelligence on Mac) (https://www.apple.com/os/macos/, read 2026-10-07), and Apple's developer documentation already carries `macOS 27.0` availability badges (e.g. `NSStatusItem.expandedInterfaceDelegate`, see 1.1). So "macOS 26 Tahoe" is the *previous* release at the time of this recon; version notes below name the first macOS that has each API.

Reachability vocabulary used below: **Rust/objc2** = callable from the existing Tauri process via `objc2` + `objc2-app-kit` (theuth already links them: `crates/desktop/Cargo.toml:65-69`); **Swift-only** = the API is usable from Rust in principle (it is Objective-C-visible) but needs an Xcode-built target in practice; **extension** = must live in a separate app-extension bundle (`.appex`) with its own code signature.

### 1.1 Menu bar extra (NSStatusItem, SwiftUI MenuBarExtra, menu-bar Live Activities)

- **What/API.** `NSStatusBar.statusItem(withLength:)` creates an `NSStatusItem`; its `button` (an `NSStatusBarButton`) carries image/title/target-action; `menu` attaches a menu; `behavior`, `isVisible`, `length`, `autosaveName` are the remaining knobs; `view`, `popUpMenu`, `doubleAction` and friends are deprecated (https://developer.apple.com/documentation/appkit/nsstatusitem — topics list read via the docs JSON endpoint, 2026-10-07). SwiftUI's `MenuBarExtra` scene (macOS 13+) renders "a persistent control in the system menu bar"; its `.window` style (macOS 13+) "displays a popover-like window from the menu bar icon that contains standard controls"; an app that only shows in the menu bar "will be automatically terminated if the user removes the extra" and should set `LSUIElement = true` to hide from Dock/app switcher (https://developer.apple.com/documentation/SwiftUI/MenuBarExtra; https://developer.apple.com/documentation/swiftui/menubarextrastyle/window).
- **New in macOS 27:** `NSStatusItem.expandedInterfaceDelegate` / `expandedInterfaceSession` (macOS 27.0): "The delegate shows the expanded interface, such as an `NSWindow` positioned beneath the status item, in response to `statusItem(_:didBegin:)`, and dismisses the interface in response to `statusItemDidEndExpandedInterfaceSession(_:animated:)`"; status items with an `NSMenu` do not receive these callbacks (https://developer.apple.com/documentation/appkit/nsstatusitem/expandedinterfacedelegate). This is Apple's first sanctioned hook for a custom window hanging off a status item (before 27 every app rolled its own `NSPanel` positioned under `button.window.frame`). Only on macOS 27; unverified what the system does for the dismissal gesture on older releases.
- **HIG guidance (macOS platform section of "The menu bar").** "The menu bar's height is 24 pt." "Display a menu — not a popover — when people click your menu bar extra" unless the functionality "is too complex for a menu". "When necessary, the system hides menu bar extras to make room for app menus" and "if there are too many menu bar extras, the system may hide some"; "Avoid relying on the presence of menu bar extras" — "you can't be sure which other menu bar extras people have chosen to display or predict the location of your menu bar extra"; offer the same functionality elsewhere (Dock menu). Icons: template images (black + clear) so the system recolours them; prefer SF Symbols (https://developer.apple.com/design/human-interface-guidelines/the-menu-bar, section "Menu bar extras"; change log last entry June 9, 2025).
- **Live Activities in the menu bar (macOS 26).** `ActivityKit` availability is **iOS 16.1, iPadOS 16.1, Mac Catalyst 16.1 — no native macOS entry** (https://developer.apple.com/documentation/activitykit). Its overview says "On Mac, it appears in the Menu bar" and the companion article says Live Activities appear "on a paired Mac or Apple Watch" (https://developer.apple.com/documentation/activitykit/displaying-live-data-with-live-activities). Apple's user-facing support page and third-party how-tos confirm the mechanism: the Mac shows Live Activities **from a nearby iPhone** (same Apple account, iPhone Mirroring set up, Wi-Fi + Bluetooth on; System Settings › Notifications › "Allow Live Activities from iPhone") and "Mac apps aren't allowed to show them" (https://support.apple.com/en-us/122868; https://www.idownloadblog.com/2025/06/28/how-to-use-live-activities-mac/). **Conclusion: a Mac app cannot post a menu-bar Live Activity; only an iOS app on a paired iPhone can.** theuth's iOS link client could in principle start one (ActivityKit on iOS) and have it mirrored to the Mac menu bar, but that routes through the phone; unverified whether a Mac Catalyst build can post one on macOS 26/27 (the Catalyst badge exists, the Mac menu-bar mention does not say which apps).
- **Limits.** One 24 pt strip, system may hide the item; no per-item width guarantee; a status-item "menu" cannot host arbitrary views except through `NSMenuItem.view`; a `.window`-style extra is an ordinary popover-like window (it takes key focus when shown).
- **Reachable from Tauri 2 / Rust?** Yes for the icon + menu: Tauri's `tray-icon` feature is already on (`Cargo.toml:312`, `tauri-plugin-positioner` with `tray-icon` at `Cargo.toml:318`). A custom window under the item is what theuth would build with an `NSPanel` (1.2); the macOS 27 `expandedInterfaceDelegate` is an Objective-C protocol, so reachable from `objc2` with a `declare_class!`-style delegate, but no Rust crate wraps it yet (unverified beyond the docs).

### 1.2 Non-activating floating panels (NSPanel, tauri-nspanel)

- **What/API.** `NSPanel` is "a special kind of window that typically performs a function that is auxiliary to the main window"; configuration is `isFloatingPanel`, `becomesKeyOnlyIfNeeded`, `worksWhenModal` plus the style-mask bit `NSWindowStyleMaskNonactivatingPanel` ("a panel … that does not activate the owning app") (https://developer.apple.com/documentation/appkit/nspanel; https://developer.apple.com/documentation/appkit/nswindow/stylemask-swift.struct/nonactivatingpanel). `becomesKeyOnlyIfNeeded`: "If the panel is a non-activating panel, then it becomes key only if the hit view returns `true` from `needsPanelToBecomeKey`. This way, a non-activating panel can control whether it takes keyboard focus" (https://developer.apple.com/documentation/appkit/nspanel/becomeskeyonlyifneeded). `isFloatingPanel` docs give Apple's own criteria for when floating is appropriate: small enough not to obscure what is behind it, mouse-oriented ("doesn't become the key window or becomes so only when needed"), needs to stay visible while the user works elsewhere, and "hides when the app is deactivated (the default behavior for panels)" (https://developer.apple.com/documentation/appkit/nspanel/isfloatingpanel).
- **Levels.** `NSWindow.Level` constants, lowest to highest: `normal`, `floating`, `submenu`/`tornOffMenu`, `modalPanel`, `mainMenu`, `statusBar`, `popUpMenu`, `screenSaver` (the list also names `dock`); "even the bottom window in a level will obscure the top window of the next level down" (https://developer.apple.com/documentation/appkit/nswindow/level-swift.struct). theuth's island uses `NSStatusWindowLevel` = 25 (`crates/desktop/src/island/macos.rs:28-29`) and the point-and-say overlays use popup-menu level (`crates/desktop/src/point/macos.rs:1`).
- **Collection behaviour.** `NSWindow.CollectionBehavior` (macOS 10.5+) groups: Spaces (`canJoinAllSpaces`, `moveToActiveSpace`), Mission Control (`stationary`), `managed`/`transient`, full screen (`fullScreenPrimary`, `fullScreenAuxiliary`, `fullScreenNone`, `fullScreenAllowsTiling`, `fullScreenDisallowsTiling`), Stage Manager (`primary`, `auxiliary`, `canJoinAllApplications` — mutually exclusive), cycling (`participatesInCycle`, `ignoresCycle`) (https://developer.apple.com/documentation/appkit/nswindow/collectionbehavior-swift.struct). `fullScreenAuxiliary` is what lets a panel show over another app's full-screen Space; theuth sets `CanJoinAllSpaces | FullScreenAuxiliary | Stationary` on the island (`island/macos.rs:40-44`).
- **tauri-nspanel (ahkohd, MIT / MIT-or-Apache-2.0).** Current line is `tauri-nspanel = "2.1"` on crates.io (branch `v2.1`): "Create panels with PanelBuilder API or convert existing windows", "Mouse tracking with enter, exit, and move events", panel events, "Thread-safe operations handled on main thread"; showcase includes Cap, screenpipe, Handy, Overlayed, EcoPaste, Coco, Asyar (https://github.com/ahkohd/tauri-nspanel, README on branch v2.1). The older `v2` branch (what theuth pins: `Cargo.toml:326` `branch = "v2"`) exposes `WebviewWindowExt::to_panel()` ("Only call the `to_panel()` method once on a webview window"), `ManagerExt::get_webview_panel`, a `panel_delegate!` macro for `NSWindowDelegate` callbacks, and warns that `close()` does not release a panel unless `set_released_when_closed(true)` (https://raw.githubusercontent.com/ahkohd/tauri-nspanel/v2/README.md). The v2 API still speaks the deprecated `cocoa` crate types (`island/macos.rs:33` comment: "`tauri-nspanel` speaks the old `cocoa` types"), so theuth already carries `#[allow(deprecated)]`.
- **What theuth does today with it** (file:line): island swizzled with style mask `NonactivatingPanel | Resizable` (`island/macos.rs:25-27`), status level, all-Spaces + full-screen-auxiliary + stationary, `set_hides_on_deactivate(false)` because "ours is an Accessory app that is rarely active" (`:45-46`), `set_becomes_key_only_if_needed(true)` so "typing keeps going to the meeting app" (`:47-49`), never ordered out — "WebKit throttles a webview whose window is not on screen" so hidden = alpha 0 + mouse-transparent (`:51-54`, `:59-62`), `sharingType = .none` capture exclusion (`:64-67`), notch placement + screen-change notification (`:10-11`, `:55`). The plugin is registered on every desktop OS with a per-OS island backend (`crates/desktop/src/lib.rs:274-276`; `island/mod.rs:3`).
- **Limits of the webview-in-NSPanel route.** (1) Key focus is binary per window: a webview that needs typing must make the panel key, and `needsPanelToBecomeKey` is decided per hit view — theuth routes this by hand (`island_resign_key`, `island/macos.rs:48`). (2) A non-activating panel still steals keyboard focus from the frontmost app while key — the HIG expectation is that panels are mouse-oriented. (3) Vibrancy/glass of the panel chrome is `NSVisualEffectView`-level only (see 1.10). (4) WebKit throttling when off-screen (theuth's workaround above). (5) The plugin API is single-maintainer and tracks Tauri's internal window types.
- **Reachable from Tauri 2 / Rust?** Yes — this is the one surface theuth already ships natively from Rust.

### 1.3 Edge-docked shelf / notch windows

How shipping apps place an out-of-window surface (all are ordinary borderless `NSPanel`/`NSWindow`s positioned by the app; macOS has no "dock to edge" API):

- **Notch-anchored (boring.notch, NotchNook, Notchmeister, theuth's island).** Geometry comes from `NSScreen.safeAreaInsets` (macOS 12.0+): "On some Macs, the insets reflect the portion of the screen covered by the camera housing" (https://developer.apple.com/documentation/appkit/nsscreen/safeareainsets). theuth already does exactly this: `island_place` finds the screen with `safeAreaInsets().top > 0`, centres a 440 pt panel on it with the top at the screen top (content under the bezel hidden), else centres under the menu bar of the primary screen via `visibleFrame`; it keys a per-screen-configuration position memory on the sorted screen frames and re-places on `NSApplicationDidChangeScreenParametersNotification` (`crates/desktop/src/island/macos.rs:109-144`, `:10`, `:55`). boring.notch (TheBoredTeam) is **GPL-3.0** — techniques only, never open the clone into theuth (https://github.com/TheBoredTeam/boring.notch, licence badge in the repo sidebar). Notchmeister (chockenberry) is **BSD-3-Clause** (https://github.com/chockenberry/Notchmeister). NotchNook is closed-source, subscription (US$2/month after relaunch), 48-hour trial (https://getnotchnook.com/).
- **Drag shelves (Yoink, Dropover).** Yoink (closed source; macOS 10.13+) offers three placements: "appear at the screen edge immediately when a drag starts, appear only when the pointer approaches the edge, or appear at the mouse cursor", with per-app exclusions and a manual keyboard shortcut; Dropover (closed source; macOS 13.0+) summons its shelf with a **mouse-shake mid-drag** gesture or a held modifier (Shift default; Command/Control selectable) so it "appears wherever the drag happens to be", and also accepts drops on its menu bar icon or on the notch (https://atriens.com/learn/dropover-vs-yoink/; https://daringfireball.net/linked/2026/05/15/dropover). Both work "across full-screen apps and multiple Spaces" (https://www.notchspace.com/blog/dropover-vs-yoink-mac-shelf) — i.e. `canJoinAllSpaces | fullScreenAuxiliary` panels (1.2).
- **Launcher bars (Spotlight, Raycast, Alfred).** Closed source (Raycast's extensions are open, its app is not; Alfred is closed; Spotlight is Apple's). The commonly reproduced shape is a centred, non-activating, key-when-shown panel at a fixed fraction of screen height on the screen with the mouse, dismissed on resign-key/Esc; ahkohd's `tauri-macos-spotlight-example` and `tauri-plugin-spotlight` (both linked from the tauri-nspanel README) reproduce it in Tauri (https://raw.githubusercontent.com/ahkohd/tauri-nspanel/v2/README.md, "Related"). Exact placement rules of Raycast/Alfred: unverified (closed source).
- **PopClip** (closed source) appears next to a text selection; it needs the Accessibility permission to read the selection and observes mouse-up system-wide. theuth's point-and-say already has the ingredients from Rust: non-activating overlay panels at popup-menu level on every Space (`crates/desktop/src/point/macos.rs:1-4`), `NSEvent` access (`point/macos.rs:7`) and AX hit-testing in the engine (knowledge `facts/macos-accessibility-hit-test-chromium-and-frontmost-2026-10-04`). PopClip's exact mechanism: unverified (closed source).
- **Patterns worth naming** (all implementable with NSPanel + NSScreen + tracking areas): hover-reveal at an edge = a 1–4 px-wide invisible panel or a global mouse-moved monitor near `NSScreen.frame` edges; auto-hide = order out / alpha 0 after a resign-key or mouse-exit timer (theuth keeps alpha-0 panels ordered in because WebKit throttles off-screen webviews, `island/macos.rs:51-54`); multi-display = per-screen placement keyed on the screen set (theuth's `rect_key`, `:123-126`). tauri-nspanel 2.1 adds "mouse tracking with enter, exit, and move events" on the panel itself (https://github.com/ahkohd/tauri-nspanel).
- **HIG.** No HIG page covers edge-docked or notch windows; the applicable guidance is the `isFloatingPanel` criteria (1.2) and the full-screen guidance that the menu bar hides in full screen (https://developer.apple.com/design/human-interface-guidelines/the-menu-bar, macOS section). macOS version: `safeAreaInsets` macOS 12.0; the rest is 10.x-era AppKit.
- **Reachable from Tauri 2 / Rust?** Yes — all of it is `NSScreen`/`NSPanel` work theuth already does in Rust.

### 1.4 Notifications (UNUserNotificationCenter, Tauri plugin, Focus)

- **API and versions.** `UNNotificationCategory` (macOS 10.14+) defines actionable notifications: "notifications that have action buttons the user can select"; register with `UNUserNotificationCenter.setNotificationCategories(_:)` and reference by `categoryIdentifier` (https://developer.apple.com/documentation/usernotifications/unnotificationcategory). `UNTextInputNotificationAction` (macOS 10.14+): "the system displays controls for the user to enter or dictate the text content" and returns it in the response (https://developer.apple.com/documentation/usernotifications/untextinputnotificationaction). `threadIdentifier` (macOS 10.14+) groups notifications visually: "assign the same thread identifier string to all notifications that you want to group together" (https://developer.apple.com/documentation/usernotifications/unmutablenotificationcontent/threadidentifier). `UNNotificationInterruptionLevel` (macOS 12.0+): `passive`, `active`, `timeSensitive`, `critical` (https://developer.apple.com/documentation/usernotifications/unnotificationinterruptionlevel). `.timeSensitive`: "presents the notification immediately, lights up the screen, can play a sound, and breaks through system notification controls" such as Notification Summary and Focus; "The user can turn off the ability for time sensitive notification interruptions" (https://developer.apple.com/documentation/usernotifications/unnotificationinterruptionlevel/timesensitive). `.provisional` authorization (macOS 10.14+): "post noninterrupting notifications provisionally to the Notification Center" without an upfront prompt (https://developer.apple.com/documentation/usernotifications/unauthorizationoptions/provisional). Critical alerts need the `com.apple.developer.usernotifications.critical-alerts` entitlement, granted by Apple on request: with it the app "can request `criticalAlert` authorization" and the sound plays "even when the app is locked, muted, or a person uses Do Not Disturb" (https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.usernotifications.critical-alerts).
- **Time-sensitive outside the App Store.** The time-sensitive capability is an App ID capability (`com.apple.developer.usernotifications.time-sensitive`) added in Xcode's Signing & Capabilities; Apple's entitlement reference page for it did not resolve at the documented path during this recon (HTTP 404 at the docs JSON endpoint) — **unverified** whether a Developer ID-signed, notarized non-App-Store app may carry it (Apple's capability matrix lists which capabilities Developer ID profiles may include; not checked within the time box). Critical alerts are explicitly request-only.
- **Focus.** `INFocusStatusCenter` (macOS 12.0+) exposes `requestAuthorization`, `authorizationStatus`, `focusStatus` (is the user in a Focus) (https://developer.apple.com/documentation/intents/infocusstatuscenter). `SetFocusFilterIntent` (macOS 13.0+, App Intents) lets a Focus mode configure the app ("adapt your app's behavior when Focus changes") and is surfaced in System Settings › Focus › Focus Filters (https://developer.apple.com/documentation/appintents/setfocusfilterintent). Both require the app to be a signed bundle; Focus filters additionally need an App Intents extension or in-app intent, i.e. Swift.
- **What the official Tauri plugin does on macOS.** `tauri-plugin-notification` v2 desktop backend is `notify-rust` (`Notification::new()`, `summary`, `body`, `icon`; on macOS it calls `notify_rust::set_application(bundle id)` and, in dev, impersonates `com.apple.Terminal`) (https://raw.githubusercontent.com/tauri-apps/plugins-workspace/v2/plugins/notification/src/desktop.rs). The guest-JS API documents: `ActionType` — "Only used on mobile"; `Action` — "Only used on mobile"; `Schedule` — "Scheduling is only supported on mobile; desktop notifications are always shown immediately" (https://raw.githubusercontent.com/tauri-apps/plugins-workspace/v2/plugins/notification/guest-js/index.ts). A Tauri discussion confirms "actions are only supported on mobile platforms" and asks for a Swift workaround (https://github.com/orgs/tauri-apps/discussions/14781). So from the official plugin theuth gets title/body/sound only — no buttons, no text input, no interruption level, no thread grouping, no click-to-route (theuth pins it at `Cargo.toml:315`).
- **A community plugin closes most of the gap without a separate app.** `Choochmeque/tauri-plugin-notifications` (MIT, `0.5.0-rc.14`, `rust-version 1.93`) ships a **Swift backend through `swift-bridge`** on macOS (`[target.'cfg(target_os = "macos")'.dependencies] swift-bridge`, `swift-bridge-build` in build-dependencies) and claims "macOS: Native notification center integration", interactive actions with text input, grouping with summary, pending/active management, APNs on macOS behind a `push-notifications` feature; `default-features = false` turns off `notify-rust` to use the native backend (https://raw.githubusercontent.com/Choochmeque/tauri-plugin-notifications/main/README.md; https://raw.githubusercontent.com/Choochmeque/tauri-plugin-notifications/main/Cargo.toml). Not verified: whether its macOS backend sets interruption levels or `threadIdentifier`, and whether it builds in theuth's toolchain (swift-bridge needs the Xcode toolchain at build time — the same requirement the `screencapturekit` crate imposes).
- **Precondition for any UNUserNotificationCenter use:** the process must be a signed `.app` bundle with a bundle identifier (the framework refuses to run from a bare executable); in `tauri dev` the official plugin works around this by impersonating Terminal (source above). Developer ID + notarization is sufficient; the App Store is not required (the critical-alerts entitlement is the only request-gated one; time-sensitive: see above).
- **Reachable from Tauri 2 / Rust?** Title/body: yes today. Actions, text input, interruption levels, thread grouping, Focus status: need `objc2-user-notifications` bindings or a Swift bridge inside the same `.app` (no separate executable required); Focus *filters* need App Intents (Swift). None of this needs an app extension except a Notification Content extension for custom notification UI (not needed for buttons).

### 1.5 WidgetKit on macOS

- **What/versions.** WidgetKit: macOS 11.0+ (iOS 14) — "On Mac, people put native Mac app widgets on the desktop and in Notification Center. Additionally, people place iPhone widgets in locations like a Mac desktop and Notification Center" (https://developer.apple.com/documentation/widgetkit). Desktop placement arrived with macOS 14 Sonoma (the WidgetKit overview's phrasing; release-note version not re-verified). Interactive widgets: "Widgets and Live Activities can include buttons and toggles to offer specific app functionality without launching the app" — sizes systemSmall/Medium/Large/ExtraLarge(+Portrait); buttons/toggles run **App Intents** (`Button(intent:)`, `Toggle(intent:)`) in the widget extension (https://developer.apple.com/documentation/widgetkit/adding-interactivity-to-widgets-and-live-activities). Controls (Control Center / menu bar buttons driven by App Intents) are also WidgetKit ("Controls appear in Control Center or as menu bar items"), same source.
- **Refresh budget.** "WidgetKit renders the views on your behalf in a separate process … your widget extension is not continually active, even if the widget is onscreen"; the daily budget for a frequently viewed widget is "typically … from 40 to 70 refreshes", "roughly … every 15 to 60 minutes"; reloads are free (not counted) while "The widget's containing app is in the foreground"; the app can call `reloadAllTimelines()` when data changes and WidgetKit push notifications exist as a supplement (https://developer.apple.com/documentation/widgetkit/keeping-a-widget-up-to-date). A widget is therefore a slow glance (minutes), not a live agent-state surface.
- **Packaging.** A widget is an **app extension** (`.appex` inside `Contents/PlugIns/`) built from a Swift/SwiftUI target with its own bundle id, entitlements and signature, sharing data with the host via an App Group container. HIG: https://developer.apple.com/design/human-interface-guidelines/widgets.
- **Reachable from Tauri 2 / Rust?** No in-process route: the UI must be SwiftUI in a separate extension process. Shipping it inside a Tauri-built `.app` = adding the `.appex` to the bundle and signing it (see §3(d)).

### 1.6 App Intents / Shortcuts / Spotlight actions / Services menu

- **App Intents** (macOS 13.0+): "Make content and actions discoverable by Apple Intelligence and support system experiences like Siri, Spotlight, Shortcuts, and widgets"; intents, entities and enums are Swift types the compiler indexes at build time (https://developer.apple.com/documentation/appintents). Focus filters (1.4) are App Intents too.
- **Spotlight actions (macOS 26 Tahoe) — confirmed.** WWDC25 session 260 "Develop for Shortcuts and Spotlight with App Intents": "This year, you can now run actions from your app directly from Spotlight on Mac! Your apps can show actions in Spotlight by adopting App Intents, just like what you do for Shortcuts"; the parameter summary drives the Spotlight UI, and actions may run in the background or open the app (https://developer.apple.com/videos/play/wwdc2025/260/). The same session brings personal Automations (folder, external-drive, time-of-day triggers) to the Mac. macOS 27 adds "Ask Siri" as a Spotlight top hit and Siri taking actions in apps (https://www.apple.com/os/macos/).
- **Services menu** (classic AppKit, any macOS): an app advertises services in `Info.plist` (`NSServices`) and `NSApplication.registerServicesMenuSendTypes(_:returnTypes:)` lets responders consume them: "a menu item is added for each service provider that can accept one of the specified sendTypes" (https://developer.apple.com/documentation/appkit/nsapplication/registerservicesmenusendtypes(_:returntypes:)). Services are plist + an Objective-C-visible method on a registered object, so reachable from `objc2`; they appear under App › Services and in context menus system-wide and can carry a keyboard equivalent.
- **Reachable from Tauri 2 / Rust?** Services: yes (plist + objc2). App Intents / Shortcuts / Spotlight actions / Focus filters: **Swift-only** (the framework relies on Swift macros/compile-time metadata; there is no Objective-C surface), either in the main app binary (requires the app to be a Swift target or to link a Swift static library that contains the intents and is built with Xcode's metadata extraction — unverified for a Rust-linked binary) or in an App Intents extension (`.appex`).

### 1.7 Global hotkeys

- **Carbon `RegisterEventHotKey`** (still the only non-deprecated-in-practice registration API): sindresorhus/KeyboardShortcuts, which wraps it, states "Most of the Carbon APIs were deprecated years ago, but there are some left that Apple never shipped modern replacements for. This includes registering global keyboard shortcuts", and answers "Does this package cause any permission dialogs? No." — it is "fully sandboxed and Mac App Store compatible", macOS 10.15+ (https://raw.githubusercontent.com/sindresorhus/KeyboardShortcuts/main/readme.md). A registered hot key needs a key code plus modifiers — modifier-only chords (double-tap Option, as One uses) cannot be expressed.
- **`CGEvent.tapCreate`** (macOS 10.4+): "Event taps receive key up and key down events if one of the following conditions is true: The current process is running as the root user. Access for assistive devices is enabled" — i.e. the Accessibility (`AXIsProcessTrusted`) permission; a tap can observe *and* swallow events (https://developer.apple.com/documentation/coregraphics/cgevent/tapcreate(tap:place:options:eventsofinterest:callback:userinfo:); https://developer.apple.com/documentation/applicationservices/1460720-axisprocesstrusted). `CGPreflightListenEventAccess()` / `CGRequestListenEventAccess()` (macOS 10.15+) preflight the Input Monitoring TCC class that listen-only keyboard taps fall under (https://developer.apple.com/documentation/coregraphics/cgpreflightlisteneventaccess()). Which of the two prompts (Accessibility vs Input Monitoring) a listen-only `flagsChanged` tap triggers on macOS 26/27: **unverified** here; the conservative reading of Apple's text is Accessibility.
- **`NSEvent.addGlobalMonitorForEvents(matching:handler:)`** (macOS 10.6+): observe-only — "you can only observe the event; you cannot modify or otherwise prevent the event from being delivered"; "Key-related events may only be monitored if accessibility is enabled or if your application is trusted for accessibility access"; `flagsChanged` is in the monitorable list, so a **double-tap-Option detector is possible with a global monitor + Accessibility trust, without a CGEventTap** (https://developer.apple.com/documentation/appkit/nsevent/addglobalmonitorforevents(matching:handler:)). Whether `flagsChanged` alone is exempt from the trust requirement: unverified (Apple's sentence says "key-related events").
- **`tauri-plugin-global-shortcut`** wraps the `global-hotkey` crate, whose macOS backend is Carbon `RegisterEventHotKey`/`InstallEventHandler` (`src/platform_impl/macos/mod.rs` imports exactly those symbols) and requires "an event loop … running on the main thread" (https://raw.githubusercontent.com/tauri-apps/global-hotkey/dev/src/platform_impl/macos/mod.rs; https://raw.githubusercontent.com/tauri-apps/global-hotkey/dev/README.md). Consequences: key+modifier chords only, no modifier-only chords, no hold/double-tap detection, no per-app exclusions; the chord is swallowed in every app while registered. theuth already carries this plugin (`Cargo.toml:316`) and a Carbon voice key (design 96), and its point-and-say code already reads `NSEvent` from Rust (`crates/desktop/src/point/macos.rs:7`).
- **Reachable from Tauri 2 / Rust?** All three mechanisms are C/Objective-C APIs: yes via `objc2-app-kit` (`NSEvent`), `core-graphics`/`objc2-core-graphics` (event taps) and Carbon FFI. The permission prompt is the cost, not the language.

### 1.8 Speech

- **`SFSpeechRecognizer`** (macOS 10.15+): one language per recognizer, "For some languages, the recognizer might require an Internet connection", `isAvailable`, authorization via `requestAuthorization` with `NSSpeechRecognitionUsageDescription` (+ `NSMicrophoneUsageDescription` for live audio) (https://developer.apple.com/documentation/speech/sfspeechrecognizer).
- **`SpeechAnalyzer` + `SpeechTranscriber`** (macOS 26.0+, Swift-only `AsyncSequence` API): the analyzer "Holding associated modules, Accepting audio speech input, Controlling the overall analysis"; `SpeechTranscriber` is "appropriate for normal conversation and general purposes", on-device models checked with `isAvailable`/`supportedLocales`/`installedLocales`, fallback `DictationTranscriber` (https://developer.apple.com/documentation/speech/speechanalyzer; https://developer.apple.com/documentation/speech/speechtranscriber). Swift concurrency API — **Swift-only** in practice.
- **`AVSpeechSynthesizer`** (macOS 10.14+): utterance queue, pause/stop/resume, voice selection (https://developer.apple.com/documentation/avfaudio/avspeechsynthesizer). Objective-C-visible → reachable from `objc2-avf-audio`.
- **Permissions.** Microphone (TCC, prompt on first capture) and Speech Recognition (TCC, `SFSpeechRecognizer.requestAuthorization`); both need usage-description strings in `Info.plist` or the process is killed on access. One asks for Microphone "to talk to One" (https://getone.one/). theuth's existing Talk mode uses its own engine-side STT/TTS (`lib/speech.ts` output node per the UI code map), so Apple speech is optional here.

### 1.9 Screen context (ScreenCaptureKit, Accessibility API, TCC)

- **ScreenCaptureKit** (macOS 12.3+; `SCContentSharingPicker` macOS 14.0+): "Use `SCContentSharingPicker`, the system screen-sharing control, as the recommended approach for letting people select content sources"; "Request screen recording permission from the person before capturing content … add a `NSScreenCaptureUsageDescription` key" (https://developer.apple.com/documentation/screencapturekit; https://developer.apple.com/documentation/screencapturekit/sccontentsharingpicker). The picker route avoids the Screen Recording TCC grant for user-chosen content; a silent capture of "what is on screen" needs the grant (`CGPreflightScreenCaptureAccess()` / `CGRequestScreenCaptureAccess()`, macOS 10.15+, https://developer.apple.com/documentation/coregraphics/cgpreflightscreencaptureaccess()). theuth's knowledge base records the `screencapturekit` Rust crate (swift-bridge based) and its build requirements from spike 121 — it is reachable from Rust but drags the Xcode toolchain into the build.
- **Accessibility API.** `AXUIElementCopyElementAtPosition` (macOS 10.2+) "does hit-testing based on window z-order" and, with the system-wide element, "the position test is not restricted to a particular application"; it returns `kAXErrorNotImplemented` when "The process does not fully support the accessibility API" (https://developer.apple.com/documentation/applicationservices/1462077-axuielementcopyelementatposition). Requires the Accessibility (trusted client) grant: `AXIsProcessTrusted` (https://developer.apple.com/documentation/applicationservices/1460720-axisprocesstrusted). theuth's point-and-say already uses this path and has recorded the Chromium `AXManualAccessibility` and frontmost-app pitfalls (knowledge `facts/macos-accessibility-hit-test-chromium-and-frontmost-2026-10-04`).
- **What One asks for** (verbatim from its site): "allow Microphone (to talk to One), Accessibility (so the shortcut works in every app) and Screen Recording (for the screenshot sent with each request). macOS may also ask to let One control your terminal app" — i.e. four TCC classes: Microphone, Accessibility, Screen Recording, Automation (Apple Events to the terminal); requires macOS 13+ (https://getone.one/). Note One attributes the *shortcut* to Accessibility — consistent with a modifier-only (double-tap Option) chord needing an event monitor/tap rather than Carbon.
- **TCC mechanics relevant to a companion.** Grants are per code-signing identity (bundle id + Team ID); a helper executable or XPC service inside the `.app` gets its own prompts unless it shares the responsible-process attribution (launched by the app, same bundle) — Apple's `LSUIElement` helpers inherit the host's TCC attribution when spawned by it; a LaunchAgent does not (it is its own responsible process). Unverified in detail within this time box; flag for the design.
- **Reachable from Tauri 2 / Rust?** Yes for both (C APIs); theuth already ships the AX path from Rust.

### 1.10 Liquid Glass (macOS 26) and webview-drawn panels

- **HIG "Materials".** Two material families: Liquid Glass and standard materials. "Liquid Glass forms a distinct functional layer for controls and navigation elements — like tab bars and sidebars — that floats above the content layer"; "Don't use Liquid Glass in the content layer"; "Use Liquid Glass effects sparingly … Limit these effects to the most important functional elements"; two variants, `regular` ("blurs and adjusts the luminosity of background content"; use it for text-heavy elements such as "alerts, sidebars, or popovers") and `clear` ("highly translucent", for media backgrounds, consider a 35 % dark dimming layer); appearance changes with the user's Liquid Glass preference and Reduce Transparency / Increase Contrast. The macOS section separately keeps the standard-material/vibrancy guidance (behind-window vs in-window blending) (https://developer.apple.com/design/human-interface-guidelines/materials).
- **APIs.** `NSGlassEffectView` (macOS 26.0): `contentView`, `cornerRadius`, `style`, `tintColor`, `effectIsInteractive` (https://developer.apple.com/documentation/appkit/nsglasseffectview); SwiftUI `glassEffect(_:in:isEnabled:)` (page did not resolve at the docs JSON endpoint — unverified here, present in the WWDC25 material). Pre-26 material: `NSVisualEffectView` (macOS 10.10+): "AppKit creates visual effect views automatically for window titlebars, popovers, and source list table views"; custom views must opt into vibrancy via `allowsVibrancy` and "Vibrancy works best when your custom views contain grayscale content" (https://developer.apple.com/documentation/appkit/nsvisualeffectview).
- **Webview panel implications.** A WKWebView cannot *be* glass: the glass/vibrancy is a native backdrop view behind a transparent webview. Tauri's `window-vibrancy` crate (tauri-apps) does exactly this: `apply_vibrancy(window, NSVisualEffectMaterial::HudWindow, …)` on macOS 10.10+, and since its macOS-26 work `apply_liquid_glass(window, LiquidGlassOptions::new(NSGlassEffectViewStyle::Clear).radius(26.0).opaque(false).interactive(true))` where `.interactive` "requires macOS 27 or newer and is silently ignored on macOS 26"; it can reparent a `WKWebView` into the glass view's `contentView`; Tauri needs `"transparent": true` on the window and `html, body { background: transparent }` (https://raw.githubusercontent.com/tauri-apps/window-vibrancy/dev/README.md). theuth already builds the island with Tauri's `macos-private-api` feature for a transparent window (`Cargo.toml:312`). What the webview cannot get: per-element glass (buttons/pills individually refracting), the system's interactive glass response on controls, vibrancy-blended text (`allowsVibrancy` on CSS text is impossible — text is rasterised by WebKit), and automatic adaptation to Reduce Transparency unless the UI polls `prefers-reduced-transparency`.
- **Reachable from Tauri 2 / Rust?** Backdrop glass/vibrancy: yes (window-vibrancy, or objc2 directly). Per-control glass and system control styling: Swift/AppKit views only.

## 2. Keyboard-first and undo conventions on macOS

- **HIG "Keyboards" — custom shortcuts.** "Define custom keyboard shortcuts for only the most frequently used app-specific commands"; modifier guidance: "Prefer the Command key as the main modifier", Shift "as a secondary modifier", "Use the Option modifier sparingly for less-common commands or power features", and "**Avoid using the Control key as a modifier.** The system uses Control in many systemwide features and shortcuts, like moving focus or capturing screenshots"; "If you must use a modifier other than Command, prefer using it only with the alphabetic characters" (keyboard-layout safety); list modifiers in the canonical order; "don't repurpose standard keyboard shortcuts for custom actions" (https://developer.apple.com/design/human-interface-guidelines/keyboards, sections "Custom keyboard shortcuts" and "Standard keyboard shortcuts"). The page also lists system-reserved input-source chords (Control-Space, Control-Option-Space, [modifier]-Command-Space). Implication for a companion: single-letter, unmodified keys (j/k/e/1/2/3) are legitimate only **inside a focused panel** of your own; a system-wide trigger should be one Command-based chord or a modifier gesture, not Control.
- **The j/k + single-letter grammar is an established convention, not a macOS one.** Gmail (keyboard shortcuts on): `j`/`k` older/newer conversation, `e` archive, `z` undo last action, `[`/`]` archive and go previous/next, `o`/Enter open, `u` back to list, `?` help, `g+…` go-to chords, `/` search (https://support.google.com/mail/answer/6594). Superhuman mirrors it: `E` Mark Done (archive), `Shift+E` Mark Not Done, `H` Remind Me, `Z` Undo, `/` Search, `?` Shortcuts, `⌘K` command palette, `[`/`]` act-and-move (https://nickgray.net/superhuman/ — third-party transcription; Superhuman's own help page is a JS wall for this reader, unverified). Things 3 and Linear use the same vocabulary (↑/↓ or j/k, Enter open, `⌘K` palette); not re-verified within the time box. One's site uses exactly this grammar: "J and K move between cards. E clears one", answers by `1/2/3`, "Every answer waits 2 seconds. Press Escape to undo" (https://getone.one/).
- **Undo affordances.** Gmail's "Undo Send" is a *delayed commit*: default 5 s, configurable to 10/20/30 s; the action is shown as a toast ("Message sent · Undo") during the window (https://blog.google/products-and-platforms/products/gmail/how-to-unsend-email-gmail/; https://techweez.com/2026/07/29/gmail-undo-send-change-time-limit/). HIG "Undo and redo": "Help people predict the results of undo and redo" (name the action in the menu item, e.g. "Undo Typing"), "Show the results of an undo or redo" (scroll/highlight what came back — people repeat an undo that looks like it did nothing), "Let people undo multiple times", don't add arbitrary limits (https://developer.apple.com/design/human-interface-guidelines/undo-and-redo). For a menu bar/panel app the macOS-native expression is an Edit › Undo menu item wired to `NSUndoManager` with ⌘Z (available even for an `LSUIElement` app while its panel is key) plus the Esc-within-window pattern One uses for *irreversible* sends (a delayed-commit toast, not an undo stack).
- **VoiceOver / accessibility for a custom panel.** HIG Accessibility: "Describe your app's interface and content for VoiceOver"; support "Full Keyboard Access, Pointer Control, and switch-control"; Assistive Access guidance: "Always ask for confirmation twice whenever people perform an action that's difficult to recover from" (https://developer.apple.com/design/human-interface-guidelines/accessibility). Concretely for the two build routes: a **WKWebView panel** exposes the DOM's ARIA tree to VoiceOver automatically (roles, labels, live regions), so an inbox card list needs `role="listbox"`/`option`, `aria-live="polite"` for arrivals and visible focus rings; a **native AppKit/SwiftUI panel** gets `NSAccessibility` for free on standard controls and must set `accessibilityLabel`/`accessibilityRole` on custom views. In both, a non-activating panel that takes keystrokes must *become key* for VoiceOver's cursor to enter it — the same `needsPanelToBecomeKey` decision as 1.2. Also: Reduce Motion / Reduce Transparency (`prefers-reduced-motion`, `prefers-reduced-transparency` in CSS; `NSWorkspace.accessibilityDisplayShouldReduceTransparency` natively) must be honoured by any glass surface (1.10).

## 3. Build options, compared

Common facts first (theuth today): the macOS package is a Tauri bundle built by `scripts/package-macos.sh` with `externalBin: ["binaries/t"]`, `hardenedRuntime: true`, an `entitlements.plist` (`com.apple.security.cs.allow-jit`, `com.apple.security.device.audio-input`; no App Sandbox), inside-out `codesign --options runtime`, `codesign --verify --deep --strict`, a DMG, and a separate `notarize-macos.sh` (submit + staple); `minimumSystemVersion` is **15.0**; the `t` engine already statically links three **Swift-bridge** crates and must carry `LC_RPATH /usr/lib/swift` (knowledge `procedures/theuth-package-macos-sidecar-guard-and-swift-runtime-2026-10-07`, `facts/cargo-link-arg-does-not-propagate-rpath-swift-bridges-2026-10-07`). ## 5. Implications for theuth (≤ 15 bullets)

1. **The rail, Inbox and Router are all reachable from the existing Tauri/Rust shell today**: they are non-activating `NSPanel` webviews, which theuth already builds for the island and point-and-say (`crates/desktop/src/island/macos.rs`, `point/macos.rs`). No Swift is needed for the core One-style surface.
2. **Menu-bar Live Activities are off the table for a Mac app** — only a paired iPhone's ActivityKit activities appear in the Mac menu bar (1.1). The equivalent on Mac is a status item whose icon encodes agent state plus a panel under it; on macOS 27 the sanctioned hook is `NSStatusItem.expandedInterfaceDelegate`.
3. **Rich notifications are the first thing that genuinely needs native code**: the official Tauri plugin gives title/body only on macOS; buttons, text-input replies (answer a question from the banner), `timeSensitive`, and `threadIdentifier` grouping need `UNUserNotificationCenter` via objc2 bindings or a `swift-bridge` backend in-process (Choochmeque's plugin is the proof) — no second executable required (1.4).
4. **Time-sensitive notifications for a Developer ID app: unverified** (entitlement page did not resolve); critical alerts are request-gated. Design the default on `.active` and treat `.timeSensitive` as an upgrade to confirm.
5. **Double-tap-Option (One's trigger) is not a Carbon hot key.** `tauri-plugin-global-shortcut` cannot express it; it needs an `NSEvent` global monitor (or CGEventTap) on `flagsChanged` and the Accessibility grant — the same grant point-and-say already asks for, so the marginal permission cost is zero if Accessibility is already granted (1.7, 1.9).
6. **Permission order the user would see** (each TCC class once per signing identity): Notifications (ask at first finished-work event, or use `.provisional` to deliver quietly without a prompt first) → Accessibility (at first Router hotkey/gesture setup; also powers AX point-and-say) → Microphone (first voice use) → Screen Recording (only if "point at it" sends a screenshot; prefer `SCContentSharingPicker` or AX-text-only to avoid it) → Automation (only if the companion drives Terminal/iTerm). One asks for Microphone, Accessibility, Screen Recording and Automation on setup (1.9); theuth can ask for fewer, later.
7. **Keep one signing identity**: a Swift helper executable or LaunchAgent (option b) is a *separate* TCC responsible process and would re-prompt for Accessibility/Screen Recording/Notifications; if native Swift UI is wanted, prefer static `swift-bridge` code inside the existing binaries (a+) or an Xcode-built framework loaded in-process, over a second process (§3).
8. **What only Swift unlocks** and is worth it: App Intents → Spotlight actions on macOS 26+ ("Ask theuth…", "Approve latest"), Shortcuts, Focus filters; per-control Liquid Glass. What Swift unlocks and is *not* worth it for this design: WidgetKit (40–70 refreshes/day — minutes-stale, wrong for live agent state; useful only for a daily summary tile), Notification Content extensions.
9. **Liquid Glass for a webview panel = backdrop only**: `window-vibrancy`'s `apply_liquid_glass` (macOS 26+, interactive on 27) behind a transparent webview; HIG says use glass sparingly and only for the floating functional layer — a rail and an inbox panel are exactly that layer; honour Reduce Transparency/Increase Contrast and the user's glass preference.
10. **Keyboard grammar**: Gmail/Superhuman/One agree on `j/k` move, `e` clear/done, `1/2/3` pick, `z`/Esc undo, `?` help, `⌘K` palette; single letters are fine only while the panel is key; the one system-wide trigger should be a ⌘-based chord or a modifier gesture — HIG says avoid Control as a modifier (theuth's voice key is Ctrl+S; the companion should not add more Control chords).
11. **Undo**: One's "wait 2 s, Esc undoes" is Gmail's delayed-commit pattern (5–30 s), not `NSUndoManager`; for a menu bar/panel app implement both: a delayed commit with a visible countdown toast for sends/approvals, and Edit › Undo (⌘Z) on reversible local actions, naming the action (HIG).
12. **Focus awareness is cheap and native**: `INFocusStatusCenter` (macOS 12+) tells the companion when the user is in a Focus so it can batch; Focus *filters* (per-Focus configuration) need App Intents (Swift).
13. **Packaging**: everything in (a)/(a+) ships through the existing `package-macos.sh` (Developer ID, hardened runtime, notarize); a `.appex` (d) is a scripted extra signing step with App Groups and is **unverified** against Tauri's bundler — budget a spike before promising widgets/Spotlight actions.
14. **Parity**: option (a) surfaces port to Windows/Linux through the existing per-OS island backends; every Swift-only item (3, 8, 12-filters) is macOS-only by nature — list them as macOS enhancements in the design, not as the companion's definition.
15. **Reuse list** (permissive): tauri-nspanel 2.1 (MIT), window-vibrancy, Choochmeque notifications plugin (MIT) or its swift-bridge pattern, Maccy (MIT) for panel keyboard UX, KeyboardShortcuts/LaunchAtLogin-Modern/Settings (MIT) only if a Swift target appears. **Techniques only**: Ice, boring.notch (GPL-3.0).
