- `crates/sessionsync/src/snapshot.rs` (new):
  - `build(store, origin) -> Msg::Snapshot`. **Method: scratch `sqlite3session` on the `temp` database**, not `sqlite3session_diff`. Inside one `Store::begin_apply()` transaction (write connection held, capture disabled, nothing else commits): every `ATTACHED` table gets a `CREATE TEMP TABLE "<same name>"` twin built from `PRAGMA main.table_info` (declared types + `PRIMARY KEY (…)`, no FKs); rows whose session `owner = origin` (`sessions.owner = ?`, else `<session col> IN (SELECT id FROM main.sessions WHERE owner = ?)`) are copied in rowid-keyset chunks of 1 000 (`SELECT rowid … WHERE rowid > ? … LIMIT 1000`, then `INSERT INTO temp.t SELECT * FROM main.t WHERE rowid BETWEEN ? AND ? AND <filter>`), each chunk under a fresh `sqlite3session_create(db, "temp")` + `sqlite3session_attach(table)` whose changeset — named after the table, INSERTs only — is one `(table, changeset)` entry; the twin is emptied between chunks, dropped at the end, and the transaction is dropped (rolled back). `current_to_seq` = `log_seq()` for self, else our `(origin, "")` cursor, both read after `BEGIN IMMEDIATE`. Why not `sqlite3session_diff`: `ATTACH` is refused inside a transaction and `ApplyTx` is the only route to the raw handle; `diff` cannot filter by owner.
  - `split(Msg) -> Vec<Msg>`: parts of ≤ 32 MiB of changesets, then an **empty terminator** `Snapshot { tables: [] }`. All parts carry the real `current_to_seq`; the receiver moves the cursor on the terminator only, so a stream cut mid-snapshot leaves no cursor claiming completeness (it re-bootstraps at the next `Hello`).
  - `apply(store, part, fenced: &mut HashSet<String>, move_cursor) -> Vec<(session, owner, epoch)>`: each entry through `sqlite3changeset_apply` with the incoming row winning (`owner_wins`: REPLACE on DATA/CONFLICT, OMIT otherwise). **Fence**: the `sessions` entry is iterated (`sqlite3changeset_start/next/op/new`) for `(id, owner, epoch)`; ids whose local fence (`max(sessions.epoch, session_epochs.epoch)`, one `UNION ALL` query) is higher go into `fenced`; while `fenced` is non-empty every entry is rebuilt through a `sqlite3changegroup` without those sessions' records (`sqlite3changegroup_add_change`, 3.50.4 vendored). `move_cursor`: `session_cursors(origin,'') = max(old, current_to_seq)` and the `session_epochs` upsert for every session the snapshot owns; `fenced` cleared. Tables apply in `ATTACHED` order (`sessions` first).

### `deda39e` feat(sessionsync): ship/sync/prune — Hello, catch-up, live feed, relay, acks, prune timer; loopback tests
- `crates/sessionsync/src/sync.rs` (new): `Node { store, me, rt: Option<Runtime>, relay: broadcast<(PeerId, LogRow)>, kick: Notify, held: per-remote per-origin seq, stale_logged, origins: per-origin tokio::Mutex, pending }` and `run_stream(node, remote, stream)`, the symmetric protocol mirroring `replica/src/sync.rs`:
  1. `Hello { cursors }` = our log head `(me, log_seq)` plus every applied cursor `(origin, seq)`, nothing at 0. Their `Hello` replaces what we believe they hold; their cursor for us is persisted as `session_cursors(me, remote)` (it is an ack).
  2. Catch-up per origin we hold: peer has no cursor → snapshot; peer behind and origin = me → `Log` batches (≤ 5 000 rows / ≤ 32 MiB) from `log_after(theirs)`; if the log does not start at `theirs + 1` (pruned past them, or an orphaned run) → snapshot instead; peer behind on a **relayed** origin → snapshot (D1).
  3. Live (`tokio::select!`): `store.log_watch()` change or `ShipNow` kick → own rows after what the remote holds; relay feed → `Log` of one row for other origins when the remote holds less, a snapshot when it holds nothing of that origin yet; inbound `Log` → `receive_log`; inbound `Snapshot` parts → `receive_snapshot` (per-origin lock from first part to terminator, skipped when our cursor ≥ `current_to_seq`, `Ack` on the terminator); inbound `Ack` → mark held, plus `set_cursor(me, remote, seq)` when it is about our log; `Release/Released/Events/Event/Fetch` logged at debug and ignored on these streams (O/F).
  4. Events (when a `Runtime` is present): `AgentEvent::ContextChanged { session, revision: store.context_revision, reason: "replicated" }` once per session touched by a `Log` batch; `AgentEvent::SessionOwnerChanged { session, owner, epoch, here }` when a batch changed the row's `(owner, epoch)` and for every `sessions` record a completed snapshot applied.

### `3aaf8a8` fix(sessionsync): apply log rows in seq order
- The first test run lost rows when both ends dialed (two streams per pair): row *k+1* could be applied before *k* on the other stream and `apply_log_row`'s cursor check then dropped *k* as a duplicate (`snapshot_bootstrap_equals_a_full_replay` never converged). Fix: `Shipper::dial` only when `me < peer` (one stream per pair; the higher id serves the accepted one); `receive_log` applies strictly `cursor + 1`, treats `≤ cursor` as duplicate and parks rows further ahead in a per-origin reorder buffer (`Node.pending`, `BTreeMap` by seq, drained as the gap fills) — a gap open longer than `GAP_WAIT` (10 s) ends the stream so the `Hello` exchange re-sends from the cursor or snapshots over an orphaned run; `Ack` carries the cursor reached and is sent only when it moved. `StaleEpoch` rows move the cursor too (`set_cursor(origin, "", seq)`): seen, not applied — otherwise they would be re-sent at every `Hello` and hold the gap open forever.

## 2. Deviations from the brief / contract

- **D1 Relayed origins re-sync by snapshot, not log.** `session_log` holds only our own rows (seq is our log position, there is no origin column), so a peer behind on an origin we merely relay gets `Snapshot{origin}` built from our tables (`current_to_seq` = our cursor). Live rows of other origins are relayed as `Log` rows the moment we apply them (A→B→C live; tested). Cost: a reconnecting peer a few rows behind on a third engine's origin gets a full snapshot of that origin's sessions from us.
- **D2 Solo prune does not call `build_snapshot`, and the head row always stays.** Snapshots are built on demand from the live tables at `Hello`, so a never-paired engine's log is dead weight; `tick` deletes everything below the head row without the 20 000-row / 64 MB thresholds (`snapshot_rows`/`snapshot_mb` not added to `SessionsConfig`; `prune_secs` is the constant `PRUNE_SECS`). The head row is kept because `Store::open` seeds `seq` and the HLC from `MAX(seq)`/`MAX(hlc)`: deleting it would restart the log at seq 1 and collide with every peer's cursor. Same guard in the replica prune.
- **D3 Multi-part snapshots.** `Msg::Snapshot` unchanged; a snapshot over ~32 MiB travels as parts plus an empty terminator (`tables: []`) that moves the cursor. The contract's single-message `apply_snapshot(store, &Msg)` still applies and moves the cursor in one call. A per-origin `tokio::Mutex` on the `Node` serializes snapshot parts and `Log` batches of one origin so a slower snapshot on one stream cannot roll back newer rows applied from another.
- **D4 Fence on apply without iterating the changeset.** `apply_log_row` upserts `session_epochs` from the post-state `sessions` row in the same transaction (`WHERE excluded.epoch > …`): equivalent to `set_fence` when `owner/epoch` moved, a no-op otherwise. `StaleEpoch` is logged once per `(session, epoch)` (`Node.stale_logged`).
- **D5 UI refresh events** come from `sync.rs` (`ContextChanged{reason:"replicated"}`, `SessionOwnerChanged`); no `supervisor.rs` hook: `Agents` already invalidates search on `ContextChanged`, and desktop/TUI reload the transcript on a new `context_revision` (the owner's append bumped it and the changeset carried it). After a completed snapshot, one `SessionOwnerChanged` per session in its `sessions` entries, no per-session `ContextChanged` (a bootstrap may carry thousands of sessions).
- **D6 Ack semantics.** `Ack{origin, seq}` = "my cursor for `origin` reached `seq`", after a `Log` batch that moved it and after a completed snapshot (`current_to_seq`); the peer's `Hello` cursor for us counts as an ack. Only acks about **our** origin are persisted (`session_cursors(me, peer)`, what prune reads).
- **D7 One dialer per pair + reorder buffer** (see `3aaf8a8`), instead of replica's both-ends-dial: order matters for a changeset log, not for LWW records.
- **D8 Orphan retention** (`prune_orphans_before(now − orphan_keep_days)`) runs in L's prune tick. O owns orphan marking; this only enforces the 7-day retention from `SessionsConfig.orphan_keep_days`.
- **D9 Replica prune scope.** Own batches only; relayed batches stay (the relay catch-up source). Wired into `emit_locked`, not a timer (one indexed DELETE per local commit).
- **Out-of-allow-list edits, all disclosed above:** `crates/agent/src/store.rs` (+7 lines), `crates/agent/src/store/capture.rs` (`pub const ATTACHED`), `crates/sessionsync/Cargo.toml` (3 deps), `crates/sessionsync/src/lib.rs` (`shipper` field, `start_transport` call sites, `PeerGone` one line, `mod` lines), `crates/replica/src/engine.rs` (prune fn + call).

## 3. Not built / known gaps
- `snapshot_rows` / `snapshot_mb` / `prune_secs` config keys (D2): constants instead.
- A take row (`UPDATE sessions SET owner, epoch`) arriving for a session whose row a replica does not hold yet is `OMIT`ted by `sqlite3changeset_apply` (NOTFOUND); its fence is set only once the `sessions` row arrives by snapshot. If that snapshot comes from a peer that has not seen the take, the replica shows the pre-take owner until the next snapshot of the taker's origin. Protocol-level; for O/Z.
- `Msg::Release/Released/Events/Event/Fetch` on a shipping stream are ignored (debug log). O/F open their own streams or extend `Shipper::serve`.
- `snapshot::build` holds the store's write lock for the whole build (`ponytail:` comment); a read connection with its own session extension would free it.
- A relayed origin's snapshot is sent whenever the remote holds less than we do (D1) — including a peer only slightly behind. Bounded by reconnect frequency.
