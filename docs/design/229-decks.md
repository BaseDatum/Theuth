# 229 — Decks

Status: **Release Candidate** on `feat/decks-release`.

## 1. Product Contract & Motivation

A **Deck** is a first-class, collaborative live workspace document in Theuth — combining:

- **Collaborative visual sections** (`json_render`, `note`, strict-CSP `html`) independently created and edited by humans and agents with stable IDs, optimistic concurrency (`expected_rev`), per-section revision history, attribution, and focus presence.
- **Review-gated Monty execution** backed by the exact same session runtime as normal agent sessions (reusing `agent::repl` pool/checkout construction, live `ToolRegistry::Invoke` & `ListTools(session)`, full configured MCP namespace injected as async SDK functions, tool risk/approval gates, secret expansion/redaction, and `.monty` persistence + `rebase_dump_stubs`).
- **Scheduled collection AND persistent streaming** on portable bounded entrypoints (`on_start(last_state)`, `on_step()`, `collect()`, `on_action(action, args, ctx)`), keeping a supervised checkout and globals alive even with zero views open.
- **Interactive UI actions** entering the SAME live checkout via declared JSON-Schema actions, returning per-caller private results while broadcasting shared frames only when Python explicitly calls `deck_emit(...)`.
- **Full-page views and reference-only whiteboard cards** sharing the same live subscription and renderer, with zero whiteboard Y.Doc churn on streaming/snapshot repaints.

Decks are native to Theuth — NOT `crates/plugins`, with no `plugin.yaml`, no external process SDK, and no user build toolchain.

## 2. Architecture

### 2.1 Strict Separation of Collaborative State vs. Executable / Runtime State

| Plane | Storage | Authority | Mutated by |
|---|---|---|---|
| **Visual / Collaborative Document** | `DocKind::Deck` in `crates/document` (pure `yrs::Doc` root maps: `meta`, `sections`, `order`, `aliases`, `script_refs`) | `DocumentActor` | Owner UI & Agent `deck_section_*` / `deck_focus` tools |
| **Executable Scripts & Review Gate** | SQLite `deck_script_revisions` in `crates/decks` (`pending_review` / `approved` / `rejected` / `superseded`) | `DeckSupervisor` + owner-only `deck_script_approve` RPC | Propose: Owner or Agent; Approve/Reject: Owner RPC only |
| **Durable Runtime State & Snapshots** | SQLite `deck_meta` (including monotonic persisted `run_epoch`), `deck_snapshots`, `deck_state_checkpoints`, `deck_run_log`, `deck_action_idempotency` | `DeckOwner` (single runtime owner per Deck) | `DeckOwner` / Monty cooperative builtins |
| **Transient Live Frames & Push** | In-memory `DeckHub` bounded per-Deck subscription (`deck_subscribe`) with coalescing & rate/size caps | `DeckHub` | `DeckOwner` (`deck_emit(durable=False/True)`) |

**Security invariants**:
- Visual CRDT edits to `DocKind::Deck` can NEVER modify executable Python or self-authorize a script revision. `script_refs` in the Y.Doc stores read-only metadata pointers (`active_rev`, `pending_rev`, `mode`, `schedule`, `updated_at`) reconciled from authoritative SQLite state on read.
- Script creation or modification ALWAYS creates a `pending_review` revision. Starting/running a Deck refuses unapproved revisions; only the owner-only `deck_script_approve(deck_id, rev, expected_digest)` RPC transitions a revision to `approved`.
- High-frequency transient live frames NEVER touch the global `RuntimeWire` (only coarse `DeckChanged` events on `decks.changed@1` are published on metadata/section/script transitions) and NEVER mutate any whiteboard `Y.Doc`.

### 2.2 Collaborative Document Schema (`crates/document/src/deck/mod.rs`)

- Root `Y.Map`s: `meta`, `sections`, `order`, `aliases`, `script_refs`.
- Each section in `sections[id]` has stable ULID/hex ID, human alias (`s1`, `s2`, ...), `kind` (`json_render | note | html`), `title`, `content`, `col_span` (`1..=12`), optional `data_key`, `archived`, monotonic `rev`, `created_at/by`, `updated_at/by`, and bounded per-section `history` (`Y.Array`, capped at 50 revisions with byte caps and tiered compaction).
- Ordering uses finite fractional float ranks in `order[section_id]` with automatic re-normalization on underflow: moving one section updates a single key in `order` without rewriting sibling sections.
- Optimistic CAS: `SectionPatch` and `SectionArchive` accept optional `expected_rev` and return structured `DeckDocError::Conflict(SectionConflict)` on mismatch.
- `data_key` patching supports omitted (unchanged), explicit `null` / `clear_data_key: true` / empty string (clear), and non-empty string (set) across `DeckOp::SectionPatch`, agent `deck_section_patch`, and RPC `deck_section_patch(..., data_key, summary, clear_data_key)`.

### 2.3 Monty Session Runtime & Single-Owner Execution (`crates/decks/src/{runtime,owner}.rs`)

- Each Deck receives its own persisted `SessionId`, isolated `.monty` dump path (`<data_dir>/decks/runtime/<session_id>.monty`), and isolated per-Deck working/write directory (`<data_dir>/deck-work/<deck_id>`), reusing `agent::repl` (`open_default_pool`, `session_repl_config`, `session_mounts`, `session_tool_specs`, `find_session_tool`, `rebase_dump_stubs`, `tool_result`, `os_answer`).
- **Full tool parity**: Every `ToolCall` / `ListTools` runs directly through `ToolRegistry::Invoke` and `ToolRegistry::ListTools` with the Deck's `SessionId`, exposing the full configured MCP namespace as async Python SDK functions (`mcp__<server>__<tool>` / `tools()` / `help()` / `bindings()`), normal tool policies/approvals, and secret expansion + output redaction (`tools::secrets::redact` / `redact_value`).
- **Portable bounded entrypoints & cooperative builtins**:
  - `on_start(last_state)` — cold start / state restoration entrypoint.
  - `on_step()` — bounded streaming iteration (never one infinite feed; respects worker/inproc clamps).
  - `collect()` — scheduled / one-shot collection entrypoint.
  - `on_action(action, args, ctx)` — interactive action handler on the SAME live checkout.
  - Cooperative host builtins: `deck_emit(payload, durable=False, section=None)`, `deck_checkpoint(state)`, `deck_sleep(seconds)` (strictly validates finite non-negative numeric seconds), `deck_state()`, `deck_last_snapshot()`.
- **Cron & interval scheduling**: `schedule_cron` is evaluated via `croner::Cron` (clamped to `1..=MAX_INTERVAL_SECS`), falling back to `interval_secs` (or mode defaults) when unset.
- **Warm restore + cold fallback**: On startup/restart, `DeckCheckout` attempts warm `.monty` heap restore + `rebase_dump_stubs` when the saved `script_rev`, canonical `revision_sha256`, and actual `.monty` file byte SHA-256 match; on mismatch or corruption, it deletes the stale dump and falls back cleanly to a fresh checkout calling `on_start(last_state)` with the last durable JSON checkpoint.
- **Periodic clean-boundary rollover**: After `CHECKPOINT_ROLLOVER_STEPS` clean step/action boundaries, the checkout dumps heap state, refreshes tool stubs, and rolls cleanly without leaking memory.
- **Single-flight serialization & persisted fencing**: One `DeckOwner` task per Deck owns the checkout exclusively, serializing `on_step`, scheduled `collect`, and `on_action` calls at cooperative boundaries. Every run transition monotonically increments and persists `run_epoch` in SQLite `deck_meta` so post-restart snapshots strictly outrank pre-restart snapshots; stale frames/checkpoints from superseded epochs or deleted Decks are fenced out.
- **Failure / stale semantics**: Collection, step, or durable snapshot persistence failures preserve `last_ok_snapshot_id` and mark `runtime.stale = true` with redacted `last_error` and `consecutive_failures` (with exponential backoff on both initial `Start` and scheduled ticks) without clobbering the last-good snapshot. Durable `deck_emit(..., durable=True)` snapshots bypass transient frame rate limiting and persist atomically inside a SQLite `BEGIN IMMEDIATE` transaction.
- **Tool approval pause surfacing**: `DeckApprovalWatcher` subscribes to `ApprovalRequested` / `ApprovalResolved` on `RuntimeWire` for Deck sessions, immediately transitioning runtime state to `waiting_approval`, pushing `DeckRuntimeEvent::ApprovalPending` to `DeckHub` subscribers, fast-failing concurrent `deck_interact` calls with `WaitingApproval`, and restoring the pre-approval runtime state once resolved via standard `resolve_approval`.

### 2.4 Interactive Actions & Stream Controls

- **Declared actions only**: Every script revision declares `declared_actions: Vec<DeclaredAction>` with `name`, `title`, `description`, JSON `schema`, `mutates_state`, and `allow_while_paused`.
- `deck_interact` validates: (1) no pending approval (`waiting_approval`), (2) action is declared, (3) `args` match JSON Schema via `jsonschema::validate`, (4) optional `expected_rev` matches active approved revision (`revision_mismatch`), (5) caller-scoped `(deck_id, caller_id, request_id)` idempotency cache in SQLite (`deck_action_idempotency` prevents replay on retry/disconnect and returns `conflict` on mismatched reuse), (6) bounded queue/busy/timeout handling, and (7) `allow_while_paused` when paused.
- **Privacy**: `on_action` return values (and redacted errors) are returned ONLY in the caller's `InteractResponse` (`private: true`); other viewers see shared updates ONLY when Python explicitly invokes `deck_emit(...)`.
- **Stream lifecycle**: `start` (approved rev only), `pause` (retains live checkout & globals, stops stepping), `resume` (wakes existing checkout), `stop` (checkpoints and releases checkout), `run_once` (bounded one-shot execution, clearing `Error` state on success).

### 3.1 Security & Runtime Hardening (As-Built)

- **RPC & subscription authorization (B1)**: Every `DecksApi` method and `deck_subscribe` enforces `owner_only` (authenticated, non-closed owner peer); security-sensitive transitions (`deck_script_approve`, `deck_script_reject`, `deck_runtime_control`, and mutating `deck_interact` actions with `mutates_state: true`) additionally enforce `human_press` on the RPC path (rejecting share guests, engine-internal peers, closed peers, and `Forwarded` calls), while leaving the explicit `Risk::Mutating` `DeckInteractTool` agent tool path intact. `UnsubGuard` is armed before `pending.accept()` so failed handshakes never leak subscribers.
- **Protected internal state & fail-closed path resolution (B2)**: `tools::seat::real` anchors relative paths and resolves components left-to-right (failing closed `None` on empty/root escape). `tools::seat::refuse_internal_state` and `ToolRegistry` hard-refuse all writes into `<data_dir>/decks` (including `<nonexistent>/..` traversals), with post-`create_dir_all` re-checks in `WriteFile::call`.
- **Canonical revision & `.monty` integrity (B2, B3)**: Every `ScriptRevision` persists and recomputes `code_sha256` and canonical `revision_sha256` over `(code, declared_actions, mode, interval_secs, schedule_cron)` on every SQLite load and approval. Warm `.monty` restore additionally verifies the actual `.monty` file bytes SHA-256 against `monty_dump_sha256`, deleting tampered files and falling back cleanly to cold `on_start(last_state)`.
- **Digest-bound, pending-only, manual-only approval (B3)**: `deck_script_approve(deck_id, rev, expected_digest)` runs inside `BEGIN IMMEDIATE`, requires `status = 'pending_review'` (prior pending proposals are atomically marked `superseded` on new proposals), verifies `expected_digest == revision_sha256`, stops any prior revision, and leaves `schedule_enabled = 0, stream_enabled = 0` until explicit owner `Start`. Agent `deck_runtime` restricts `op` to `AgentRuntimeOp::{Pause, Stop, RunOnce}` (no `start`/`resume`).
- **Deadlock-free supervision & re-entrancy isolation (B4)**: `DeckSupervisor` reads `GetDeck`/`ListDecks`/`SubscribeDeckMsg` from a lock-free `LiveDeckCache` without awaiting `DeckOwner`, fast-fails `InteractMsg` when pending approvals exist, sends `RevisionApproved` non-blockingly, and excludes `DIRECT_ONLY`, `deck_*`, and `show_deck` from Deck scripts while keeping full normal session & MCP tool parity.
- **Caller-scoped idempotency privacy (B7)**: `deck_action_idempotency` is keyed by `(deck_id, caller_id, request_id)` and checks `(action_name, args_sha256, script_rev)` so one caller never reads another caller's private result and mismatched key reuse returns `InteractErrorCode::Conflict`.
- **Safe rollover & cold recovery (B8)**: If a rollover heap dump exceeds `DUMP_HARD_BYTES`, `maybe_refresh_or_rollover` returns `Err("rollover_dump_too_large")` instead of installing an empty VM, prompting `DeckOwner` to clear `.monty` metadata and cold-start `on_start(last_state)`.
- **Per-Deck isolation, lifecycle & boot recovery (H1–H4, H9–H10, M1–M3, L1, L3)**: Each Deck runs with isolated `<data_dir>/deck-work/<deck_id>` as `cwd`/`write_root` and per-session `SetApprovals { enabled: true }` pinned; phantom Decks are rejected; `DocumentChanged { deleted: true }` tears down SQLite, `.monty`, spill, work dir, hub state, and seat before broadcasting `Closed { reason: "deck_deleted" }`; startup awaits `RecoverEnabledDecksMsg` (indexing all live Deck sessions/seats and resuming previously enabled Decks), honors `decks.enabled`, and wires `DecksPlugin` into `cli.acp`; `DeckHub` coalesces unread `pending_frames` per section scope, clears on `Snapshot`/`Sync`/`Closed`, and prunes empty maps; all script/emit/stdout/action-return/interval caps and `checked_add`/`checked_sub` arithmetic are enforced; concurrent tool approvals queue per Deck and restore the exact pre-approval `RuntimeState`; `rebase_dump_stubs` uses sentinel-delimited managed blocks (`STUBS_BEGIN`/`STUBS_END`) supporting both `async def` and sync `def`.

### 3.2 Native Mesh Decks (Single Authoritative Home + Multi-Source Nodes)

- **Single authoritative home (NOT CRDT-elected)**: Deck documents/sections continue replicating through `DocumentActor` hub/relay (`DocKind::Deck.homed() == true`), while runtime execution, trigger state writes, and routine dispatch belong exclusively to the Deck's persisted `home_engine_id` (and `home_epoch`). Non-home engines may render/read/subscribe and keep the last-good Deck visible when home is offline, but refuse source ingest, runtime controls, interactive actions (`InteractErrorCode::NotHome`), source registration, and boot auto-resume (pausing execution rather than dual-home firing).
- **Typed source identity & authenticated binding**: Registered `DeckSourceRegistration` records (`deck_sources`) bind each `source_id` to an `engine_id`. Incoming `deck_source_ingest` calls derive the caller's engine identity strictly from the authenticated mesh transport (`agent::rpc_forward::Forwarded(PeerId)` on `theuth/rpc/1`, or local engine ID for local owner calls) and never trust an engine ID from untrusted RPC args. Full session tools and MCP servers remain strictly **local** to each source engine — there is no distributed Python VM and no remote raw tool access.
- **Home ingest dedup, epoch fencing, redaction & caps**: Home validates deck existence, home ownership, registration, authenticated engine binding, payload caps (`MAX_SOURCE_PAYLOAD_BYTES`, `MAX_HEARTBEAT_PAYLOAD_BYTES`), metric caps (`MAX_SOURCE_METRICS`), and per-source rate limits, and redacts all payloads/sections/errors before persistence or fanout. Events are deduplicated persistently by `(deck_id, source_id, source_epoch, seq)` in `deck_source_dedup`; duplicate retries return the exact persisted `IngestSourceAck` without duplicating frames, snapshots, or trigger fires. Monotonic `source_epoch` fencing rejects older epochs (`IngestStatus::RejectedStaleEpoch`).
- **Local source runtime, bounded offline spool & replay invariants**: `DeckSourceRuntime` runs Monty locally on the source engine with its local `ToolRegistry`, allocates a monotonically increasing persisted `source_epoch`, and buffers events in a bounded SQLite offline spool (`deck_source_spool`, enforcing `max_events`/`max_bytes` backpressure) when home is unreachable. On reconnect, `flush_spool` drains strictly in `(source_epoch ASC, seq ASC)` order with `replay: true`. Replayed history transitions the source to `Replaying` (`is_healthy() == false`) and **never** marks a source `Live`, never emits fresh live snapshots, and never opens, advances, or fires a fresh sustained-time threshold breach. Heartbeat/liveness sweeps (`Live -> Stale -> Offline`) clear in-progress sustained windows when a source goes `Stale` or `Offline`.
- **No automatic failover; explicit cold-start `deck_move_home`**: There is no automatic failover. Explicit owner transfer (`deck_move_home`) requires both `confirm_cold_start = true` and `verify_local_mcp_and_approvals = true`, stops any prior owner, clears `.monty` heap dumps for mandatory cold start, verifies local tool/approval seating, bumps `home_epoch` + `run_epoch`, clears in-flight sustained windows, and leaves auto-resume disabled (`requires_owner_start = true`).
- **Delivery & dispatch semantics (no distributed exactly-once)**: Mesh Decks do **not** provide distributed exactly-once execution. They provide **at-least-once source delivery with persistent deduplicated home ingest and persistent deduplicated dispatch** keyed by `(deck_id, source_id, source_epoch, seq)` and `(deck_id, trigger_key, source_id, source_epoch, seq)`. Downstream side-effecting routines must still treat dispatch keys as idempotency tokens.
- **Trigger integration (`SourceTriggerAdapter` + `TriggerSpec`)**: Home ingest evaluates fresh authenticated per-source samples through `SourceTriggerAdapter` (`classify_trigger_evidence` + host `TriggerSpec` sustained-trigger evaluator), dispatching existing owner-reviewed routines via `schedule::FireTrigger` without duplicating transport, auth, dedup, epoch fencing, or replay/liveness rules. Per-source scope (`source_id`) is supported natively; multi-source `any`/`all`/`quorum`/`aggregate` scopes remain a documented follow-up.

## 4. Honest Remaining Limitations & Follow-Ups

1. **Browser / Relay web CSP for HTML sections**: In the Tauri desktop app, strict HTML sections are served via the dedicated `theuth-page` custom protocol with `PageProfile::DeckStrict` HTTP CSP (allowing inline scripts inside an opaque-origin `sandbox="allow-scripts"` frame with zero network/form/parent access). In the browser relay SPA (`crates/relay/src/web.rs`), `srcDoc` iframes inherit the parent SPA's HTTP CSP (`default-src 'self'` without `script-src 'unsafe-inline'`), so interactive inline scripts in HTML sections require Tauri desktop rather than weakening the parent relay SPA's XSS defense.
2. **Unsupported session artifact adapters**: `mermaid`, `cells`, and whiteboard-in-Deck adapters are intentionally unsupported in Decks; sections are restricted to `json_render`, `openui`, `note`, and strict-CSP `html`.
3. **Real-time Yjs section sync in Desktop UI**: Full-page Deck views currently load sections via `deck_get` and refresh on `decks.changed@1` events (with per-section optimistic CAS via `deck_section_patch`), rather than opening a live browser `Y.Doc` provider for character-level note typing. The backend `DocKind::Deck` already lives in `DocumentActor` with full `yrs` updates, so binding a live `y-provider` in `DeckView` is incremental.
4. **Whiteboard "+ Add Deck" picker UI**: Agents and tests can place `CardKind::Deck` cards on whiteboards via `wb_place` / `addCard`, and whiteboards render and open them live; adding a dedicated "+ Add → Deck" modal picker in the whiteboard cluster toolbar is a small UI follow-up.
5. **Script editor UI**: Owners can review, approve, approve-and-start, and reject proposed script revisions in the Deck UI, and agents/RPC can propose new revisions; an inline CodeMirror script editor in the Script drawer for direct human Python authoring is a follow-up.
6. **External SaaS / OAuth discovery wizard**: The bundled `decks.md` skill guides agents to use existing Theuth MCP/secrets/OAuth flows; an interactive one-click integration discovery wizard is optional follow-up per the product contract.
7. **Mesh Deck follow-ups**: Multi-source aggregation/quorum trigger scopes (`any`/`all`/`quorum`/`aggregate`) and automatic background source daemon management/provisioning UI remain follow-ups. No automatic failover and no distributed exactly-once execution (persistent deduplicated dispatch only).
