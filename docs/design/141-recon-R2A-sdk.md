### 3.1 `ConnectionDriver` ownership in theuth's harness
Nobody in theuth owns or awaits a `ConnectionDriver`. `Link::spawn` passes `AcpAgent` / `Lines` straight into `Builder::connect_with` (`harness.rs:437,445`) and `tokio::spawn`s the returned future (`:450`); 3.1.0's `into_connection_and_future` does `DynConnectTo::new(transport).into_channel_and_future()` and polls `Some(driver)` inside `other_actors` (`3.1.0/src/jsonrpc.rs:1914-1958,2028-2048`). `AcpAgent` and `Stdio` implement only `connect_to` (`acp_agent.rs:646-650`, `stdio.rs:28`), so they normalize to an **opaque** `ConnectionDriver::new(..)` (default impl `component.rs:376-381`), while `Lines` returns a cooperative driver `with_finish` (`jsonrpc.rs:6989-7006,7036-7039`). No code change required; see §5 row "process exit text" for the behavioural consequence.

### 3.2 Raw / untyped handling (`child_update`, peer messages, `t --acp`)
- `child_update()` and `PeerMessage::parse` consume `UntypedMessage` from the typed-notification fall-through; 3.1.0 keeps the same chain: a typed `NotificationHandler` returns `Handled::No` when `matches_method` is false (`3.1.0/src/jsonrpc/handlers.rs:282-290`), the next handler (`UntypedMessage`) sees it. Unchanged.
- A `session/update` whose `sessionUpdate` tag is unknown to the enabled schema features makes `SessionNotification` parsing fail → handler `Err` → `handle_handler_error(.., None)` logs "Ignoring message-processing error because there is no request to answer" and returns `Ok` (`3.1.0/src/jsonrpc/incoming_actor.rs:561-564,682-689`). Same text exists in 2.2.0 (`2.2.0/src/jsonrpc/incoming_actor.rs:659`). Hence: the connection survives an unknown update in both versions; the update is dropped (never reaches theuth's `UntypedMessage` handler because the method *did* match). Consequence for 141: `subagent_update`/`session_message*` are only visible to theuth with `unstable_subagents` on (schema test `message_updates_require_subagents_gate`, `schema-1.10.2/src/v1/client.rs:625-643`).
- `rpc/src/acp.rs` never touches raw JSON-RPC; its `Error` construction (`:429-433,443`) is the typed ACP `Error`, unaffected by the `RawJsonRpcError` split (`migration-v3.md:28-37`).

### 5.1 Behavioural risk: child exit status / stderr tail may be lost (row 23-24)
Today (2.2.0): when the child dies, stdout EOF fires `cx.incoming_closed()` → theuth's `main` returns `Ok(())` (`harness.rs:418-422`) → the SDK's `drain_outgoing` **unconditionally** awaited `transport_completion` (`agent-client-protocol-2.2.0/src/jsonrpc.rs` `drain_outgoing`: "Transport completion is the sink-level barrier … `self.transport_completion.clone().await?`"), i.e. the `AcpAgent` future, whose `finish_child_exit(child?)` returns `Err` with `exit status: N` and the captured stderr on a non-zero exit (`3.1.0/src/acp_agent.rs:519-520,777-778`; same in 2.2.0). That `Err` became `exit_text` → `Update::Closed(..)` → the turn's error text (`acp_child.rs:1165-1175`).

3.1.0: `connect_with` passes `wait_owned_transport = false` (`3.1.0/src/jsonrpc.rs:1880-1881`) and `AcpAgent` normalizes to an **opaque** driver (only `connect_to` implemented, `acp_agent.rs:646-650`; default `into_channel_and_future` wraps with `ConnectionDriver::new`, `component.rs:376-381`), so `drain_outgoing(None, false)` skips the await (`jsonrpc.rs:3992-3996`). The connection result is then decided by a race in `run_until_connection_close` (`jsonrpc.rs:3806-3822`): after the foreground `Ok`, it polls the background **once** (`util::run_until`, `util.rs:95-115`); if the child's wait-status has not yet surfaced, the future returns `Ok(())` → `exit_text` yields the bare `"process exited"` (`harness.rs:1011`) and the driver is dropped (`ChildGuard` kills the group, `acp_agent.rs:306-331`). The SDK only guarantees exit-status reporting for `Builder::connect_to` (reactive, `wait_owned_transport = true`, `jsonrpc.rs:1801-1810`; test `protocol_eof_still_reports_nonzero_child_exit` uses `connect_to`, `acp_agent.rs:1197-1226`). CHANGELOG wording: "Request the futures executor…", "Opaque application drivers have no physical finish contract… do not globally join work which may intentionally run forever after the foreground returns" (`jsonrpc.rs:3997-4000`).

Impact: the user-visible failure text for a crashed/killed harness degrades from `…: exit status: 1\n<stderr tail>` to `process exited`; `is_busy("process exited: signal 9")` style checks unaffected. Mitigations (pick one, smallest first):
1. Read theuth's own stderr log tail (`<data_dir>/logs/acp-<name>.log`, already written by `with_debug`, `harness.rs:428-435`) when `exit_text` is the bare `closed` string — restores the stderr tail without SDK plumbing; loses the numeric exit status.
2. Wrap `AcpAgent` in a theuth newtype implementing `ConnectTo<Client>` whose `into_channel_and_future` takes the SDK driver, `map_future`s it (`ConnectionDriver::map_future`, `3.1.0/src/component.rs:174`; documented `migration-connection-drivers.md:69-86`) to stash the `Result` in an `Arc<Mutex<Option<Error>>>` + `Notify`, and have `main` wait ≤ `SHUTDOWN_GRACE_PERIOD`-ish (1-2 s) for that signal after `incoming_closed` before returning. Exact parity; ~40 lines.
3. Ask upstream for `connect_with_owned` / a `wait_owned_transport` knob (not available in 3.1.0: the parameter is private, `jsonrpc.rs:1888-1891`).

### 5.2 Behavioural change (favourable): `Lines` finish on dial/mesh (row 26)
3.0.0 made `Lines` a cooperative driver (`with_finish`, `jsonrpc.rs:6989-7006`): when theuth's `main` returns (`Harness::close`), the SDK requests finish, drains accepted output and completes **without waiting for remote EOF** (`migration-connection-drivers.md:137-140`, CHANGELOG `sdk-docs/CHANGELOG.md:112-114`). In 2.2.0 `drain_outgoing` awaited the `Lines` future, which (per the 3.0 fix list) could wait for the remote read side to close. Net effect for the mesh child (`MeshDialer`) and link nodes: `close()` resolves faster, no hang on a peer that keeps its write half open. The loopback test `child_session_over_the_mesh_loopback` (`rpc/src/acp.rs:1272-1277`) asserts `harness.close()` is followed by the server task ending within 10 s — it will keep passing and is the regression guard.

### 5.3 Behavioural change (minor): `t --acp` final flush at stdin EOF (row 28)
`Stdio` is also opaque (only `connect_to`, `stdio.rs:28`), so after stdin EOF theuth's `main` returns, the protocol drain marker completes, and the `Stdio` driver is dropped without the SDK proving the stdout write finished (`jsonrpc.rs:3997-4001`). 2.2.0 awaited it. A `session/update` queued in the same instant as the client closing stdin could be truncated — theuth cancels `rt.shutdown` right after anyway (`rpc/src/acp.rs:90-93`). No user-visible loss expected; note only. (If exactness is wanted, `serve()` could call `Builder::connect_to(transport)` instead of `connect_with(.., incoming_closed)`: identical semantics plus `wait_owned_transport = true`, `jsonrpc.rs:1801-1810` — but `serve()` needs no `cx` outside handlers, so this is a one-line swap.)
