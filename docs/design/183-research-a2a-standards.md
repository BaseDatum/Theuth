# Research sheet: A2A-standard discovery and pairing for theuth peers outside one mesh
Read 2026-11-08, web only, no files written. Tags: **[V]** I read the source text itself; **[S]** search-result snippet only; **[I]** my inference, in no source.

## Bottom line
- A2A defines discovery (Agent Card) but **no pairing or first-contact flow**: credentials are acquired "out-of-band" (spec §7.3). No ratified standard covers LAN pairing of two personal harnesses. Three rival mDNS service types exist (`_a2a._tcp`, `_agent._tcp`, `_lad-a2a._tcp`). All are single-author or individual-draft specs, and none is registered or ratified.
- Best fits: draft-zhao for the LAN advert; LAD's consent rules as policy; Syncthing/KDE-Connect structure plus a Bluetooth/Signal-style short string (or SPAKE2+ code) for the ceremony; A2A as a custom binding over iroh for the relay path.

## 1. A2A protocol: 1.0.0 released 2026-03-12, 1.0.1 on 2026-05-26 (fixes HTTP media type, error mapping, TaskStatus only) [V]
Sources: github.com/a2aproject/A2A `docs/specification.md`, `specification/a2a.proto`, `docs/topics/{agent-discovery,extensions,custom-protocol-bindings}.md`, releases page, a2a-protocol.org blog. Governance: "A2A Protocol Working Group"; accepted as a Growth Stage project of the Agentic AI Foundation (Linux Foundation; announced 2026-08-27, with MCP as sibling). Not an IETF/ISO standard.
- **Discovery (§8.2):** (a) `https://{domain}/.well-known/agent-card.json` (IANA-registered, "Permanent", §14.3); (b) curated registries (spec "does not prescribe a standard API"; registry proposal discussion #741 is closed); (c) direct configuration. Zero mentions of mDNS/DNS-SD/DHCP in the spec. Issue #378 (mDNS request, May 2025) is still open; the only maintainer reply is a Jun 2025 pointer to #741.
- **Card fields (proto):** `supportedInterfaces[]{url, protocolBinding, protocolVersion, tenant}` (first = preferred; binding is an open string: JSONRPC, GRPC, HTTP+JSON, custom ones SHOULD be a URI, §5.8); `provider{organization,url}`; `securitySchemes`; `securityRequirements` (v1.0 name; prose in §3.1.11/§13.3 still says `security`); `capabilities{streaming,pushNotifications,extendedAgentCard,extensions}`; `signatures[]`. **The card has no agent-id field.**
- **Signing (§8.4):** optional JWS (RFC 7515) over the RFC 8785 JCS-canonical card; protected header needs `alg`+`kid`, SHOULD `typ=JOSE`, MAY `jku`; key comes from `kid`+`jku` "or from a trusted key store"; clients SHOULD verify one signature; several allowed for rotation. No key is embedded in the card, so the anchor must be pinned or pre-shared.
- **Extended card (§3.1.11, §13.3):** `GetExtendedAgentCard` needs auth and `capabilities.extendedAgentCard`; content may differ per client identity.
- **Schemes (proto):** apiKey (query/header/cookie); http (any IANA scheme, e.g. Bearer); oauth2 (authorization_code, client_credentials, **device_code** {device_authorization_url, token_url, refresh_url, scopes}; implicit/password deprecated; `oauth2_metadata_url` = RFC 8414); openIdConnect (discovery URL); mutualTLS (a `description` only: no CA or pin semantics).
- **Pairing/consent: none.** §7.3 "Credential Acquisition (Out-of-Band)"; §7.2 clients verify server TLS against trusted CAs. No registry API, no first-contact flow, nothing on mDNS.
  - Nearest in-band items: `TASK_STATE_AUTH_REQUIRED` (§7.6: per-task OAuth token or human approval, not peer pairing); experimental extensions `experimental-ext-cratb-auth` (draft v0.1.4, 2026-09-24: SD-JWT identity challenge, needs an issuer) and `experimental-ext-oid4vp-auth`; the example extensions (Secure Passport, Timestamp, Traceability, AGP) cover nothing here.
  - Community gap note: discussion #1714 (Apr 2026, "first-contact, no shared AS"; unadopted proposal).
- **Push (§4.3.3, §13.2):** client registers `TaskPushNotificationConfig{url, token, authentication{scheme,credentials}}`; agent POSTs a `StreamResponse` with `Authorization: {scheme} {credentials}`; agents SHOULD reject private, loopback and link-local webhook URLs (SSRF). So push is unusable between LAN-only or relay-only peers: use SSE (`SendStreamingMessage`) and `SubscribeToTask` (§3.1.6: first event is the current Task, so a reconnect over a relay resynchronizes from current state).

## 2. IETF draft-zhao-a2a-dns-sd-00 [V: ietf.org/archive/id/draft-zhao-a2a-dns-sd-00.txt, datatracker.ietf.org/doc/draft-zhao-a2a-dns-sd/]
- **Status:** individual Internet-Draft, C. Zhao, Informational, dated 2026-08-19, **expires 2027-02-20** (not expired; only -00 exists). Datatracker: "Active I-D (individual)", no WG or stream, IESG state "I-D Exists". One running implementation (a governance gateway). Companion draft-zhao-a2a-webfinger-00 (acct:agent@domain to card; global scope; same dates).
- **Service type** `_a2a._tcp`; no subtypes. Instance name = card `name` (a label, no semantics); port = TCP port serving the card/A2A. IANA: requests service name `a2a`/tcp, A2A project as preferred assignee; the author says (issue #378, 2026-08) `a2a` is still unregistered (not checked by me).
- **TXT keys:** `card` (RECOMMENDED; path, default `/.well-known/agent-card.json`), `proto` (optional; = `AgentInterface.protocolBinding`), `v` (optional; A2A version, e.g. 1.0), `tls` (optional; `1` means https). Unknown keys MUST be ignored; no credentials in TXT. **No fingerprint, key id or capability key.** The card wins on any disagreement.
- **Security (§4, §6):** discovery output is an unauthenticated hint; trust comes only from the Agent Card (TLS + JWS signatures). "Discovering an agent MUST NOT imply registering, trusting, or routing work to it"; a client MUST NOT persist a discovered instance on the advertisement alone; admission policy = "human review, signature verification against known keys, or both". Advertising leaks presence (SHOULD, not MUST). **It defines no pairing.**
- **Rivals [V]** (same problem, different service types; none settled):
  - draft-jakab-dawn-agent-discovery-mdns-00 (Cisco, 2026-07-06, expires 2027-01-07): `_agent._tcp`, TXT `proto=a2a`, `agentId`, `cardUrl` (required) + `caps`, `ver`, `a2aBinding`, `a2aProtoVer`; no IANA request; says types can coexist; cites OpenClaw's `_openclaw-gw._tcp`, which puts a TLS fingerprint hint in TXT.
  - LAD `_lad-a2a._tcp` (section 3).
  - IETF WG **DAWN** "Discovery of Agents With Names" (Internet Area, charter approved, updated 2026-10-22): scope includes local-network discovery over DNS/mDNS; OUT of scope: agent identity management, trust management, all communication after discovery. Its draft-mozleywilliams-dawn-dnsaid-00 (2026-11-02) is wide-area SVCB/DNSSEC/DANE with no mDNS. IETF `agentproto` WG (charter 2026-10-08) is dialog-context, not discovery or pairing. DAWN will likely choose the service type [I].

## 3. LAD-A2A v0.2.0-draft, 2026-07-01 (v0.1.0-draft 2026-01-28) [V: github.com/franzvill/lad `spec/spec.md` + README; lad-a2a.org]
- **Who/maturity:** personal GitHub project of Francesco Villano (franzvill); Apache-2.0, 26 commits, 245 stars, 31 forks; not an A2A-org or IETF document; v0.2 is a "breaking security revision following a hostile-network audit". It requests (does not hold) IANA entries for `_lad-a2a._tcp` and well-known name `lad`.
- **Service type:** LAD-owned `_lad-a2a._tcp` (v0.1 and its demo used `_a2a._tcp`); `_lad._sub._a2a._tcp` only if the A2A project owns the base type. TXT (closed set): `path` (req), `v` (req, LAD major), `id` (req; DID, e.g. `did:web:example.com#agent`), `org` (display only). Differs from Zhao: DID identity in TXT, https-only URLs, trust rules, more mechanisms. Card must carry the singular `protocolVersion` (pre-1.0 shape; examples use `/.well-known/agent.json`).
- **Other mechanisms:** MUST serve `https://<host>/.well-known/lad/agents` (JSON, max 100 agents / 256 KiB, no wildcard CORS, `max-age=300`); clients MUST query every mechanism and dedupe by identity key (an mDNS answer may not suppress the authenticated list). DHCP and captive-portal are non-normative/deferred in v0.2 (README still lists a DHCP option). QR/NFC fallback MUST carry a DID or org-bound key fingerprint, not just a URL.
- **Channel authentication vs identity verification (§4.0):** verified TLS proves only that bytes reached the host in the URL. Only identity (domain, JWS or DID bound to the org domain; a failed stronger method is fatal, no fallback; JWS `exp` <= 24 h) may be shown as "verified". Root of trust = org domain over WebPKI (did:web idea); self-signed certs "NOT acceptable for production"; a pre-shared key counts only for a managed fleet. **Does not fit two home machines with no domain.**
- **Consent (§4.3):** explicit human consent before first contact (no auto-approve; nothing sent before it); prompt shows channel and identity separately; capabilities shown from the fetched, verified card; "don't ask again" keyed to the verified identity key; grants invalidated when the key or cert changes; user can revoke (tears down sessions). **No TOFU, pairing code, mTLS or relay/NAT text** (grep: 0 hits).
- **Limits (§4.6):** body 256 KiB, 100 agents, 8 card fetches per run, 30 s deadline; prefer unicast over mDNS on untrusted networks; no eager card fetch; generic User-Agent, no cookies.

## 4. Pairing prior art after discovery, and which fits "confirm once, then limited trust"
| Prior art (status) | Mechanism | Fit for theuth |
|---|---|---|
| Matter PASE (SPAKE2+) and HomeKit (SRP-3072, 8-digit code) | Code on a label/QR typed at the controller; PAKE session; then attestation and a CSR answered with an operational cert from the fabric root [V developers.home.google.com/matter/primer/commissioning; S docs.silabs.com/matter, support.apple.com/guide/security/communication-security-sec3a881ccb1/web] | PAKE step yes; outcome (fabric admin credentials) is full trust: wrong for contacts |
| RFC 9383 SPAKE2+ (Informational, Independent Stream, not IETF-endorsed) [V rfc-editor.org/info/rfc9383] | Augmented PAKE; one side holds only a verifier | Library for a code-based ceremony |
| Bluetooth LE Secure Connections numeric comparison [S bluetooth.com/blog/bluetooth-pairing-part-4/] | ECDH; both screens show 6 digits; user taps yes/no on both. "Just Works" gives no MITM protection | Best symmetric UX when both UIs are in reach |
| Signal safety numbers [S signal.org/blog/safety-number-updates/] | 60-digit/QR fingerprint of both identity keys; verifying is optional; key change is flagged | Model for "unverified until compared" and key-change alerts |
| KDE Connect [V valent.andyholmes.ca/documentation/protocol.html; S mDNS `_kdeconnect._udp`, UDP 1716] | LAN identity packet (deviceId, name, capabilities), then TLS with certificate-based auth; `kdeconnect.pair` request needs a `pair:true` answer from the other side (30 s); packets from unpaired devices rejected | Closest UX: nearby list, mutual accept |
| Syncthing [S docs.syncthing.net/dev/device-ids.html, /users/introducer.html, /users/relaying.html, /specs/localdisco-v4.html] | Device ID = SHA-256 of the TLS cert; add on both sides; introducer auto-adds devices it knows; local discovery (announcements every 30-60 s), global discovery, relays that only forward E2E-encrypted bytes (relay sees IP + device ID) | Closest identity and relay model (ID = key, like an iroh EndpointID) |
| RFC 8628 device grant (Proposed Standard, Aug 2019) [V] = A2A `deviceCode` flow | Device shows a user code ("WDJB-MJHT", base-20, ~34.5 bits); user approves at the authorization server; client polls for a token. Server MUST rate-limit codes (§5.1: ~5 attempts for 2^-32); warn against remote phishing (§5.4) | Only A2A-native code flow: mints a bearer if the harness plays AS; asymmetric, no key pinning |
| FIDO CTAP 2.2 hybrid transport [S developers.yubico.com/CTAP/CTAP2.2.html]; magic-wormhole [S magic-wormhole.readthedocs.io] | QR secret + BLE proximity + WebSocket tunnel + Noise KNpsk0; short code + SPAKE2 via mailbox and transit relays | Patterns for pairing and carrying traffic through an untrusted relay. WebAuthn itself registers a key at a relying-party server, so it fits login, not peer pairing [I] |
- **Verdict [I]:** no one standard fits. Identity and relay model = Syncthing/iroh (ID is the key; relay is blind). Ceremony = KDE Connect's mutual accept plus a short string derived from both keys (Bluetooth/Signal) or a one-time code through a PAKE (Matter/RFC 9383). RFC 8628 and LAD §4.3 are useful only as bearer-minting and consent-policy templates.

## 5. A2A-adjacent efforts (none solves LAN pairing)
- **ANS:** v1 draft-narajala-ans-00 (Experimental, 2025-05) expired 2025-11-17. v2 draft-narajala-courtney-ansv2-02 (2026-10-26, exp 2027-04-29, Informational; GoDaddy/OWASP/Cisco authors) = domain-anchored identity: a registration authority checks domain control, issues an identity cert binding name to agent key, logs to a Merkle record [V]. GoDaddy sells it (godaddy.com/ans) [S]. Needs a domain and a registry; no mDNS or pairing text.
- **AGNTCY** (Linux Foundation; Directory/OASF, DID/VC identity, SLIM) [S docs.agntcy.org]: SLIM is the only relay-like piece (see §6) [V]. **NANDA** (MIT Media Lab; global index + signed "AgentFacts", arXiv 2507.14263) [S]: research-stage, registry-based.
- **MCP** [S modelcontextprotocol.io/specification/2025-11-25/basic/authorization; a 2026-07-28 spec exists]: OAuth 2.1, RFC 9728 resource metadata, client-ID metadata documents, DCR as fallback; MCP Registry lists servers (server.json). I found no LAN discovery or pairing in MCP.

## 6. Relay / NAT traversal for A2A
- **Core bindings [V §9-11]:** JSON-RPC 2.0 over HTTP(S) with SSE streaming, gRPC, HTTP+JSON. The spec has nothing on relays, tunnels or NAT; push needs a reachable webhook (see §1).
- **Custom bindings are allowed [V §5.8, §12; docs/topics/custom-protocol-bindings.md]:** the docs say bindings "change the transport layer itself" (examples: WebSockets, MQTT). `protocolBinding` is an open string (SHOULD be a URI; a new URI for a breaking change), declared in `supportedInterfaces`, and must support the card's auth schemes. Official ones live under `https://a2a-protocol.org/bindings/` (`cpb-*` repos), experimental under `experimental-cpb-*`; your own URI is also valid.
- **Official-org experiments [V]:** `a2aproject/experimental-cpb-slimrpc` (id `https://a2a-protocol.org/bindings/experimental-slimrpc/v1`; url `slim://[node:46357/]domain/ns/service`; both sides dial a SLIM broker node, auth at the SLIM layer by shared secret or mTLS, no A2A `Authorization` header; MLS end-to-end). `experimental-cpb-websocket` is an empty stub (1 commit, title-only README).
- **iroh side [V README; S docs.iroh.computer]:** EndpointID = Ed25519 public key, connections E2E-encrypted, hole punching plus relay. `n0-computer/iroh-proxy-utils` ("work in progress, API subject to change") already defines ALPN `iroh-http-proxy/1`: one HTTP/1.1 connection per bidirectional stream (CONNECT or absolute-form) with a pluggable `AuthHandler`.

## RECOMMENDATION
1. **LAN discovery (standard):** advertise and browse `_a2a._tcp` per draft-zhao (TXT `card`, `proto`, `v`, `tls`; advertise only while A2A is on, since advertising leaks presence, draft-zhao §6); browse only `_agent._tcp` (proto=a2a) and `_lad-a2a._tcp` so other vendors' agents appear; keep the type list in config because DAWN will probably pick one. Treat results as hints and never persist one on an advertisement alone (draft-zhao §4). All three are individual drafts: expect churn.
2. **theuth-only TXT keys [I]:** unknown keys MUST be ignored (draft-zhao §3.4), so add `eid` = short EndpointID fingerprint (hint only; OpenClaw does the same with a TLS fingerprint) and `pair=1` only while a pairing window is open. No standard has a "pairing window open" signal.
3. **Foreign A2A agents (standard flow):** fetch the card from the hint, verify the JWS if present, show a LAD §4.3-style consent card (channel and identity shown separately, nothing sent before consent, grant keyed to the verified key, revoked on key change), then store a per-peer bearer or run the card's OAuth device flow. Adopt LAD's limits (256 KiB, 8 fetches, 30 s) as defaults; do not adopt its wire format (WebPKI/DID/domain trust, pre-1.0 card, one author).
4. **Identity and pairing between theuth meshes (compose, no standard):** identity = iroh EndpointID. Ceremony = mutual accept on both UIs (KDE Connect [V]) plus a short string derived from both EndpointIDs (Bluetooth numeric comparison, Signal safety number [S]) or a one-time code through SPAKE2+ (RFC 9383 [V]); then pin both IDs, show "unverified" until the string is compared, re-prompt on key change. Contacts get no vault and no mesh RPC.
5. **Relay-only path:** carry A2A over the existing iroh QUIC connection on a new ALPN, one HTTP/1.1 request per bidirectional stream, declared as a custom binding in `supportedInterfaces` under a theuth-owned URI (shape: iroh-proxy-utils `iroh-http-proxy/1` [V]; do not depend on its unstable API).
   The EndpointID authenticates the channel, so WebPKI TLS (A2A §7.2) is not needed; use the same path on the LAN. Streaming via SSE + `SubscribeToTask`; no push webhooks. Keep the existing HTTPS + bearer endpoint for foreign agents; use SLIM or an HTTPS tunnel only when a foreign agent has no direct route.
6. **Card identity:** sign the theuth Agent Card with the engine's Ed25519 key (JWS `kid` = EndpointID; verify against the pinned key, since §8.4.3 allows "a trusted key store"); the card has no agent-id field.
7. **theuth must define itself (no standard covers it):** the pairing ceremony and string/code format; trust tiers and capability caps for contacts (A2A leaves authorization to the agent, §7.5, §13.1); the iroh binding URI, ALPN and auth mapping; the pairing-window advertisement and its rate limits (RFC 8628 §5.1 style); revocation, expiry and key rotation; relay-side rendezvous between strangers (ticket or short code, cf. magic-wormhole); labelling contact messages as untrusted input.
