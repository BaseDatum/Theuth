## Capture spike (§7, reported first)

**`takeSnapshot(rect)` does contain a sandboxed custom-scheme iframe, on macOS and on the iOS 26 iPad
simulator.** Neither B3's `page` snapshots nor anything else needs the labelled-box fallback for that reason.

Method: two throwaway programs (not committed), run tonight. A `WKWebView` with `WKURLSchemeHandler`s for `tauri`
and `theuth-page`. The main page is `tauri://main/` (red), as in the app. It has a `sandbox="allow-scripts"` iframe
from `theuth-page://p/1` (green) and a `sandbox` `srcdoc` iframe (blue). The program takes `takeSnapshot` of a
`WKSnapshotConfiguration` with `rect` 520×220 and `afterScreenUpdates = true`, then samples pixels.

| Where | custom-scheme sandboxed iframe | `srcdoc` sandboxed iframe | page |
|---|---|---|---|
| macOS 26 (this Mac, AppKit, `swiftc`) | `#00f900` (green, sRGB→display) ✔ | `#0432ff` (blue) ✔ | `#ff2600` (red) |
| iOS 26.0 simulator `glass-198-ipad` (a separate throwaway app `io.theuth.b5spike`, installed, run, uninstalled; theuth app untouched) | `#00ff00` ✔ | `#0000ff` ✔ | `#ff0000` |

The simulator also showed the coordinate trap that `wb_capture` handles. The web view's scroll view has
`adjustedContentInset.top = 32`, so CSS (0, 0) is at web-view point (0, 32). `wb_capture` and the stroke hand-over
both convert through the scroll view.

A side finding on macOS: an `https:` page cannot load a `theuth-page://` iframe at all (the frame stays blank).
It does not affect the app (its page is `tauri://`).

## What is built

### `crates/tauri-plugin-ink` (new)
- `Cargo.toml` (`links = "tauri-plugin-ink"`; `tauri` workspace, `+wry` on iOS; build-dep `tauri-plugin 2.7.2`, the version `Cargo.lock` already had), `build.rs` (`COMMANDS` = the eight of §6), `api-iife.js` (hand-written global API), `permissions/default.toml` (`ink:default` = the eight `allow-*`), `permissions/autogenerated/**` + `schemas/schema.json` (generated by the build, committed as the official plugins do), `.gitignore` (`/.tauri`, the Swift build dirs).
- `src/lib.rs`: `init()` builds `Builder::new("ink")`. On desktop it adds an invoke handler for the stub. On iOS the setup registers the Swift plugin.
- `src/models.rs`: the §6 types (`AttachResult`, `Reason`, `Route`, `NativeView`, `Tool`, `NativeStroke`, `StrokeBatch`, `PencilAction`, `PencilGesture`, `InkEvent`, `ToolArgs`, `Recognized`), with golden serde tests.
- `src/desktop.rs`: the stub. `attach` → `{ native: false, reason: "desktop" }`, `recognize_text` → `{ text: "", confidence: 0 }`, the rest no-ops.
- `src/mobile.rs`: `ios_plugin_binding!(init_plugin_ink)` + `register_ios_plugin`.
- `guest-js/index.ts`: typed wrappers of the eight commands (reference API; not an npm dependency).
- `ios/Package.swift`: tools 5.9 (needed for `.iOS(.v17)`), static library, `Tauri` path dependency, `linkerSettings` PencilKit + Vision. The manifest was checked with `swift package dump-package`.
- `ios/Sources/`:
  - `InkPlugin.swift`: `class InkPlugin: Plugin`, the eight `@objc` commands (lowerCamelCase), `@_cdecl("init_plugin_ink")`. Every command hops to the main thread.
    - `attach` answers `not_ipad` (idiom ≠ pad), `unsupported_os` (< iOS 26, `#available`) or `route_failed`, with `os` set.
    - The other commands are no-ops when not attached.
  - `InkModels.swift`: the wire structs (mirroring `models.rs`), `CapturedInk`, the `NativeInkOverlay` / `CaptureSurface` protocols, force normalisation, and `#rrggbb` ⇄ `UIColor`.
  - `InkOverlay.swift`: the coordinator and the hand-over/ack/retry queue (details below).
  - `CaptureSurfaces.swift`: **route A** (`CanvasSurface`) and **route B** (`ShapeSurface`).
    - Route A: a capture-only `PKCanvasView` subclass. `hitTest` → nil, `.pencilOnly`, scroll and zoom off, `overrideUserInterfaceStyle = .light` (JS colours are already theme-resolved). It is a sibling above the web view, with the same frame and autoresizing. Its `drawingGestureRecognizer` moves onto the web view with `allowedTouchTypes = [.pencil]`.
    - Route B: a pencil-only `UIGestureRecognizer` subclass on the web view, with coalesced touches and `preciseLocation`. One `CAShapeLayer` per stroke on a pass-through view (marker ×3 width, 45 % opacity, like the web renderer).
  - `ToolPickerController.swift`:
    - `PKToolPicker(toolItems:)`: monoline 2.4, pen 2.8, marker 6, vector eraser. `showsDrawingPolicyControls = false`, `colorUserInterfaceStyle = .light`. Attached through `webview.pencilKitResponderState.activeToolPicker`, visibility `.visible`/`.hidden`, `.inactive` on detach.
    - The observer reports user changes as `tool` events; JS's own `set_tool` echo is suppressed.
    - Also `PencilController`: `UIPencilInteraction`; tap and squeeze (squeeze at `.ended`) are reported with the user's preferred action.
  - `HandwritingRecognizer.swift`: `VNRecognizeTextRequest` `.accurate` on a utility queue. Lines are in reading order, joined with spaces and cut to 200 chars; `confidence` = the mean of the top candidates.

**Hand-over** (`InkOverlay`):
- Each finished stroke is captured at stroke end:
  - Route A: `interpolatedPoints(by: .distance(1.5))`, through `stroke.transform`, force `min(1, force/2)`, `t` in ms since `t0` (= `path.creationDate`).
  - Route B: raw coalesced samples, deduplicated under 0.5 pt.
- The stroke's pen and viewport are the ones at pen-down.
- At pen-idle (120 ms after the last pen-up) every not-yet-sent stroke goes in one `StrokeBatch`, in `seq` order (`seq` monotonic per attach, from 1).
- A 300 ms repeating timer resends every stroke still unacked 300 ms after its last send: same `seq`, `retry + 1`, a new `batch` number, for as long as attached.
- `ack(seqs)` removes the strokes from the overlay. Route A defers the removal to pen-up, because replacing `PKCanvasView.drawing` mid-stroke would cancel the stroke in progress.
- With the eraser selected (picker or `set_tool`), or with `set_enabled(false)`, the surface stops drawing (`isDrawingEnabled = false` and the recogniser disabled), so pen events reach the page.
- A second `attach` replaces the channels, renumbers still-unacked strokes from 1, and hands them over again. `detach` removes the overlay, the recogniser, the picker and the pencil interaction, and drops the queue.

### `crates/desktop`
- `src/apple_tile.rs`: `wb_capture(webview, rect, width?)` → `{ png, width, height, scale }`.
  - Main webview only. A non-finite, empty or off-view rect → `"wb_capture: empty rect"`.
  - A typed `WKSnapshotConfiguration` with `snapshotWidth` (capped at 4096 pt) and `afterScreenUpdates = true`. `setRect:` goes through `msg_send!`, because the typed setter is behind `objc2-web-kit`'s `objc2-core-foundation` feature.

- `capabilities/mobile.json`: `"ink:default"`.
- Root `Cargo.toml`: the one `[workspace.dependencies]` line. `Cargo.lock`: only the new package and the desktop edge.

## Deviations (with reasons)

1. **No Rust command wrappers on iOS** (recon §7 proposed `src/commands.rs` → `run_mobile_plugin`). Tauri 2.12 forwards a plugin command that no Rust handler claims straight to the native plugin as lowerCamelCase (`tauri-2.12.5/src/webview/mod.rs#L2127-L2158`), and it initialises `Channel` arguments on the way. So the Rust invoke handler is registered on desktop only, and the eight commands reach Swift directly. ACL still applies (`ink:default`). There is no `register_listener`/`remove_listener`: events travel on the `onEvent` channel, not `trigger`.
2. **The overlay mounts at `attach`, not in `load(webview:)`** (§9 wording). `load` only keeps the web view (weakly). The §6 table says `attach` "mounts the overlay" and `detach` removes it, and mounting at load would move PencilKit's recogniser onto the web view while no whiteboard is open.
3. **Route B is built** (contract: "only if A fails on the spike"). The spike needs a real Pencil and cannot run tonight, so B is ready rather than missing. Selection: route A, unless A cannot be installed (B is used and an `error` event says so), or `UserDefaults` `InkRoute = "B"` (e.g. launch argument `-InkRoute B`) forces B for device testing.
4. **Stroke points are CSS px of the layout viewport**, converted through the web view's scroll view at hand-over. The contract says "web-view points"; the two are identical with no inset and zoom 1. On the simulator the inset is 32 pt at the top, so raw points would shift every stroke by 32 px.
5. **The plugin does not act on Pencil tap/squeeze itself.** It reports `{ kind: 'pencil', gesture, action }`; JS owns the tool state and answers with `set_tool` / `set_picker_visible`, so the action is applied once.
6. The desktop plugin is not registered in the macOS app (registration point §9 = the mobile `configure` only, and `capabilities/default.json` is not B5's). A desktop `invoke('plugin:ink|attach')` rejects "plugin not found", and B4's wrapper maps that to `null`, as it would for `native: false`.

## For other builders / the orchestrator

- **B4 (`lib/ink-native.ts`, `native-ink.ts`):**
  - `NativeStroke.width` and the `tool` event's `width` are **screen points** (the picker's unit); world width = `width / view.zoom`. `set_tool` takes the same unit; the overlay draws it as given.
  - `pts` x/y are CSS px of the viewport (deviation 4): `world = (pt − (view.tx, view.ty)) / view.zoom` holds as the contract says.
  - `tool` events for the eraser carry `colour: "#000000"`.
  - Retries come with a **new** `batch` number and the same `seq`.
  - `tool` is never `'eraser'` in a stroke.
- **Orchestrator:**
  - The first iOS build copies the Tauri Swift API into `crates/tauri-plugin-ink/.tauri/` (gitignored).
  - Proof of link: `nm -gU …/theuth.app/theuth | grep init_plugin_ink`.
  - Overlay proof on the simulator: open a whiteboard; `attach` should answer `{ native: true, route: "A", os: "26.0" }`; the picker appears at the bottom.
- PencilKit may handle a Pencil double-tap itself while its picker is active (switching to the eraser), in addition to our `pencil` event. If B4 also toggles, the tap could cancel out. **Unverified** (needs a Pencil 2/Pro).
