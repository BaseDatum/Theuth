## Bugs found and fixed (`137e7656`, `0477f072`)

1. **`/data` root-owned → `first_run: Permission denied`.** The SDK's pre-boot file `/data/config.yaml` recreates `/data` as `root:root 755`, shadowing the image's `chown engine`; `runuser -u engine … t --secret-list` got EACCES. `bringup.rs` `config` step now runs `mkdir -p /data && chown -R engine:engine /data` unconditionally (before, only when the file was missing).
2. **`config: vncpasswd: Failed to connect to bus`.** `boot()` returns once `/proc/1/comm == systemd`, ~0.5 s after activation; systemd's D-Bus socket comes later, so `systemctl restart xvnc` failed on the second-ever create. The command now retries `systemctl restart xvnc` every 0.2 s for 20 s. (`sandbox_retry` resumed from `config` and reached `ready` in 15.1 s; retry first takes an `auto-retry` disk snapshot, 158 ms.)
3. **Ceilings above the host accepted, VM unbootable.** `sandbox_resize {max_memory_mib: 65536}` on a 64 GiB host was recorded as `next_start`; the next boot (recreate for pending shares) failed with `VM enter: build error: start: build_microvm: Internal(Vm(SetUserMemoryRegion(MemoryMap)))` and the record sat in `starting` with the VM removed. `check_ceilings` in `Create` and `Resize` refuses `max_memory_mib >= host RAM` and `max_cpus > cores` (`"max_memory 65536 MiB exceeds this host's 65536 MiB"`, `"max_cpus 32 exceeds this host's 16 cores"` — both observed live). `resize_validation_and_outcome` test updated (mock host 8 cores / 16 GiB). 65536 = the host's RAM exactly is what the brief asked for; the design's default ceiling is host/2, and the safe bound below "all of it" is not measured — `>=` is the smallest rule the evidence supports.

### Bugs found and fixed by F5 (beside 10)

11. **Fresh-vault migration race in the guest.** The image enables `theuth.service` at boot, so the guest engine and the host's `first_run` (`t --secret-list` as `engine`) both ran `sqlx::migrate!` on a fresh `/data/secrets.sqlite` in the same second; sqlx lists applied rows and creates tables in separate statements, so one side failed with `table vault|secret_requests already exists`. Lost by the daemon (check 2: no vault in the guest → no adoption → Z2-style orphan) or by the CLI (check 4: `failed{first_run}`). Fixed at the root in `secrets::store::open` (migrator inside `BEGIN IMMEDIATE`, `c2f123c7`) and belt-and-braces in the `daemon` step (`systemctl restart theuth` after `first_run`, `c8813bb2`), which also puts the engine on the re-owned `/data` and the final `t` deterministically (before, the boot-started daemon might have started before the `config` step's `chown` — the timing-dependent tail of smoke bug 1). Cost: none measurable (create → ready 13.9–15.1 s, Z2 15.4 s).
12. **Guest mode never selected.** The host writes `sandbox: { enabled: false, guest: {…} }` (§5.3), but `config::mode()` returned `Disabled` before looking at `guest`, so no VM ever registered the guest prompt block (F2's masked-field sentence) or `sandbox_takeover`; Z2's "not observable" was this, not the old guest binary. `guest` now wins over `enabled` (`89a37fdd`, `mode_follows_the_switches` updated).
