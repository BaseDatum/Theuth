The vault holds named, versioned secrets: provider API keys, web search keys,
Slack tokens, and anything you add. The agent references a secret as
`{{secret:NAME}}` in a tool argument; the harness substitutes the value when
the tool runs and scrubs it from the result. No tool returns a value, and no
model-facing surface ever shows one.

## Storage and keys

| Item | Where |
|---|---|
| Vault | `<data_dir>/secrets.sqlite`; each value is encrypted with XChaCha20-Poly1305 under a vault key, with the row id as associated data |
| Vault key | encrypted under an engine key; stored in the vault's local metadata |
| Engine key | the OS keychain (service `theuth`, account `secrets:<absolute data_dir>`: macOS Keychain, Linux Secret Service, Windows Credential Manager) or `<data_dir>/secrets.key` (base64, mode 0600) |

`secrets.key_store` in `config.yaml` chooses:

| Value | Behaviour |
|---|---|
| `auto` (default) | keychain when one answers; if the keychain backend is unavailable, fall back to `secrets.key` with the warning `no keychain available: …; vault key in <data_dir>/secrets.key (mode 0600)` |
| `keychain` | keychain only; fail if unavailable |
| `file` | `secrets.key` only; never touches the keychain |

A corrupt keychain item (not 32 bytes) is a hard error, not a fallback. If
the vault cannot be opened the harness still runs: the log says
`secrets vault unavailable: …` and provider keys come from `/login` and the
environment only. Losing the engine key (or the keychain item) loses every
secret; back up `secrets.sqlite` together with `secrets.key` or the keychain
item.

Two legacy inputs are migrated on open: a single-file `secrets.vault` is
imported and renamed `secrets.vault.migrated`, and a flat `credentials.yaml`
(`name: value`) is imported and deleted.

## Names and versions

Names are `[A-Za-z0-9_.-]{1,64}`, case-sensitive. Names containing `/` are
reserved for the harness's own rows (`oauth/…`, `mesh/…`, `sandbox/…`) and
are never listed or expandable.

Every write (`set`, a `secret_request` answer, `secret_capture`, `restore`)
creates a new version; the five most recent versions are kept and older ones
are deleted. Writing a value identical to the current one is a no-op.
Restoring copies an older version to the top as a new version (source
`restore v<N>`), so history is never rewritten. Deletion is hard: every
version of the name is removed.

Names used by convention:

| Name | Used for |
|---|---|
| `anthropic`, `openai`, `gemini`, `together`, `fireworks`, … (genai adapter names) | provider API keys; the name is the adapter, not the catalog id (`google/*` models use `gemini`, `togetherai/*` use `together`, `fireworks-ai/*` use `fireworks`); a vault key beats `/login`, which beats the provider's env var |
| `<gateway>` | the key of a named OpenAI-compatible gateway from `providers.yaml` |
| `opencode` | the built-in Zen provider (`opencode/<model>` ids); else `OPENCODE_API_KEY`. Not a gateway: `/provider add opencode` is refused |
| `openrouter` (or genai's `open_router`) | the built-in OpenRouter provider (`openrouter/<model>` ids); else `OPENROUTER_API_KEY` / `OPEN_ROUTER_API_KEY`; `agent.openrouter.*` tunes headers and routing |
| `bedrock_api` | a Bedrock bearer key (else `BEDROCK_API_KEY` / `AWS_BEARER_TOKEN_BEDROCK`); an explicit `agent.aws_profile` wins over it |
| `firecrawl`, `brave`, `openserp`, `xai`, `github` | web search providers and GitHub search |
| `slack_bot`, `slack_app` | Slack tokens written by `t --slack-setup` |
| `a2a_<peer>_outbound`, `a2a_<peer>_inbound` (any names you choose) | A2A credentials referenced from `a2a/peers.yaml` |

`/model` lists only providers that are "configured": a vault key, a gateway,
a login, or the adapter's env var.

## The placeholder

```text
{{secret:NAME}}        current version
{{secret:NAME:-1}}     previous version, up to :-4
```

Placeholders are recognised in every string value of a tool's arguments,
nested arrays and objects included (object keys are not expanded): a shell
command, a header, a URL, file content, an MCP tool's field, a shell `env`
map. Expansion happens inside the harness after the approval gate; the
transcript, the approval card and the model see the placeholder only. An
unknown name fails the call with `unknown secret NAME; secret_list shows the
names`; a missing version with `NAME has N versions; :-K does not exist`.

Rules around the gate:

- A call that mentions a placeholder is raised to at least `ask`, even for a
  `read_only` tool, unless approvals are off for the session or globally.
  `deny` stays `deny`.
- Tools whose arguments are literal sources or queries do not expand
  placeholders at all: `app`, `task_draft`, `agent_draft`, `search`,
  `code_*`, `project_profile`, `sandbox_*`, `secret_request_form`,
  `desktop_handoff`. An `app` source keeps `{{secret:…}}` literally and the
  bound tool resolves it when a button is pressed.
- In the Python runtime, `http_request` accepts placeholders in headers only
  (`http_request: secret placeholders are allowed in headers only`), and
  cpython sensors refuse them.
- MCP files expand `{{secret:…}}` in `command`, `args`, `env`, `url` and
  `headers` when a server connects; see [MCP](/docs/reference/mcp).

```sh
# the model writes this; you see exactly this in the approval card
curl -H "Authorization: Bearer {{secret:github}}" https://api.github.com/user
```

## Scrubbing

After every tool call the harness replaces, in the text and structured
output, every exact value and every standard-base64 encoding of every kept
version of every secret with its placeholder (`{{secret:NAME}}`, or
`{{secret:NAME:-N}}` for an older version). Shell job output is scrubbed per
chunk while streaming and once more exactly over the whole render when the
job ends; the command shown in job cards and terminal viewports is scrubbed
too; so are Python runtime output, vision questions and sensor errors.

Values shorter than 8 characters are **not** scrubbed; `secret_capture`
warns `value shorter than 8 characters cannot be scrubbed from tool output`
when it stores one.

## The model's tools

All five are `read_only` and none returns a value. They exist only while
`secrets.tools` is `true`.

| Tool | Does |
|---|---|
| `secret_list` | names, versions, notes and timestamps; empty vault: `no secrets; the user adds them with /secrets add, Settings › Secrets or t --secret-set, or call secret_request` |
| `secret_request{name, note}` | asks you to type a value into a masked field; receipt `stored NAME vN`, `declined`, or `no answer after N s` (`secrets.request_timeout_secs`, 1800) |
| `secret_request_form{title, fields}` | several named fields at once, each optionally masked |
| `secret_capture{name, tool, args, pattern?, replace?}` | runs another tool quietly and stores its output (or the first match of `pattern`) as a secret without showing it to the model; refuses an existing name unless `replace: true` |
| `secret_restore{name, back}` | makes version `back` (1–4) current as a new version |

`secrets.tools: false` removes the tools and the prompt block, leaves
`{{secret:…}}` literal and scrubs nothing; the vault, `/secrets` and the
harness's own keys keep working.

## Entering a secret

| Surface | How |
|---|---|
| CLI | `t --secret-set NAME` prompts twice without echo on a TTY (`values differ` on mismatch); from a pipe it reads the first line of stdin: `printf %s "$KEY" \| t --secret-set anthropic`. `--secret-note <text>` attaches a note. `t --secret-list` prints `key: keychain\|file` and one line per name with version count and note; `t --secret-rm NAME` deletes |
| TUI | `/secrets` opens the menu (`a` add, `r` replace as a new version, `h` history and restore, `d` delete after typing the name); `/secrets add [name]`, `/secrets rm <name>`, `/secrets restore <name> [n]` skip the menu. Values are typed into a `•`-masked field |
| Desktop | Settings › Secrets with a password input; a `secret_request` from the agent appears as a masked card |
| Slack, Signal, Telegram | a `secret_request` posts a notice only; the value is never entered there, because it would sit in the channel's history |
| RPC | `list_secrets`, `set_secret`, `restore_secret`, `delete_secret`, `answer_secret`, `secret_requests_list` |

The desktop header and `/secrets` title show which key store is in use
(`key: keychain` or `key: file`).

## Rotation

Rotation is a new version: `t --secret-set NAME` again, `r` in `/secrets`, or
a `secret_request`. The previous value stays reachable as `{{secret:NAME:-1}}`
during the switch and falls off after five newer versions. There is no
command to rotate the engine key; pairing a new engine into a mesh re-seals
rows under a shared mesh key automatically. There is no export command:
a backup is the `secrets.sqlite` file plus the engine key.

## Limitations

These follow from the design and are worth knowing before relying on the
vault:

- **The destination sees the value.** Scrubbing protects the transcript, not
  the world: a shell command receives the real value on its command line or
  environment, `write_file` with a placeholder writes the real value to
  disk, and an HTTP request sends it. The model can still direct a value
  somewhere observable; the approval prompt is your check.
- **Only exact and base64 forms are scrubbed.** Hex, URL-encoding, reversed
  or split values pass through. A value split across two streaming chunks
  escapes the live scrub and is caught only by the final pass.
- **Short values are not scrubbed** (fewer than 8 characters).
- **`key_store: file`** leaves the engine key as a readable file beside the
  vault; anyone with your user account can decrypt it. Prefer the keychain.
- **Replication.** Vault rows replicate between the engines of your mesh;
  concurrent writes to the same name on two engines resolve last-writer-wins.
- **Login grants are hidden rows.** Provider `/login` tokens are stored as
  reserved `oauth/<provider>` rows of the same vault: never listed, never
  expandable by placeholder. Legacy `<data_dir>/oauth/<provider>.json` files
  are migrated in and renamed `.migrated`; MCP server tokens stay as files
  under `oauth/mcp/`.
