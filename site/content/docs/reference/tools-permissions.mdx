Every tool call carries a risk class. `tools.policy` maps each class to an
action; `ask` puts a prompt in front of you and the call waits. This page
lists what the harness ships, how the gate decides, and how to answer or
turn off prompts on each surface.

## Risk classes

| Risk | Meaning | Default action |
|---|---|---|
| `read_only` | reads, searches, screenshots, questions to you | `allow` |
| `mutating` | writes files, sends input, changes state that can be undone | `ask` |
| `destructive` | runs arbitrary commands, deletes, removes servers or skills | `ask` |

The risk is fixed per built-in tool at compile time. The only per-tool
override is for MCP tools through `mcp/config.yaml` (below), where a fourth
value `off` exists; `off` is a gate, not a risk, and means "not registered at
all".

## Built-in tools

Names are exact. Risk is the default class; `direct` marks tools the model
always sees as a tool definition even with the Python runtime on (the rest are
callable as `async` functions inside `python`).

### Shell, jobs, files (tools plugin)

| Tool | Risk | Notes |
|---|---|---|
| `shell` | destructive | brush bash in-process at the session cwd; output within `tools.job_grace_secs` comes back inline, otherwise a job id and a later `<job_result>` |
| `start`, `send`, `screen`, `wait` | destructive, mutating, read_only, read_only | a command on a 120×40 pseudo-terminal (`$SHELL -lc`); `ready: {log, port, host, timeout}` waits for readiness; `wait` defaults to 30 s, max 120 |
| `jobs`, `cancel_job` | read_only, mutating | list and kill; `cancel_job` replies `killed <id>; no <job_result> will follow` |
| `read_file`, `list_dir`, `grep`, `glob` | read_only | |
| `write_file`, `edit` | mutating | |
| `remind_me_in` (direct), `cancel_reminder` | read_only | ceiling `tools.reminder_max_secs` |
| `ask_user` (direct) | read_only | multiple-choice questions; gives up after `tools.ask_timeout_secs` |

Shell state (cwd, variables, functions) persists per session. There is no
sandbox around `shell`: it runs on the host as you. Isolated execution is
what [sandboxes](/docs/automation/sandboxes) are for.

### Turning groups off

There is no per-tool disable list for built-ins. Groups come and go with
their plugin's switch in `config.yaml`: `secrets.tools`, `knowledge.enabled`,
`web.enabled`, `scrape.enabled`, `codeindex.enabled`, `browser.enabled`,
`computer.enabled`, `documents.enabled`, `artifact.enabled`, `app.enabled`,
`schedule.enabled`, `sandbox.enabled`, `voice.enabled`, `talk.enabled`,
`meeting.enabled`. The communication trio needs agent messaging on (`agent.communication`; unset = on once a machine is paired).
MCP tools are switched individually in `mcp/config.yaml`.

## The gate

For every call the registry computes an action in this order:

1. If the session (or an ancestor) has a subagent cap and the tool's risk is
   above it: `deny`.
2. `tools.policy.<risk>`.
3. If any string argument contains a `{{secret:` placeholder and the tool
   consumes secrets: at least `ask`. The approval card shows the
   placeholder; the value is substituted only after approval.
4. If the result is `ask` and approvals are off for the session: its own
   pin, else the nearest ancestor's, else `tools.approvals` on the engine
   that owns the session. Off: `allow`.

`deny` is never rewritten by step 4. What the model sees when a call does not
run:

| Situation | Tool result |
|---|---|
| policy `deny` | `<tool>: denied by policy` |
| you denied | `<tool>: denied by user` |
| no answer within `tools.approval_timeout_secs` (300) | `<tool>: approval timed out` |
| subagent cap | `<tool>: denied: subagent is capped at <risk>` |
| communication off | `<tool>: communication_disabled: <why>` |
| hidden or unknown tool | `unknown tool: <name>` |
| turn cancelled while waiting | `<tool>: cancelled before it ran` |

Policy configuration:

```yaml
tools:
  policy:
    read_only: allow
    mutating: ask
    destructive: ask      # deny on an unattended server
  # approvals: false      # never prompt for `ask`; `deny` still denies
  approval_timeout_secs: 300
```

## Approvals

### Scope

| Command | Scope | Persisted |
|---|---|---|
| `/approvals off` | this session and every subagent under it (its pin: `off`) | yes: on the session; it survives a restart and a move to another machine |
| `/approvals on` | this session and its subagents (pin `on`): asks even when `tools.approvals` is false | yes: on the session |
| `/approvals off always` | every session | yes: `tools.approvals: false` |
| `/approvals on always` | every session | yes: `tools.approvals: true` |

The same command exists on Signal and Telegram (`/approvals on|off [always]`, owner only;
Telegram's reply is a panel with the three states as buttons) and Slack
(`/theuth approvals on|off [always]`, owner only; its settings modal offers
the same three states), and the desktop app's Settings dialog has an
approvals switch. In the desktop chat's **⋯**, **Approvals ▸** has On, Off and
**Machine default (on|off)**, which clears the pin. For a chat owned by
another machine the pin and the default are that machine's, and a relayed
card reads `<engine> asks: <tool>`. Children inherit the parent's pin,
hidden tools and cap.

### Answering

| Surface | Allow | Deny |
|---|---|---|
| TUI modal | `y` | `n` or `Esc`; `o` opens the child session that asked |
| Print mode / piped stdin | a line `y` | a line `n`; stdin closed = deny (`denied: stdin closed`) |
| Desktop | Allow button on the card | Deny button |
| Slack | **Allow** block button | **Deny**; the card updates to `✅ tool allowed`, `❌ tool denied` or `⌛ tool timed out (denied)` |
| Signal | react 👍 / ✅ / 👌, or `/approve <code>` | react 👎 / ❌ / 🚫, or `/deny <code>` |
| Telegram | **Allow** inline button | **Deny**; the card updates to `✓ tool allowed by <name>`, `✗ tool denied` or `⌛ tool timed out` and the buttons collapse into one disabled verdict |
| ACP editors | the client's `allow` option | anything else |

Slack sessions started elsewhere send their approvals to the owner's DM when
`slack.approvals: all`, and nowhere when `threads`; Telegram does the same with
`telegram.approvals` and the owner's chat. On Signal, approvals for unbound
sessions go to the owner.

### Apps

An [app](/docs/workspace/apps) you click is different: **the press is the
approval.** A `Mutation` binding behind a button runs on click with no card,
a tool the policy would ask about becomes a Load/Refresh button whose press
is the consent, and a policy-denied tool is shown unavailable. Timer and load
reads never run mutations.

## MCP gates

MCP tools default to the risk their server annotates: `readOnlyHint: true`
is `read_only`, `destructiveHint: true` is `destructive`, anything else
(including no annotations) is `mutating` and therefore prompts. Override per
server or per tool in `<data_dir>/mcp/config.yaml`:

```yaml
servers:
  kubernetes:
    risk: read_only          # every tool of the server unless a tool line says otherwise
    tools:
      pods_delete: destructive
      helm_uninstall: off    # not registered at all
  teams:
    risk: off                # server not even started
```

Resolution order is tool line, then server line, then annotations. The
`/mcp` menu writes this file (Space cycles the risk, Backspace resets it,
Enter asks whether to hide a server for this session or turn it `off` for
good); hand edits are picked up within a second. Details in
[MCP](/docs/reference/mcp).

## Subagents

Configured under `agent.subagents` (defaults `max_depth: 1`,
`max_concurrent: 8`, `max_runtime_secs: 600`, `reply_timeout_secs: 120`):

- A session at depth ≥ `max_depth` gets `subagents are not available at depth N`.
- At most `max_concurrent` child turns run at once; further spawns queue.
- A child turn over `max_runtime_secs` is stopped and its result is prefixed
  `[timed out after Ns, stop=…]`.
- `spawn_subagent{tools: read_only|mutating}` installs a cap: the child and
  its descendants are denied anything above it and do not even see those
  tools in their list. `destructive` means no cap. `send_message` is exempt
  from caps so a capped child can still report back.
- Children inherit the parent's approval bypass; their approval prompts
  surface in your UI like the parent's.
- Scheduled runs set `approvals: false` in the schedule file to run
  unattended; see [Schedules](/docs/automation/schedules).

More on spawning and ACP harnesses in [Delegation](/docs/automation/delegation)
and [Agents](/docs/automation/agents).

## Secrets in tool calls

`{{secret:NAME}}` in any string argument of a secret-consuming tool is
swapped for the vault value after approval and scrubbed from the output
(exact value and its base64, values of 8+ characters). Tools that take
literal sources or queries (`app`, `task_draft`, `agent_draft`, `search`,
`code_*`, `project_profile`, `sandbox_*`, `secret_request_form`,
`desktop_handoff`) do not expand placeholders and do not raise the gate. See
[Secrets](/docs/reference/secrets).
