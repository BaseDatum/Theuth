A skill is a markdown file the model can pull into context when it is
relevant. The system prompt lists every skill's name and one-line
description; the model calls `load_skill` to receive the body. Nothing is
"installed" or "enabled": a skill is in context until the next compaction or
`/clear`.

## Where skills live

`<data_dir>/skills/`, walked recursively on every model call. There is no
watcher and no cache: a change on disk is in the next system prompt. A
missing directory means no skills.

| Path | Is |
|---|---|
| `<dir>/SKILL.md` | one skill named after `<dir>`; the rest of `<dir>` is supporting files and is not walked further |
| any other `*.md` | one skill named after the file stem |
| `README.md`, `LICENSE.md`, `CHANGELOG.md`, `CONTRIBUTING.md` (any case) | ignored |
| `.git/`, other extensions | ignored |
| `learned/`, `retired/` (top level) | not skills: dreaming's learned notes per skill and the skills it retired (see [Learning](#learning)) |

Subdirectories are organisation only and do not affect names. Duplicate
names: the last file in path order wins and the log warns
`duplicate skill name, last wins`. An unreadable file is skipped with a
warning.

There are no project-local skills: the harness reads `<data_dir>/skills/`
only, not a `.theuth/` or `AGENTS.md` in the working directory. The
top-level `*.md` skill files replicate to the other engines of your
[mesh](/docs/automation/mesh); directory skills, clones and `learned/` do
not.

## Front matter

Optional YAML between `---` delimiters at the top of the file:

| Key | Default | Effect |
|---|---|---|
| `name` | file stem, or directory name for `SKILL.md` | the name in the index and in `load_skill` |
| `description` | first non-empty line of the body | one line shown in the index |
| `always` | `false` | `true`: the body is inlined into every system prompt instead of being indexed |
| `origin` | none | `dreaming` marks a skill the nightly routine made; such skills are listed after the others and only they can be retired by it |

Unknown keys (`license`, `allowed-tools`, `metadata`, …) are ignored, so
third-party `SKILL.md` repositories load as they are. Invalid front matter
logs a warning and the whole file is used as the body. Names must match
`[a-z0-9][a-z0-9._-]*` when written by the harness.

```markdown
---
name: commit
description: Write a conventional commit message for staged changes
---

Run `git diff --cached`, then write a message in the form
`type(scope): subject`, subject under 50 characters, body only when the
"why" is not obvious from the diff.
```

```markdown
---
always: true
---
Never run `git push`.
```

## What the model sees

The system prompt is assembled on every call in this order: the built-in
header, `prompt.md`, the bodies of `always` skills (name order, blank-line
separated), then the index:

```text
## Skills
Call `load_skill()` (python: `await load_skill(name="…")`) to get a skill's full instructions.
- commit: Write a conventional commit message for staged changes
```

`load_skill{name}` returns the body; for a `SKILL.md` skill it appends
`files (under <dir>):` and the relative paths of the supporting files, which
the model reads with `read_file`. When `learned/<name>.md` exists, its
bullets are appended under `## Learned (dreaming)`, in `load_skill`, in
`always` bodies and in what an external harness receives. An unknown name
returns `no skill named <name>`. The index is in name order. The TUI status
line lists the skills currently in context (`skills: commit, review`) and the
`/skills` picker marks them `●`. A capped contact session (an inbox answering
someone outside your mesh) gets no skills.

`prompt.md` and an `always` skill are indistinguishable to the model;
`prompt.md` is the one place for "how I want you to behave", skills are the
reusable pieces. `/prompt` shows the assembled prompt.

## Handing a skill to the model

| Where | How |
|---|---|
| TUI | `/skills` then Enter on a row; or `/<skill> [words]` (for example `/commit fix the typo`); `s` shows the body |
| Desktop | the Skills page (`/skills`) with Use, New skill, Repos and an `always` switch for local skills; the composer's `+` › Skills picker (searchable); the same chat slash commands. Every pick (and every `/skill:<name>`) adds a chip, so one message can carry several skills |
| Slack, Signal, Telegram | `/theuth skills` and `/skills` list and manage; the model still loads skills itself with `load_skill` |
| RPC | `use_skill{name, args}`; `use_skills{names, args}` for several at once |

Using a skill injects `<skill name="…">body</skill>` plus your words as your
input: it starts a turn when the model is idle or steers the running one.
Several skills are one input, their blocks in the order named, then your
words. The body is in context until compaction or `/clear`, not permanently.

## Git repositories

A skill repo is a plain clone directly under `skills/`; the clone is the
record, there is no manifest, registry or lock file. Skills found inside show
`[repo-name]` in `/skills` and refuse `add_skill` / `remove_skill` (edit
upstream and sync, or remove the repo).

```text
~/.theuth/skills/
  commit.md                   loose skill
  review/SKILL.md             directory skill
  anthropics-skills/          clone: /skills add https://github.com/anthropics/skills
    .git/
    skills/pdf/SKILL.md       indexed, repo = anthropics-skills
    README.md                 ignored
```

| TUI | Tool | Does |
|---|---|---|
| `/skills` | `load_skill` | picker; Enter uses, `s` shows |
| | `add_skill` (mutating) | writes `skills/<name>.md` with `name`, `description`, `always` front matter |
| `/skills rm <name>` | `remove_skill` (destructive) | deletes a local skill file or `SKILL.md` directory |
| `/skills add <url>` | `add_skill_repo` (mutating) | `git clone --depth 1 <url> skills/<name>`; default name = repo basename without `.git`; returns the skills found |
| | `remove_skill_repo` (destructive) | removes `skills/<name>` if it has a `.git` |
| `/skills sync` | `sync_skills` (mutating) | `git pull --ff-only` in every repo; per repo `updated`, `unchanged` or `error: …` |

Git is your `git` binary; without one the repo operations report that and
everything else works. The same operations exist over RPC (`list_skills`,
`load_skill`, `use_skill`, `use_skills`, `add_skill`, `remove_skill`, `add_skill_repo`,
`remove_skill_repo`, `sync_skills`), on Slack as
`/theuth skills [add <url>|rm <name>|sync]` and on Signal and Telegram as
`/skills [add <url>|rm <name>|sync]`.

## Bundled skills

On every start the binary rewrites the skills it owns when their text
differs, so they always describe the running version; edits to them are
overwritten, everything else in `skills/` is never touched:

| File | Purpose |
|---|---|
| `harness.md` | the model's manual for this data dir: layout, config keys, vault, MCP gates, skills, what only the user can do |
| `visualize.md` | drawing in replies with json-render and Mermaid blocks, and when to show a live HTML page instead |
| `pdf.md` | front matter, page breaks and Typst for `show` with a `.pdf` name |
| `loops.md` | schedules that loop until done: retry loops and supervisors that fan out to subagents |
| `routines.md` | designing or editing a routine (clock, sensor or loop) and proposing it as a draft card |
| `apps.md` | OpenUI Lang, the component catalog and examples for the `app` tool |
| `board.md` | drawing a board: a long-form, scrollable explanation of code with diagrams, code links and a read-back |
| `decide.md` | classifying many items with the local decision model (`decide_many`) |
| `double.md` | reading and respecting the owner's double: its chip, the L0 to L3 ladder, the `double_*` functions |
| `native-apps.md` | driving apps by script (`applescript`, `shortcuts`, `powershell`) with recipes and verify steps |
| `cells.md` | writing cells and runbooks the user runs with one press |

Plugins write three more when they start:

| File | Written | Purpose |
|---|---|---|
| `autoresearch.md` | while `autoresearch.enabled` (default on); binary-owned | setting up a study: interview, write and run the benchmark once, draft it, then status and control; one section per study kind |
| `dreaming.md` | while `dreaming.enabled` (default on); binary-owned | the nightly routine's own instructions |
| `codeindex.md` | when the code index starts | the `code_*` functions; a copy you edited is kept, never overwritten |

`apps.md` is written even when `app.enabled` is `false`.

## Learning

The model writes a skill itself with `add_skill` when you ask it to remember
a procedure. Durable facts belong in [knowledge](/docs/workspace/knowledge)
(`knowledge_put`, harvested automatically); reusable instructions belong in
skills.

[Dreaming](/docs/workspace/knowledge#dreaming), the nightly routine, also
tunes skills, within bounds:

- It never edits a skill file, `prompt.md` or any text you wrote. Its
  lessons go to a sidecar, `skills/learned/<skill>.md`: at most 12 bullets
  of at most 140 characters, each with helpful and harmful counts, the cases
  it came from and a date. The sidecar is appended to the skill's body (see
  above).
- An edit is written only when it passes a replay gate over held-out cases
  of your past corrections; a rejected one is logged with the gate's numbers
  and not applied. A bullet that three later cases contradict is retired.
- A skill it made (`origin: dreaming`) that nobody loaded for 45 days is
  moved to `skills/retired/`. It cannot retire a skill you wrote.
- Every night's changes are backed up first and undone in one action, the
  whole night or one group (`skill:<name>`, `edits`).

## External harnesses

When a task is delegated to an ACP harness (`spawn_subagent{agent}`), the
`always` skills plus any named in the call's `skills` list are written for it
under `<cwd>/<skills_dir>/<name>/SKILL.md` (default `.agents/skills`, which
omp, OpenCode, Codex and Gemini read; set `.claude/skills` for Claude Code). A
directory that already exists is yours and is skipped; inside a git repo each
new directory is added to `info/exclude`. The child also gets an MCP shim,
`t mcp --session <id>`, with `list_skills`, `load_skill`, `send_message`
and the text tools `read_file`, `edit`, `move_text`, `copy_text`, `indent`
and `clip`. `acp/agents.yaml` controls this per agent with
`skills: true|false`, `skills_dir:` and `mcp: true|false`. See
[Delegation](/docs/automation/delegation).
