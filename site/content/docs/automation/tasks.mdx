Tasks are theuth's unit of delegated work: a title, a markdown brief, one owner (an agent or you), a reviewer, a priority and a thread that logs every change. You use them when work should outlive a single chat turn: something an agent should pick up at its desk, something that waits on another task or on your decision, or something you want to review before it counts as done. Routines with an `agent:` line and agent hires file tasks on the same board. Tasks live in `~/.theuth/tasks.sqlite` and replicate across mesh engines.

## Prerequisites

- A running engine: the desktop app (it starts `t --headless` for you), or `t --serve` / `t --headless` for the terminal and channels. The board, the tools and `t tasks list` all talk to that engine.
- For an agent to actually work a task you need at least one roster agent with a desk. See [Agents](/docs/automation/agents). Tasks owned by **you** are tracking only; nothing runs on them.
- No config is required. The `tasks:` section of `config.yaml` tunes timers, caps and ordering (table below); the escalation wait is `roster.decision_wait_secs`.
- Every task write the model makes (`task_create`, `task_update`, `task_move`, …) is a **mutating** tool call and is subject to `tools.policy.mutating` (default `ask`). `task_draft`, `task_inbox` and `task_waiting_on_user` are read-only. See [Tools and permissions](/docs/reference/tools-permissions).
- The task tools can be switched off as a group: **Settings › Tools › Builtins**, category **Tasks** (every `task_*` tool plus `escalate`), either **Off here** (this chat and its subagents) or **Off always** (`tools.builtins.disabled` in `config.yaml`).

## How it works

### States

A task is always in exactly one of seven states:

| State | Meaning | Board chip |
|---|---|---|
| `backlog` | Filed, nothing happens. No wake, no placement, not in any inbox. | `not started` |
| `todo` | Started: the owner is woken and the task is in its inbox. | `queued for ‹agent›'s desk` (agent owner) / `todo` |
| `doing` | Checked out by a session that is working it. | `at ‹agent›'s desk · open session` while checked out; `queued for ‹agent›'s desk` when sent back and not yet picked up; for your own tasks `in progress · open session` / `in progress` |
| `review` | Owner says it is finished; the reviewer judges. | `review` |
| `blocked` | Waiting on at least one blocker (task, decision, person, or a system reason). | `blocked` |
| `done` | Closed by the reviewer. Final. | `done` |
| `cancelled` | Dropped. Final. | `cancelled` |

There is **no draft or approved state**. Proposed tasks exist only as cards in chat until you approve them (see the walkthrough below).

### Who may move what

The ledger enforces one transition table for every surface (chat tools, desktop, Inbox, CLI, MCP, routines). "You" means the user, who may act for anyone; an agent may act only for itself.

| From → to | Who | Notes |
|---|---|---|
| `backlog` ↔ `todo` | anyone | The only drag on the board. `backlog → todo` wakes the owner. |
| `backlog` → anything else | refused | `a backlog task is started first (todo), then checked out` |
| `todo` → `doing` | the owner, via `task_checkout` only | `todo → doing is task_checkout` |
| `doing` → `review` | owner only | Clears the checkout; wakes the reviewer. |
| `doing` / `todo` → `blocked` | anyone | Needs at least one blocker: `blocked needs a blockers entry`. |
| `blocked` → `doing` / `todo` | owner, once `blockers` is empty | `task_checkout` also takes a `blocked` task with no blockers left. Your move first strips system blockers (`no continuation`, and anything of the form `prefix:value` except `decision:`, such as `engine:*`, `sandbox:*`, `person:*`, `left:*`); `decision:*` and task-id blockers stay and the refusal names them (`still blocked on …; a decision needs its answer`). |
| `review` → `doing` / `todo` (send back) | reviewer only | Wakes the owner with your notes. |
| `review` → `done` | reviewer only | An agent that is its own reviewer may close only when the task has a `done_when`; otherwise: `done needs a reviewer other than the owner (self-review is only allowed against an explicit done_when)`. |
| any open state → `cancelled` | anyone | |
| `done` / `cancelled` → anything | refused | `task is done` / `task is cancelled` |

Anything not in the table answers `X → Y is not a transition`, and `task_move` wraps every refusal as `<from> → <to> is not allowed (<reason>); from <from> you may move to: a, b`.

The reviewer defaults to the owner's manager (`reports_to` in the agent file); an agent whose line ends at theuth, and every task you own, is reviewed by you. If an agent sends a task with no `done_when` to review and the reviewer would be itself, the reviewer is rewritten to its manager. Reassigning a task to its own reviewer moves the reviewer up to the new owner's manager.

### Done because

A close carries a reason, written to the thread as `done because: …`. Agents must say which: `criteria_met` (needs a `done_when`: `criteria met needs a done_when on the task`), `intent_met`, or `follow_ups_filed` with the ids of existing follow-up tasks. An agent that gives none is refused with `done needs done_because: criteria_met | intent_met | follow_ups_filed{tasks}`. A self-reviewer may claim only `criteria_met`. When **you** mark a task done (task detail, Inbox, `task_move` over RPC or MCP) the reason is `intent_met`; there is no field for another.

### Priority

Every task has a priority: `urgent`, `high`, `medium` (the default) or `low`. Only you set it. An agent's `task_create` or `task_update` that carries `priority` is refused with `priority is the user's to set; say why in task_note and the user decides`. You set it from the **Priority** select on a task's review or decision screen in the Inbox, by asking theuth in your own chat (your chat acts as you), or through `task_update` over RPC or [MCP](/docs/reference/mcp). The task detail page and the New task sheet have no priority field.

One rank orders both an agent's wake dispatch and the task's weight in the Inbox: `tasks.project_order` dominates (each project's place in the list is worth 100), and the priority weight breaks ties (urgent 9, high 7, medium 5, low 2). So a `low` task in a listed project comes before an `urgent` task in an unlisted one.

- **Dispatch.** When several wakes wait for one agent, the desk gets the one whose task ranks highest; at equal rank an `answer` or `blockers_resolved` wake goes first, then the oldest.
- **Inbox.** An item that comes from a task (or from a session working a checked-out task) gets task points: 10 per priority weight (urgent 90, high 70, medium 50, low 20), plus 10 when the project is in `tasks.project_order`, capped at 100. `urgent` and `high` items show a priority chip and the reason `<priority> priority`.

### Checkouts

An agent takes a `todo` task with `task_checkout`. The checkout records the session, the engine and an **epoch** that increases on every checkout. Rules:

- Only the owner checks out: `not the owner (<owner>)`. One live checkout at a time: a second `task_checkout` on a live `doing` task fails with `conflict: checked out by <session> on <engine> (epoch N)`.
- A session that once held the checkout but no longer does is refused on every write: `superseded: task <id> is now checked out by <session> on <engine> (epoch N); stop, your work is stale`.
- **Cross-task write cap.** A hired agent's session that changes tasks outside its own reporting line (tasks it neither checked out nor owns, directly or through a report) spends one of `tasks.cross_task_write_cap` (20) distinct tasks per `tasks.cross_task_write_window_secs` (24 h; `0` means for the session's life). theuth's desk, your own sessions and the sessions they spawn are uncapped, and `task_note` is free. Past the cap: `tasks.cross_task_write_cap: this session has written to N tasks outside <agent>'s reporting line in the last 24 h; the cap is 20. Wait for older writes to age out, delegate with task_create, or ask the owner's manager to make the change.` A capped session's `task_inbox` ends with `cross-task writes: N/20 in the last 24 h` once it has used any.
- `task_note {progress: true}` from the checkout session refreshes the progress clock. Progress notes wake nobody.
- An **orphan sweep** runs every 30 s on the task's home machine. A `doing` checkout is orphaned when its engine has been unreachable for `tasks.orphan_secs` (120 s), or when neither its session nor any of that session's children is working, and both its last progress note and its last activity are older than `tasks.stale_secs` (900 s). The epoch is bumped, a thread note is written and the owner is woken `resume`. When the lost engine was another machine, the session is taken over onto this one if possible. The checkout is kept, so the owner's next `task_checkout` succeeds and the old session is superseded. A paused agent's checkouts are skipped: they are suspended with its turn, not lost.
- When a desk's episode closes, every `doing` task it checked out without a `continuing` disposition becomes `blocked: no continuation`, the checkout is cleared and its manager is woken for review. The same happens when a desk twice ends a turn with its woken task unmoved (it gets one nudge in between).

### Wakes

Agents learn about tasks through wakes, delivered to the agent's desk session as a message beginning `Wake: task <id>`, followed by the title and `Reason: <reason>.` Reasons: `assigned`, `comment`, `mention`, `schedule`, `answer`, `review`, `resume`, `resumed`, `manual`, `reassigned`, `blockers_resolved`, `children_completed`. Wakes coalesce per (agent, task, reason), dispatch every 5 s, one per agent at a time (in rank order, see [Priority](#priority)), and a wake whose reason no longer fits the task's state is dropped with a line in the thread (`wake <reason> for <agent> dropped: stale (task is <state>)`). A failed delivery is retried after 5 s, doubling to 5 min.

A **paused** agent's wakes stay queued, undelivered and without back-off, until you un-pause it; the desktop then says `queues a wake for <agent> (paused)` where it would say `wakes <agent>`.

**Back-off.** Two consecutive wakes that change nothing put the task on a timer: the next wake waits `backoff_min_secs` doubling per repeat up to `backoff_max_secs` (120 s, then up to 1800 s). A task in back-off is hidden from `task_inbox`. Any comment by you resets it.

Wakes go to agents only. You are told through the **Inbox** (sidebar) and the collapsible queue bar at the top of the board: decisions addressed to you, tasks blocked on a person or a system reason, reviews where you are the reviewer, proposed hires, machines that hold waiting tasks offline. There is no push or channel notification for ordinary state changes.

### Machines

In a [mesh](/docs/automation/mesh) the board shows every machine's tasks, but a task belongs to one (machine, agent) pair: its **home**. Only that machine's desks get its wakes, check it out and sweep it; the same agent name on another machine (theuth is on every machine) never picks it up. You can still comment, move, answer and review any task from any machine.

- **Home.** A task is homed on the machine whose roster has its agent: the creating machine when it has the agent (theuth and tasks you own: always), else the one machine that has it, else the creating machine. A routine's `agent:` task follows the same rule from the machine that fires it. The board card shows `on <machine>` with a dot for online/offline; cards homed on another machine are dimmed (hover: `Homed on <machine>`, read-only here) but open. The **Any machine** filter narrows the board to one machine. The task detail shows `Home: <owner> on <machine>`. `task_inbox` lists only the tasks homed on the desk's own machine. A task homed on a machine without its agent waits: its thread says `<agent> isn't on <machine>; this task waits until it is moved to a machine that has <agent> (Move to ▸)` once, and the Inbox shows `<agent> isn't on <machine>; it's on <other>` with **Open task** until you move it.
- **Moving.** Open the task's **⋯** menu (or the **⋯** on a board card) and pick **Move to ▸ \<machine\>**, or ask theuth: `task_move_home {task, to}`. A machine is offered when it is online and has the task's agent (and its reviewer, when that is an agent); otherwise it is greyed out with `no <agent> agent there` after its name, or `offline 5m` under it. The move is checked first; then a live work session on this machine moves along (the row's subtitle says `Its session moves too`, see [Mesh](/docs/automation/mesh)) and keeps working the task there. Without a session that moves, the checkout is cleared (the old session is superseded) and the owner on the new machine is woken `reassigned`. A done or cancelled task does not move (`task is done`). An agent can move a task only from the machine it lives on, and only when it owns the task or the owner reports to it (`only the user, or its owner or the owner's manager on the engine it lives on, moves task <id>`).
- **Home offline.** Nothing runs elsewhere on its own. The task detail shows `<machine> is offline (since HH:MM)` with a **Move to ▸** callout: `Nothing runs elsewhere while <machine> is off. Move it to another machine to continue. If it is still waiting after 5 minutes, you get an Inbox item asking the same.` After `tasks.home_offline_ask_secs` (300 s) with tasks waiting on it, the machine's Inbox item reads `<machine> is offline`, then `N tasks are waiting`, naming the first five, with **Move them to \<this machine\>** (moves the ones whose agent is here and lists the others as `<title> (no <agent> agent here)`) and **Keep waiting** (asks again in an hour). It goes away when the machine returns or its tasks have moved. A home naming a machine this mesh does not know shows the same way, as `an unknown machine`.
- **After a restart.** A machine with paired peers does no task work until its first sync with them is done (or no peer connects within `mesh.lapse_secs`): no wakes, no sweeps, and its desks' task writes answer `this machine is still catching up with the others (first sync after a restart); try again in a minute`. A desk turn that was running when it stopped waits too; it then resumes or, when its task moved meanwhile, ends. So the old machine never continues a moved task: it delivers no wake for it, its checkout is refused (`task <id> lives on <machine>`, followed by `move it here first`) and its desk's task writes are refused (`task <id> moved to <machine>; stop, it is worked there`).
- **Versions.** Every machine must run the same theuth version: an older one ignores homes and dispatches every task to its own desks. Upgrading one machine after the other is fine: on connect each machine sends its homes again.

### Dependencies

`blocked_by` holds what a task waits on: other task ids, `decision:<id>`, `person:<name>`, or a system phrase. `blocks` is the computed inverse and is never stored. Blocker lists are cycle-checked (`blockers would form a cycle: …`). When a task closes (`done` or `cancelled`) its id is removed from every other task's blockers; a blocked task left with nothing to wait on is unblocked automatically (back to `doing` if it still has a live checkout, else `todo`) and its owner is woken `blockers_resolved`. Tasks created with `parent` form a delegation tree; when the last child closes the parent's owner is woken `children_completed`.

### Escalations

An agent that cannot decide something calls `escalate {task, question, options[]}`. That writes `**decision requested** (decision:<id>)` plus the options to the thread, adds a `decision:<id>` blocker, moves the task to `blocked`, and wakes the caller's manager with reason `answer`.

- **Dedupe first.** An agent calls `task_waiting_on_user` to see which decisions and reviews of its line already wait on you. A second escalation of its own on a task that already waits on you is refused (`decision:<id> is already waiting on the user for this task`, plus advice to add a `task_note` instead).
- **Escalating to you** needs a decision packet, and nothing is written without it: `summary` (an abstract of at most 120 words, at most 16 KiB), `board` (the id of a board document whose first three `##` sections are `What you're deciding`, `Why it matters to you`, `The picture`, followed by `Options` and `Look at`) and `if_wrong` (one line, at most 200 characters, on the cost of a wrong answer). Options: at most 4 unless it is a bundle (cap 6, labels up to 80 characters), exactly one `recommended`; optional `pointers` (up to 12, evidence inline) and `items` (a bundle of up to 20 related sub-decisions answered at once). Each refusal starts `escalating to the user needs a` (or `needs`) and names the missing field and what to write.
- **Forwarding.** A manager agent that cannot decide either escalates the same task with `question: ""` and a `recommendation {text, option}`; the report's question, summary, board, options, pointers, items and `if_wrong` are inherited, and the thread says `forwarded from <decision> by <manager>`.
- **Where you see it.** If the manager is you, the question appears as an ask card in the agent's session with the options as buttons (and on your [channels](/docs/automation/channels)), and as a decision item in the Inbox and the board's queue bar.
- **The live wait.** The tool waits `roster.decision_wait_secs` (120 s) for an answer; if none arrives it returns ``parked: task <id> is blocked on `decision:<id>`; the answer re-wakes you. End your turn.`` and the agent stops.
- **Answering.** A manager agent answers with `decide {task, decision, answer}`; you answer from the ask card or the Inbox. The answer goes to the thread, the blocker is removed, and once no blockers remain the task is unblocked and the owner woken `answer`.
- **Leave to agent.** Dismissing a decision in the Inbox (**Leave to agent**) refuses nothing and wakes no one. If the agent is still waiting live, its `escalate` returns `left to you`, the blocker is dropped and it carries on with its own pick. If it had parked, the blocker becomes `left:<decision>` and the task stays blocked; the Inbox shows it as `decision left to the agent`, and the agent's next run is told to choose, record its choice with `task_note` and remove the blocker. **Unblock** also strips a `left:` blocker.

### Review hand-offs

When an agent moves a task to `review` (`task_update {disposition: review}` or `task_move {state: review}`) and the reviewer is you, it must attach a review packet or the move is refused: `summary` (one paragraph, outcome first, at most 16 KiB) and `board` (a board document whose first three `##` sections are `What was done`, `Why it matters to you`, `The picture`, followed by `Against the criteria` and `Walk through`). Optional: `checks` (its status against each `done_when` line), `pointers` (up to 12, evidence inline), `options` (up to 4 next moves after approval, one `recommended`) and `if_wrong` (one line, at most 200 characters). An agent reviewer may receive the same packet but does not require one.

In the Inbox the review screen shows the board, **Acceptance** (the `done_when` and the agent's checks, read-only), **Review these** (the pointers) and **Next move** (the options, recommended pre-picked). **Approve → ‹move›** closes the task as done and writes `**next** (n) <label>` to the thread, waking the owner `answer`; without a pick it reads **Approve → done**. **Send back** needs a note (*What needs to change…*).

### Acceptance criteria

`done_when` is the task's checkable acceptance criteria. Agents draft one to three lines from the brief when you did not state them; the reviewer judges `done` against it first, and it is what makes self-review legal. A desk with no `done_when` on its task is told to judge on your evident intention and to set criteria once it knows them. **The desktop has no field to set it**: the New task sheet creates tasks without `done_when`, and the task detail page neither shows nor edits it (the Inbox review screen shows it read-only under **Acceptance**). Put criteria in your chat request (they land in the draft card and the record) or in the brief; to set it on an existing task, ask in chat and the agent uses `task_update {done_when}`.

### Attachments

A task can carry references of kind `note`, `knowledge`, `artifact`, `session` or `meeting`. Attachments you add to a chat message (`+` in the composer, `/attach` in the terminal) are copied onto the drafts the agent proposes. The board card shows a count; the detail page has an **Attachments** editor; tools replace the whole list with `task_update {attachments}`, and each added or removed reference is an `attached` / `detached` event. There are no separate attach/detach tools.

## Walkthrough: from a chat request to done

Describe the work in any chat, desktop or terminal:

```text
› Audit the relay's TLS setup: check the cert chain, expiry, and cipher list.
  Done when curl shows the new expiry and ssllabs grades A. ops should do it.
```

The model does not create anything yet. It calls `task_draft`, and you get one card per proposed task with the title, brief, owner, project, blockers and the drafted `done_when`, plus three buttons: **Add to backlog**, **Start now**, **Discard**. On the desktop the cards render inline under the tool call and in the artifact panel. Pressing a button sends your choice back as a message; the model then calls `task_create` with `state: backlog`, `state: todo`, or nothing. Drafts are never stored: closing the chat without pressing anything leaves no task.

Pick **Start now**. The task is created as `todo`, owner `ops`, and `ops` is woken `assigned`. In the **Tasks** view the card sits in the **todo** column with the chip `queued for ops's desk`. When the desk's session checks it out the card moves to **doing**, shows a green dot and `at ops's desk · open session`; the detail page's **Sessions** list links to that session (with its cost) so you can read along.

When `ops` finishes it moves the task to **review** with a review packet (its reviewer is its manager, or you). If you are the reviewer the task appears in the board's queue bar and in the **Inbox**, its row leading with the outcome. Open it there: the review screen shows the agent's board, the acceptance criteria with its checks and the next moves it proposes. **Approve → ‹move›** closes it with `done because: intent_met` and releases anything that was blocked on it; **Send back** moves it to `doing` and wakes `ops` with your note. The task detail's **Actions** panel offers the same as **Mark done** (enabled because you are the reviewer) and **Send back** with a *Notes for the owner* box.

Had you pressed **Add to backlog** instead, the card would sit in **backlog** with `not started` until you drag it to **todo**, press **Start** on the card, or press **Start** in the detail page (labelled with `queue for ops's desk`).

## Walkthrough: answering an escalation

While working, `ops` finds two valid cipher policies and cannot pick one. It writes a decision board and calls `escalate` with a summary, the two options, a recommendation and an `if_wrong` line. You see, in `ops`'s session, an ask card with the question, the task's short id and title, and one button per option:

```text
Keep TLS 1.2 for the legacy relay clients, or go TLS 1.3-only?

[ Keep 1.2 ]   [ 1.3 only ]
```

The same decision shows in the board's queue bar and in the **Inbox**, its row leading with the question. The card has a *Your decision…* box and **Answer**; opening it shows the board, the options as cards (the recommended one pre-picked), *Type your own…* and the **If wrong** line. Until you answer, the task is `blocked` and the detail page's **Unblock** button is hidden, because a decision needs its answer, not a force-unblock. Once you answer, the blocker is removed, the task returns to `doing` (or `todo` if the checkout was lost meanwhile), and `ops` is woken `answer` with your reply in the thread. If you take longer than 120 s the agent's turn has already ended with `parked: …`; the wake brings it back. If you would rather not decide, **Leave to agent** hands the choice back to `ops`.

If the escalating agent reports to another agent, that manager gets the wake instead and answers with `decide`; you only see it if the manager escalates further.

## Walkthrough: creating a task by hand

**Tasks › New task** opens a sheet: *Title*, *Brief* (markdown; put links here), *Attachments*, *Project* (combobox; typing a new name offers **New project ‹name›**), *Owner*, *Reviewer* (hint `the owner's manager` while unset), *Where* (a node, or `theuth decides`), *Harness* (`native`, `omp`, `opencode`, `claude`, or `theuth decides`), *Blocked by*, *Blocks*. The only submit is **Create in backlog**: nothing runs until you start it.

In the terminal, `/tasks` lists this project's tasks as `id · state · owner · title`; it does not create or move them. Ask in chat for that. From a shell:

```text
t tasks list --owner agent:ops --state todo,doing,blocked --project relay
```

prints JSON, oldest first. `--owner` takes `agent:<name>` or `user`; `--state` a comma list (the error hint omits `backlog`, but it is accepted); `--engine <node>` filters by placement (`where`).

## Reference

### Config (`tasks:` in `config.yaml`)

| Key | Default | Meaning |
|---|---|---|
| `tasks.orphan_secs` | `120` | A checkout whose engine has been unreachable this long is orphaned and the owner re-woken. |
| `tasks.stale_secs` | `900` | A checkout whose session (and its children) is idle, with no progress note and no activity this long, is orphaned. |
| `tasks.note_secs` | `300` | How often work sessions are expected to write a progress note. Advisory; nothing enforces it. |
| `tasks.cross_task_write_cap` | `20` | Distinct tasks outside its reporting line a hired agent's session may change per window. |
| `tasks.cross_task_write_window_secs` | `86400` | The cap's window; `0` means the session's lifetime. |
| `tasks.backoff_min_secs` | `120` | First no-progress back-off. |
| `tasks.backoff_max_secs` | `1800` | Back-off ceiling. |
| `tasks.place_prefer` | `[]` | Engine names to prefer, in order, when placement leaves several candidates. |
| `tasks.project_order` | `[]` | Project names whose tasks come first, in order; one rank orders wake dispatch and the Inbox by it, with priority breaking ties. |
| `tasks.home_offline_ask_secs` | `300` | A task's home machine unreachable this long, with tasks waiting on it, raises one Inbox item asking whether to move them. |
| `roster.decision_wait_secs` | `120` | How long `escalate` waits live for an answer before parking. |
| `roster.max_rounds` | `3` | Follow-up child rounds a desk may spawn per task per episode. |
| `roster.episode_idle_secs` | `21600` | Desk idle time before its episode closes (open checkouts become `blocked: no continuation`). |
| `roster.attention.weights.task_per_weight` / `task_ranked_project` / `task_max` | `10` / `10` / `100` | Inbox points a task's priority adds (per weight point, for a ranked project, cap). |

Config is read at startup; edits need a restart.

### Tools the model calls

| Tool | Arguments | Notes |
|---|---|---|
| `task_draft` | `tasks: [{title, brief, owner?, project?, where?, blocks[], blocked_by[], done_when?, attachments[]}]` | Read-only. Renders approval cards; persists nothing. |
| `task_create` | `title, brief, state?: backlog\|todo, owner?, reviewer?, parent?, project?, where?, harness?, external?[], done_when?, attachments?[], priority?` | Default state `backlog`; owner defaults to the caller; project to the session's. Other states: `state is backlog or todo, not <state>`. `priority` is refused from an agent. |
| `task_inbox` | `state?: [..], project?` | Read-only. Caller's own tasks homed on this machine, default `todo, doing, blocked`, grouped by project, oldest first; hides tasks in back-off; shows the write-cap budget once used. |
| `task_waiting_on_user` | `project?` | Read-only. Decisions and reviews of the caller's line that already wait on you, oldest first. |
| `task_checkout` | `id` | `todo` (or `blocked` with no blockers) → `doing`; returns the record, attachment markers and the thread. |
| `task_update` | `id, disposition?: done\|review{reviewer}\|blocked{on}\|delegated{to}\|continuing{by}, state?: cancelled\|doing, owner?, reviewer?, blockers?[], title?, brief?, external?[], done_when?, attachments?[], done_because?, priority?`, plus the review packet with `disposition: review`: `summary?, board?, pointers?[], checks?[], options?[], recommended?, if_wrong?` | The owner's own-work path. Other `state` values answer `state <state> goes through disposition`. `delegated` needs an existing child and adds it as a blocker. |
| `task_move` | `task, state, note?, done_because?, next?`, plus the review packet with `state: review` | User-intent moves; refusals list the allowed targets. `next` picks a reviewed task's next move when approving it. |
| `task_reassign` | `task, to, why` | Owner or user; from `todo`, `doing`, `blocked`. Releases the checkout (`doing → todo`); wakes the new owner `reassigned` unless blocked. |
| `task_move_home` | `task, to` | The task's home becomes machine `to` (name or id): online, has the owner agent, task not done/cancelled; only from the machine the task lives on. A work session it had stays (the board's **Move to** moves it). |
| `task_note` | `id, text, progress?` | Comment (wakes owner, reviewer in review, and any agent named in the text) or progress note (wakes nobody). Not counted against the write cap. |
| `task_place` | `id, needs?, where?, harness?, reason?` | Picks an engine by policy, asks theuth's desk when several fit (120 s wait). No fit: `blocked: engine:<missing>`; owner pinned to a VM that is not ready: `blocked: sandbox:<name>`. |
| `escalate` | `task, question, summary?, board?, options?[], recommended?, pointers?[], recommendation?, items?[], if_wrong?` | Agents only; you get `you are the top of the line; decide it`. `summary`, `board` and `if_wrong` are required when the manager is you. |
| `decide` | `task, decision, answer` | Answer a `decision:<id>` blocker. |

All are mutating except `task_draft`, `task_inbox` and `task_waiting_on_user`.

## Safety and permissions

- Every task write by the model is a **mutating** tool call: with the default policy you see an Allow/Deny card for `task_create`, `task_move`, `task_update`, `task_note`, `task_reassign`, `task_checkout`, `task_move_home`, `task_place`, `escalate` and `decide`. Desks that run unattended usually have approvals relaxed; the switches are `/approvals off` (this session), `/approvals off always` (`tools.approvals: false`) and **Settings › Agent › Approvals**. The approval card offers only Allow and Deny; to keep the tools away from a chat altogether, use **Settings › Tools › Builtins › Tasks**. Details: [Tools and permissions](/docs/reference/tools-permissions).
- Draft approval is a prompt rule, not a ledger rule: `task_create` accepts any agent call. What the ledger does enforce is the transition table, ownership on checkout and update, the reviewer-only close, the no-self-review-without-criteria rule, the user-only priority, the review and decision packets addressed to you, the superseded-writer check, the home check and the cross-task write cap.
- Only an agent that owns a task (or you) can check it out, move it to review, or reassign it. Only the reviewer can close it or send it back. You can act as anyone; the event log records you as `user@<client>`.
- `escalate` wakes the caller's manager, never an arbitrary agent; an agent whose line ends at theuth escalates to you.
- A desk's wake delivery, nudges and `no continuation` rule mean an agent cannot silently keep a task checked out forever: the orphan sweep, the episode close and the back-off all return control to the board.
- MCP clients that hold the server's token can create, update and move tasks with no theuth-side approval; see [MCP](/docs/reference/mcp).
- The task thread is a document of kind `task_thread`; it is hidden from the Notes lists but readable through the detail page.

## Limits and lifecycle

| Thing | Value |
|---|---|
| States | 7; `done` and `cancelled` are final |
| Priorities | 4 (`urgent`, `high`, `medium`, `low`); default `medium`; user only |
| Live checkouts per task | 1 (epoch bumps on every checkout) |
| Orphan sweep | every 30 s; `orphan_secs` 120 / `stale_secs` 900 |
| Wake dispatch | every 5 s, one wake per agent at a time, highest rank first; delivery retry 5 s doubling to 5 min |
| Back-off | 120 s doubling to 1800 s after two unchanged wakes |
| Escalation live wait | 120 s, then parked |
| Decision packet | summary 16 KiB (abstract up to 120 words); options 4 (bundle cap 6, labels 80 characters); items 20; pointers 12 (32 KiB text each); `if_wrong` 200 characters |
| Review packet | summary 16 KiB; options 4; pointers 12; `if_wrong` 200 characters |
| Placement wait on theuth's desk | 120 s |
| Cross-task writes per hired agent's session | 20 per 24 h |
| Child rounds per task per episode | `roster.max_rounds` 3 |
| Activity feed | 50 entries by default, 500 max |
| Fields that do not exist | due date, labels, an assignee separate from owner |
| Retention | none: done and cancelled tasks are kept; there is no archive or prune |
| Replication | `tasks`, `wakes`, `answered` and `packets` tables replicate across mesh peers |

Routine-created tasks: each fire of a routine with an `agent:` line files a `todo` task titled `<routine> @ <time>` owned by that agent, one per fire; when the routine's `until` passes, its open tasks are set `done` with reviewer `system`. See [Schedules](/docs/automation/schedules). Hires file a `Hire agent <name> (<title>)` task for the proposer's manager, and budget warnings file `Budget: <name> at 80 % (…)` tasks. See [Agents](/docs/automation/agents).

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `backlog → done is not allowed (a backlog task is started first (todo), then checked out); from backlog you may move to: todo, cancelled` | Trying to skip states. | Start it (`todo`), let the owner check it out, review, then done. |
| `todo → doing is task_checkout` | `task_move`/`task_update` cannot start work. | The owner calls `task_checkout {id}`. |
| `done needs a reviewer other than the owner (self-review is only allowed against an explicit done_when)` | Agent is its own reviewer and the task has no `done_when`. | Set criteria via chat (`task_update {done_when}`) or name another reviewer; or mark done yourself. |
| `a self-reviewed task is done only because its done_when criteria are met` | Self-reviewer passed `intent_met` / `follow_ups_filed`. | Use `criteria_met`, or have the manager close it. |
| `priority is the user's to set; say why in task_note and the user decides` | An agent tried to set `priority`. | Set it yourself from the Inbox or your own chat. |
| Refusal starting `handing work to the user's review needs a` (board or summary) | An agent moved a task to your review without a review packet. | The agent writes the board and summary and retries; nothing changed on the task. |
| Refusal starting `escalating to the user needs` (board, summary or `if_wrong`) | An escalation to you without the decision packet. | The agent completes the packet and retries; nothing was written. |
| `decision:<id> is already waiting on the user for this task` | The agent already escalated this task to you. | Answer the waiting decision; the agent adds new facts with `task_note`. |
| `conflict: checked out by <session> on <engine> (epoch N)` | Another live session holds the task. | Wait for the orphan sweep (120 s unreachable / 900 s idle), or reassign it; do not create a duplicate. |
| `task <id> lives on <machine>`, then `move it here first` | `task_checkout` on a task homed on another machine. | Let that machine's desk work it, or move it here with **⋯ › Move to ▸**. |
| `task <id> moved to <machine>; stop, it is worked there` | The owner's desk on the old home wrote a task that moved away. | Expected; the new home works it. |
| **Move to** row greyed with `no <agent> agent there` | The machine's roster lacks the owner (or the agent reviewer). | Hire the agent there, or reassign the task to an agent that machine has. |
| `this machine is still catching up with the others (first sync after a restart); try again in a minute` | The machine has not finished its first sync with its peers. | Wait; it resumes task work after the sync. |
| `superseded: task … stop, your work is stale` | The session lost the checkout to a newer epoch. | That session must stop; the current checkout owner continues. |
| `tasks.cross_task_write_cap: this session has written to 20 tasks outside <agent>'s reporting line …` | One hired agent's session editing many other lines' tasks. | File child tasks and let owners do their own writes, wait for the window, or raise the cap only if this is intended. |
| Task stuck in `blocked` with `decision:…`; **Unblock** missing | An escalation awaits an answer. | Answer it: the ask card in the agent's session, or the Inbox. Or **Leave to agent**. |
| Task `blocked` on `left:decision:…` | You left a parked decision to the agent; it acts when it next runs. | Wait for its next wake, or press **Unblock**. |
| Task `blocked: no continuation` | Desk episode closed, or the desk twice ended a turn without moving its woken task. | Open the task and press **Unblock** (your move strips system blockers), or reassign it. |
| `blocked: engine:<name>` / `blocked: sandbox:<name>` | Placement found no fitting node, or the owner's VM is not running. | Pair the node ([Mesh](/docs/automation/mesh)) or start the VM ([Sandboxes](/docs/automation/sandboxes)); then Unblock. |
| Agent never picks up its task | The agent is paused (its wakes queue), or the task is homed on a machine without the agent. | Switch it back to Active on its agent page (a budget pause also offers **Un-pause** in the Inbox); or **Move to ▸** a machine that has it. |
| Agent keeps getting woken but nothing changes; task missing from its inbox | Back-off after two unchanged wakes. | Comment on the task; your comment resets back-off. |
| ``parked: task … is blocked on `decision:…`; the answer re-wakes you. End your turn.`` in a transcript | Escalation outlived the 120 s live wait. | Normal; the answer wakes the agent again. |
| `you are the top of the line; decide it` | `escalate` called in your own session. | There is nobody above you: answer in chat or set the task yourself. |
| `blockers would form a cycle: …` | A `blocked_by` edge loops back. | Remove one edge in the **Blocked by** / **Blocks** chips. |
| Draft card buttons do nothing / task never appears | The press is a chat message to the model; it must still call `task_create`. | Check the session is not waiting on an approval card; re-ask "add draft d1 to the backlog". |
| `t tasks list` prints a connection error | No engine running. | Start the desktop app, or `t --serve`. |
