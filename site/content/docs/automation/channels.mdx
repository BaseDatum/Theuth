title: Channels — Slack and Signal
description: Talk to theuth from Slack or from your phone over Signal — setup, who may talk, how threads and contacts map to sessions, approvals from chat, voice notes, and the limits.
---

Channels let you use theuth from a chat app instead of the desktop app or the terminal. Slack turns the bot's DM (and `@theuth` mentions in channels you list) into sessions whose replies stream into a thread; Signal pairs the daemon as a linked device so texts from your phone become turns in a per-contact session. Both are full frontends — the same tools, the same approval rules — and both double as the place where tool approvals and `message_user` deliveries reach you when you are away from your desk.

## Prerequisites

- **A running daemon.** Channels only run in `t --headless`. The desktop app starts `t --headless` for you, so leaving the app open is enough; the terminal UI alone does not connect to Slack or Signal (`slack_status` / `signal_status` answer `daemon only` there).
- **A model provider** configured, as for any session — see [Models and providers](/docs/getting-started/models).
- **Slack:** permission to create an app in your workspace, plus your member id (`U…`). Tokens are stored in the secrets vault as `slack_bot` and `slack_app`, never in `config.yaml`.
- **Signal:** a Signal account with a primary phone. The daemon joins as a *linked device*, so the usual setup is a dedicated number on a spare phone that you text from your own account. Group messages are ignored, and "Note to Self" on your own account is not supported, so a second number is in practice required.
- **Voice notes (optional):** the voice plugin (`voice.enabled`, on by default) and the local speech models under `~/.theuth/models/`. The desktop app downloads them; `t` on its own does not (use `scripts/fetch-models.sh` from the repository on a server).

Approvals, risk levels and the `tools.policy` keys are shared with every other surface; [Tools and permissions](/docs/reference/tools-permissions) has the full story.

## How it works

Each channel is a plugin inside the daemon that maps a conversation to a session:

| | Slack | Signal |
|---|---|---|
| Unit of conversation | one thread (`channel:thread_ts`) | one contact (phone number) |
| New session | a top-level DM message, or an `@theuth` mention in a listed channel | the first message from a contact, or after `/new` |
| Follow-up | a reply in the thread: steers a running turn, else starts the next one | the next text: steers a running turn, else starts the next one |
| Pick up an old session | `/theuth resume <id>` in a new thread | `/resume <id>` |
| Progress | 👀 on your message while working, then ✅ done / 🛑 cancelled / ❌ error | same reactions, plus a typing indicator and read receipts |
| Output | one streamed bubble per turn, task cards per tool call, a quoted reasoning message, a footer with model, tokens and time | plain text in chunks of 2 000 characters |
| Inbound files | `~/.theuth/slack/inbox/` | `~/.theuth/signal/inbox/` |
| Bindings kept in | `~/.theuth/slack/threads.json` | `~/.theuth/signal/threads.json` |

Sessions started from a channel are ordinary sessions: they appear in the desktop sidebar and `/sessions`, they can be resumed from the terminal with `t --resume <id>`, and they get the same tool set and approval policy as a chat you start on the desktop. Only the *scope* differs: roots opened by the owner are `owner` scope (they can see and message your other sessions when communication is on); roots opened by any other allowed user are `isolated`.

**Routing to a named agent.** Start a message with an agent's name and a colon — `researcher: find three recent papers on …` — and the turn goes to that roster agent instead of theuth; `theuth: …` returns to the default. Agents are described in [Agents](/docs/automation/agents).

**Several engines.** In a [mesh](/docs/automation/mesh) only the engine holding the hub lease opens the Slack socket (the others report `Disconnected` with reason `hub lease held elsewhere`). Every engine stays linked to Signal and listens, but only the hub answers; the others drop the message silently.

## Walkthrough: set up Slack and send the first DM

Run the guided setup in a terminal. It asks for three tokens, verifies each one, and skips any step whose token already works on a re-run:

```text
$ t --slack-setup
config token: xoxe.xoxp-…        ← api.slack.com/apps → Your App Configuration Tokens
created app A0123456789; install it: https://api.slack.com/apps/A0123456789/install-on-team
bot token: xoxb-…                ← after installing, OAuth & Permissions
app-level token: xapp-…          ← Basic Information → App-Level Tokens, scope connections:write
owner member id: U0123456789
slack ready: run t --headless and DM the bot
```

Step by step:

1. The **app configuration token** lets setup create the app from the bundled manifest (`--app A…` updates an existing app instead; if scopes changed you are told to reinstall). The install URL is printed; open it and install the app to the workspace.
2. The **bot token** (`xoxb-`) is checked with `auth.test`; the **app-level token** (`xapp-`, scope `connections:write`) with `apps.connections.open`. Each prompt allows three attempts.
3. Your **member id** (`U…`, from your Slack profile menu) becomes `slack.owner`.
4. Setup writes `slack_bot` and `slack_app` into the secrets vault and `slack.owner` / `slack.enabled: true` into `config.yaml`.

If you prefer to click through api.slack.com yourself, `t --slack-manifest` prints the manifest; create the app "From a manifest", install it, then `t --secret-set slack_bot`, `t --secret-set slack_app`, and set `slack.owner` in `config.yaml`. The manifest asks for the bot scopes `chat:write`, `im:history`, `im:write`, `app_mentions:read`, `reactions:write`, `files:read`, `files:write`, `commands`, `assistant:write`, subscribes to `message.im`, `app_mention`, `agent_session_stopped` and `agent_session_title_changed`, enables Socket Mode and interactivity, and registers the `/theuth` slash command. It deliberately has no `channels:history` scope: the bot cannot read channel traffic it is not mentioned in.

Start (or restart) the daemon, open the **theuth** app in Slack and send a DM:

```text
› is the nightly build green? check the last CI run and tell me what failed
```

What you see in Slack:

- 👀 appears on your message, a thread opens under it, and the reply streams into one message that updates as the model works.
- Reading the repository needed no permission. The first command did, so a card arrives in the same thread:

```text
⚠️ shell wants to run
$ gh run list --limit 1 --json conclusion,url
[ Allow ]  [ Deny ]
```

- Click **Allow**. The card rewrites itself to `✅ shell allowed by @you`, the task card for that tool fills in, and the answer follows with a footer (model · tokens · elapsed). The reaction flips to ✅.
- To add something mid-turn, reply in the thread: a running turn is steered; after it finishes, the reply is the next turn of the same session. A fresh top-level DM is a fresh session.

The desktop shows the same session in the sidebar; **Settings › Channels › Slack** shows the bot state, the owner, and editable **Allowed users** and **Channels** lists.

To let the bot answer in a channel, add the channel id and mention it: `/theuth slack channel add C0123456789`, then `@theuth summarise this thread`. Messages in that channel that do not mention the bot are never delivered to theuth.

## Walkthrough: pair Signal and send a voice note

On a machine with a terminal (the owner number is your personal Signal number, in E.164 form):

```text
$ t --link-signal --owner +15551234567
scan this QR from Signal › Settings › Linked devices › Link new device
[QR code]
linked as +15557654321; owner +15551234567; run t --headless
```

Scan the code from the phone that owns the *dedicated* account. The command writes `signal.owner` (and `signal.device_name`, default `theuth`) to `config.yaml`; the account state lives in `~/.theuth/signal/presage.db`. Alternatively, with the daemon already running, open **Settings › Channels › Signal** in the desktop app and click **Link**: the same QR appears with the hint *Open Signal › Linked devices › Link new device, and scan this code*. You can also ask theuth in a desktop chat to set up Signal — it calls the `signal_link` tool and shows the provisioning link. A provisioning code is valid for 90 s and is re-issued automatically until scanned.

**Before the first text:** on the phone that owns the dedicated account, save the owner's number as a contact. Signal delivers most messages with sealed sender, and a sender that is not a contact arrives without a number, so theuth cannot match it against `signal.owner` and drops it.

Now, from your own phone, open the chat with the dedicated number, hold the microphone button and speak:

```text
🎤 "Remind me what I asked you to do about the invoices yesterday, and whether it's done."
```

What happens:

1. The audio file is saved under `~/.theuth/signal/inbox/` and transcribed locally (Parakeet TDT, ONNX, nothing leaves the machine). The model receives a line like `[voice note, 6 s] remind me what I asked you to do about the invoices yesterday and whether it's done`, and is told that this prefix means spoken input and to answer briefly, for the ear.
2. 👀 appears on your message; a typing indicator stays on while the turn runs.
3. The reply arrives twice: as text, immediately, and as a short MP3 voice clip spoken by the local Pocket TTS voice (`voice.voice`, default `peter_yearsley`). If the answer includes a tool step, the prose before it is sent (and spoken) as its own message. Typing a normal text message ends voice mode; the next replies are text only.
4. If the speech model is missing or the voice plugin is off, you still get a turn: the message carries the attachment line followed by `(transcription unavailable)`, and the model answers as if you had typed nothing more than that.

A tool approval on Signal is a plain message:

```text
⚠️ shell wants to run
  gh issue list --label invoices --state all
👍 to allow · 👎 to deny · or /approve k7mq · /deny k7mq
```

React 👍 (or ✅, 👌) on that message to allow, 👎 (❌, 🚫) to deny, or send `/approve k7mq` / `/deny k7mq`. Sending the bare code `k7mq` also approves. Codes are four characters, case-insensitive, and never contain `0 O 1 I l`. theuth marks its own approval message with ✅, ❌ or ⌛ once it is resolved.

## Configuration

Both sections live in `~/.theuth/config.yaml`; any key can be overridden with `THEUTH_SLACK__<KEY>` / `THEUTH_SIGNAL__<KEY>`. Allowlist edits made from chat or the desktop are written back to this file live; everything else needs a daemon restart.

### `slack:`

| Key | Default | Meaning |
|---|---|---|
| `enabled` | `true` | Open the Socket Mode connection when both tokens exist in the vault. |
| `owner` | `""` | Your member id (`U…`). Owner-only commands, may answer any approval, receives approvals for sessions not bound to Slack. Written by `t --slack-setup`. |
| `allowed` | `[]` | Further member ids that may talk to the bot. Each owns their own threads. |
| `channels` | `[]` | Channel ids (`C…`) where an `@theuth` mention is honoured. Empty = DMs only. |
| `tools` | `all` | Which tool calls become task cards in the thread: `all`, `errors`, `none`. |
| `reasoning` | `true` | Post the model's reasoning as a quoted message. |
| `approvals` | `all` | Where approvals for sessions *not* bound to a Slack thread (terminal, desktop, routines) go: `all` = the owner's DM, `threads` = nowhere on Slack. |

### `signal:`

| Key | Default | Meaning |
|---|---|---|
| `enabled` | `true` | Listen as a linked device once paired. |
| `device_name` | `theuth` | Name shown under *Linked devices* on the phone. |
| `owner` | `""` | Your number in E.164 form. Written by `t --link-signal --owner`. |
| `allowed` | `[]` | Further numbers that may text the bot. Each gets its own isolated session. |

### `voice:` keys that matter for channels

| Key | Default | Meaning |
|---|---|---|
| `enabled` | `true` | `false` disables transcription and spoken replies; audio arrives as a plain attachment line. |
| `stt_model_dir` | `~/.theuth/models/parakeet-tdt` | Parakeet TDT ONNX checkpoint (`encoder-model.onnx`, `decoder_joint-model.onnx`, `vocab.txt`). |
| `stt_idle_secs` | `600` | Unload the speech-to-text model after this long unused (about 1.7 GB resident); `0` keeps it loaded. |
| `voice` | `peter_yearsley` | Pocket TTS voice used for spoken replies. |
| `model_dir` | `~/.theuth/models/pocket-tts` | Pocket TTS checkpoint. |

The ONNX Runtime library is looked up at `~/.theuth/models/onnxruntime/`, inside the desktop app bundle, `$ORT_DYLIB_PATH`, or Homebrew. `t --bench-models` checks that the runtime and the STT encoder load.

## Commands

### Slack: `/theuth …`

Replies are ephemeral (only you see them). Unique prefixes are accepted (`/theuth sess`).

| Command | What it does |
|---|---|
| `help` | List the commands. |
| `status` | Daemon and session state. |
| `sessions` | The 10 newest sessions with ids. |
| `resume <id>` | Bind this thread to an existing session (id prefix or suffix is enough). |
| `cancel [id]` | Stop the running turn. |
| `compact [id]` | Compact the session's context. |
| `model [id]` | List models, or switch this session. |
| `agents` | The subagent tree of this session. |
| `prompt` | Show the system prompt. |
| `skills [add <url>\|rm <name>\|sync]` | Manage skills. |
| `mcp [add <url\|json>\|sync]` | Manage MCP servers. |
| `login [name]` / `logout <name>` | MCP OAuth. |

Owner only (anyone else gets `This command is restricted to the owner.`):

| Command | What it does |
|---|---|
| `approvals on\|off [always]` | Stop or resume approval prompts for this session; `always` writes `tools.approvals: false` globally. |
| `slack [status\|allow <U>\|rm <U>\|channel add <C>\|channel rm <C>]` | Connection state; edit `slack.allowed` / `slack.channels`. |
| `communication [on\|off [always]]` | Session or global communication switch. |
| `peers …`, `requests …`, `a2a [reload]`, `broadcast [--next] running\|roots\|<ids> <text>` | Same as the terminal commands of the same name. |

Commands that need a session answer `no active thread here; run it in a DM with the bot or /theuth resume <id>` when run elsewhere.

### Signal: `/…`

| Command | What it does |
|---|---|
| `/help`, `/status`, `/sessions` | Help, state, recent sessions. |
| `/new` | Drop the binding; the next text starts a fresh session. |
| `/resume <id>` | Bind this contact to an existing session. |
| `/cancel [name]` | Stop the running turn. |
| `/compact [summary\|cut\|snap\|style …]`, `/clear`, `/undo`, `/redo` | Context management, as in the terminal. |
| `/model [id]`, `/effort [level\|clear]` | Model and reasoning effort for this session. |
| `/agents`, `/jobs [kill <id>]`, `/prompt` | Subagent tree, background jobs, system prompt. |
| `/skills …`, `/mcp …`, `/login [name]`, `/logout <name>`, `/provider [add <name> <url> <key>\|rm <name>]` | Skills, MCP, OAuth, custom providers. |

Owner only:

| Command | What it does |
|---|---|
| `/approve <code>`, `/deny <code>` | Answer an approval by code. |
| `/approvals on\|off [always]` | Approval prompts for this session, or globally with `always`. |
| `/signal [status\|link\|allow <n>\|rm <n>\|unlink]` | Connection state; issue a new linking QR; edit `signal.allowed`; unlink this device. |
| `/communication`, `/peers`, `/requests`, `/a2a`, `/broadcast` | As in the terminal. |

Unknown or ambiguous commands print the help. Session commands before any message answer `no session yet: send a message first`.

### CLI, tools, desktop

| Surface | Items |
|---|---|
| CLI | `t --slack-setup [--app A…]`, `t --slack-manifest`, `t --link-signal --owner +E164 [--device-name <name>]`, `t --secret-set slack_bot` / `slack_app`, `t --bench-models` |
| Tools the model can call | `slack_status` (no args), `signal_status` (no args), `signal_link{owner?}` — all read-only; `message_user{text, files?, via?}` to send you something out of band |
| Desktop | **Settings › Channels**: *Signal* (Account state, **Link** / **Unlink**, Owner, **Allowed numbers**) and *Slack* (Bot state, Owner, **Allowed users**, **Channels**) |

`message_user` delivers to the session's own thread or contact when it has one (walking up to the parent for subagents); for a session that started elsewhere it goes to every channel's owner. `via: "slack"` or `"signal"` forces one. Files up to 100 MiB each are uploaded alongside the text — useful for a routine that should drop a report into your DM.

## Safety and permissions

- **Who gets in.** Slack: the owner and `slack.allowed`; DMs from anyone else are dropped silently, mentions from them in a listed channel get an ephemeral `not allowed`, as do their slash commands and button clicks. Signal: the owner and `signal.allowed`; strangers are dropped with no reply at all. Nothing is ever auto-added to an allowlist.
- **What the bot can read.** Slack: only its own DMs (`im:history`) and messages that mention it in `slack.channels`. Signal: only one-to-one messages from allowed numbers; groups are ignored.
- **Approvals follow the normal policy.** Reading needs no prompt; mutating and destructive tools ask, unless `tools.policy` says otherwise. The prompt is a card with **Allow** / **Deny** on Slack and a 👍/👎 or code message on Signal. Unanswered requests are denied after `tools.approval_timeout_secs` (300 s): Slack rewrites the card to `⌛ … timed out (denied)`, Signal sends `⌛ <code> expired`. There is no per-tool "always allow"; `/approvals off` turns prompts off for the session, `/approvals off always` for every session.
- **Who may answer.** On Slack: the owner, or the user who owns the thread. On Signal: only the number the session is bound to; reactions from anyone else and removed reactions are ignored. A code that was already used answers `<code> was already allowed` / `denied` / `timed out` for 600 s.
- **Questions from the model** (`ask_user`) arrive as one card (Slack) or one text message (Signal) per question and are answered by clicking or replying; they expire after `tools.ask_timeout_secs` (1 800 s).
- **Secrets never go through chat.** When the model needs a secret it posts a notice asking you to enter it on the desktop, in the terminal, or with `t --secret-set`. Do not paste API keys into Slack or Signal.
- **Where approvals do not go.** Signal only carries approvals for the session directly bound to a contact — approvals raised by that session's subagents, or by sessions started in the terminal or the desktop, are not sent to the phone; answer those on the desktop or in the terminal. Slack routes approvals of subagents to their own thread (or the nearest bound ancestor), and approvals from non-Slack sessions to the owner's DM when `slack.approvals: all`.
- **Communication scope.** Owner-opened channel sessions are `owner` scope; other allowed users' sessions are `isolated` and cannot reach your other sessions. The owner can change this with `/peers scope owner|isolated`. See [Delegation](/docs/automation/delegation).
- **Storage.** Tokens live only in the encrypted vault. Thread bindings are in `threads.json`; downloaded files stay in the `inbox/` directories and are never garbage-collected — clear them yourself. Transcripts are ordinary session rows, visible to anyone with access to `~/.theuth`.

## Limits and lifecycle

**Slack**

- A single Slack message holds at most 12 000 characters. The streamed bubble rotates to a new message at 11 000 characters or after 270 s (Slack closes streams at about 5 min); a keepalive runs every 25 s.
- Tool output longer than 2 500 characters is uploaded as a file in the thread instead of inline. Task card title and details are capped at 256 characters, approval arguments at 600, thread titles at 200.
- Updates are paced: at most one `chat.appendStream` call per 650 ms and one `chat.update` per 1 200 ms across all threads. If Slack answers 429, the client retries, then counts the event in `slack_status` as `RateLimited`.
- Slash commands answer inside Slack's 2.5 s budget when they can; slower ones reply through the response URL.
- Only `message` events of type `im` without a subtype (or `file_share`) and `app_mention` events are processed; edits and deletions are ignored. The native **Stop** button in Slack's agent view sends `agent_session_stopped`, which cancels the turn.
- Threads are renamed to the session title unless you rename them yourself.

**Signal**

- Output is plain text, split into 2 000-character chunks (two retries, 200 ms apart). Quote-replies are passed to the model as `(replying to: "…")`.
- Images and PDFs up to 32 MB are given to the model as input; everything else arrives as a path line only.
- A linking QR is valid for 90 s and is re-issued after 3 s; after 10 unscanned codes the daemon slows to one every 300 s. Reconnects back off from 2 s to 60 s and reset after 30 s of stable connection.
- Removing the device on the phone, **Unlink** in Settings, `/signal unlink` or the `signal_unlink` RPC deletes `presage.db` and returns to the QR rotation; thread bindings are kept.
- Audio longer than 180 s is transcribed in 180 s pieces. Supported containers: aac/m4a, mp3, ogg/opus, wav, webm/mkv. Transcription and spoken replies load their models on first use; the STT model is unloaded after `voice.stt_idle_secs`.

**Not available.** Signal groups, "Note to Self", and approvals for Signal-rooted subagents on the phone. Private Slack channels (`G…` ids) are accepted by the config validator, but the manifest has no `groups:*` scope, so as of this writing treat channel mentions as a public-channel feature. The phone and browser microphone in the theuth composer is a different path (recorded in the app, uploaded with a 16 MB cap, transcribed by the same local model) and is covered in [Voice](/docs/workspace/voice).

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `slack_status` says `unconfigured (secrets slack_bot / slack_app missing; run t --slack-setup)` | one or both tokens are not in the vault | run `t --slack-setup`, or `t --secret-set slack_bot` and `t --secret-set slack_app` |
| `slack_status` / `signal_status` says `daemon only (runs in t --headless)` | you are in the terminal UI or `-p` mode | start `t --headless` (or the desktop app) and keep it running |
| DM to the bot gets no reaction and no reply | sender is neither `slack.owner` nor in `slack.allowed` | `/theuth slack allow U…` from the owner, or Settings › Channels › Slack › Allowed users |
| `@theuth` in a channel is ignored | channel id not in `slack.channels` | `/theuth slack channel add C…`; check the id starts with `C` |
| Log warns `agents.sessions.setStatus refused` | app was not created from the manifest (no `agent_view`) | recreate the app with `t --slack-setup` or from `t --slack-manifest` |
| Slack's **Stop** button does nothing | `agent_session_stopped` missing from Event Subscriptions | re-create the app from the manifest; the event is in it |
| Slack shows `Disconnected` with `hub lease held elsewhere` | another engine in the mesh is the hub | expected; the hub answers. Change with `t mesh hub prefer` on the engine you want |
| Log warns `dropping signal message from a number not in the allowlist` with `sender=unknown` | sealed sender: the owner is not a saved contact on the primary phone | save the owner's number as a contact there; the resolution cache clears after 300 s |
| Same warning with a real number | number not in `signal.owner` / `signal.allowed` | `/signal allow +E164` from the owner, or Settings › Channels › Signal › Allowed numbers |
| `t --link-signal` prints `already linked as <number>` | this data dir is already paired | `/signal unlink` (or Unlink in Settings) first if you want a different account |
| Settings › Channels › Signal shows `unlinked` and a QR | the device was removed on the phone or unlinked | scan the new code; the sessions and allowlist are untouched |
| Voice note answered with `(transcription unavailable)`; log says `voice note not transcribed` | `voice.enabled: false`, no checkpoint (`no STT model in <dir>`), or no `libonnxruntime` | start the desktop app once to download the models (or run `scripts/fetch-models.sh`); `t --bench-models` shows what loads |
| Voice note transcribed as `(nothing recognized)` | silence or unsupported speech in the clip | re-record; check the clip plays back |
| No spoken reply, only text | the voice actor is not running, or you typed a message since (voice mode ended) | check `voice.enabled`; send another voice note |
| `This command is restricted to the owner.` | the command is owner-only | run it from the owner account, or have the owner add you with the relevant `allow` |

Logs are in `~/.theuth/logs/theuth.log.<date>`; run the daemon with `RUST_LOG=debug` to see dropped envelopes and allowlist decisions.
